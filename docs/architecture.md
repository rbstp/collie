# collie architecture 🐑

```
iPhone (Collie.app)                                   Mac (or Linux)
┌───────────────────────────────┐                     ┌──────────────────────────────────────┐
│ SwiftUI (Swift 6, UI only)    │                     │ collied (launchd agent, user)        │
│  └ CollieCore (UniFFI)        │   tailnet (WG)      │  ├ tailnet node (user-owned)         │
│     ├ protocol codec          │ ── WebSocket/JSON ─▶│  │   tailscale_listen :port only     │
│     └ tailnet node (libts)    │   dial only         │  ├ whois gate → paired node IDs      │
│ CollieWidgets  (Swift only)   │                     │  ├ protocol allowlist + audit log    │
│ ColliePush NSE (Swift only)   │◀── APNs ────────────│  ├ approvals (nonce, expiry, replay) │
└───────────────────────────────┘                     │  ├ APNs client (Keychain .p8, HTTP/2)│
                                                      │  └ herdr client ─▶ herdr.sock (0600) │
                                                      └──────────────────────────────────────┘
```

On Linux, collied is a systemd user unit, its embedded node is user-owned and the `.p8` is by default a systemd user credential: [Linux](#linux).

## Decisions (2026-10-03)

- Phone and computer run independent embedded nodes owned by the same personal Tailscale user. Authorization checks the node's own positive owner, a same-user untagged and unshared whois, the paired StableID and independent TLS key pins. Neither needs an OS VPN profile or the native Tailscale client; the Mac's corporate VPN is separate.
- libtailscale: upstream submodule pinned by SHA + patch series in `crates/tailscale-sys/patches`.
- iOS project generated by XcodeGen from `Collie/project.yml`; `.xcodeproj` is not checked in.
- APNs display content (alert titles, bodies and approval context; initial, update and end Live Activity labels and state) is authenticated ciphertext under each phone's per-machine notification key. Public alerts stay generic. Approval nonces never enter a push.
- macOS: arm64 only.
- 2026-10-04: collied also runs on Linux. x86_64 is built and tested; aarch64 is mapped in `tailscale-sys` but not built or tested. Any other OS is a compile error.
- 2026-10-04: on Linux the service is a systemd user unit with the launchd agent's semantics: kept alive, and `collied stop` keeps it off across reboots until `collied start`.
- 2026-10-04: each machine sends its own pushes with its own APNs key (own key ID, revoked on its own). On Linux the key is a systemd user credential (host key, plus the TPM2 when systemd finds one usable), or a 0600 file when systemd-creds is unavailable.
- 2026-10-06: plain shell panes from the phone ([Terminals](#terminals)): off by default, turned on per machine in `collied.toml` only, never from the phone; their own allowlist class, audited like prompts. Opening one and typing into it need a grant that collied verifies, signed by a second Secure Enclave key that signs only after Face ID or the passcode. One grant covers one terminal for 5 minutes in one session.
- 2026-10-16: user-owned embedded desktop nodes replace the per-OS tagged identities. Existing tagged nodes and old phone owner pins need an explicit reset and re-pairing; nothing is migrated or retagged. Normal user key expiry applies on both ends. No version bump: no phone wire type changed; the positive owner pin is local persistence and the OS is netmap presentation metadata.

## herdr integration (verified against 0.9.3 source and live socket)

- The socket answers **one request per connection** (NDJSON, 5 s timeouts, 1 MiB line). collied opens a connection per call; long calls (`events.subscribe`, waits) get their own.
- herdr has **no auth**: same-UID means full control. collied's allowlist is the only boundary between the phone and every shell on the machine.
- **No global agent-status stream.** `pane.agent_status_changed` is per pane and `pane.updated` does not fire on status changes. collied keeps one subscription connection: all lifecycle events plus one status entry per agent pane, rebuilt (subscribe, then `session.snapshot`) on `pane.created/closed/moved/exited/agent_detected`, `workspace.closed` and `events_lost`. An entry for a vanished pane goes silent rather than erroring, so lifecycle events drive the rebuilds. A 1 s `agent.list` reconcile plus `ping` covers silent streams. It sends `agent.status` when an agent's `state_change_seq`, status, title, name, kind or cwd changes, or, while a phone has a session open, its transcript values ([below](#context-and-inbox)); and `flock.changed` when agents come, go or change workspace, or a workspace is renamed or renumbered.
- Agents are keyed by `terminal_id`; `pane_id` changes on cross-workspace moves and is never sent to the phone. Status set is `idle | working | blocked | done | unknown`.
- With no phone session connected, a status change reads no transcript and builds no status event; status times, pane cleanup, approvals, done alerts and followed Live Activities still update. Disconnecting releases the session's terminal watch and event subscription before the close handshake; reconnecting fetches a fresh snapshot. A connection lost without a close frame ends at the 45 s silence limit (collied pings every 15 s). Tailscale upkeep and APNs notifications do not depend on the app connection.
- **No output stream** in the JSON API. While a phone watches an agent (`agent.watch`), collied polls `agent.read {source: recent_unwrapped, lines, format: ansi}` at 4 Hz with the phone's `lines` (clamped to 1 to 1000, 200 when absent) and pushes only changes: it compares a hash of herdr's raw text first, and only changed text goes through `sanitize_ansi`, the reflow and the diff. After 5 s without a change the poll drops to 1 Hz until the next change, which can therefore arrive up to 750 ms later. In Low Data Mode (`NWPath.isConstrained`) the phone sends `low_data: true` on `agent.watch` and `terminal.watch`, and collied polls that watch at 1 Hz throughout; `low_data` can only slow a watch. The app reports every path update to the core; a change applies to the next watch (opening an agent, a re-watch after a patch that did not apply, or the next session, which every return from the background starts). `herdr terminal session observe` (binary protocol, exact version match) is a later option.
  - The first push of each watch is a full `agent.output`. Later ones are `agent.output_patch {terminal_id, base, head, skip, keep, tail, trail, truncated}` when that carries at most half the text. The new text is, joined with `\n`: the `head` lines, lines `skip..skip + keep` of the previous text (the longest run both share), the `tail` lines, then the last `trail` lines of the previous text, which must start at or after `skip + keep`. The unchanged input box and status line are not resent, so a Claude Code spinner tick costs a few hundred bytes instead of about 1 to 3 KB depending on pane width (a full read is about 120 KB). `base` is the 64-bit FNV-1a of the previous text; collie-core applies a patch only to the text its watch delivered last (not a read reply) and only when `base` matches, otherwise it re-issues `agent.watch`, which restarts with a full `agent.output`.
  - The phone sends the depth chosen in Settings > Terminal > Scrollback (200, 500 or 1000 lines, default 200, per device) on `agent.watch` and on its `recent` reads; a change applies to the next watch, which the agent screen issues each time it appears. The phone renders up to 2000 rows (`TerminalScreen.maxRows`). In wrap mode it drops the oldest lines that would not fit before rendering, counting the rows each line wraps into, so soft wraps stay tracked; only a line taller than counted (a character Ghostty draws wider than counted) still scrolls the screen and leaves them unknown (`wrapsUnknown`). Lines break after the last space that fits (a longer word breaks by character) and continue at the line's indent, or past a leading symbol and its spaces such as `⏺` or a bullet; each break is a NEL, so selection, copy and links read the line whole. A box-drawn row wider than the phone (a panel padded to the Mac's width, like `/workflows`) has its space runs after the first character cut to the longest length that fits (one cell when none does), borders and column order kept, so padding before a border goes before indentation inside the box. Without wrapping the grid is 500 columns wide (`TerminalScreen.maxColumns`), but each row is read only up to the widest the snapshot reaches. The view renders on the main thread (about 3 ms for 1000 wrapped lines, measured on a Mac), so a snapshot arriving during a scroll renders when the scroll stops. Copying a terminal selection crossfades Copy to a green Done checkmark and a Copied label; the selection closes after 800 ms and Universal Clipboard stays enabled.
  - Claude Code's fullscreen mode (`"tui": "fullscreen"`) draws in the alternate screen and keeps its transcript itself, so the pane has no scrollback and an ANSI read returns only the visible rows.
  - Reads and changed watch output drop Copilot's terminal-cell scrollbar before either wrap mode renders: only a trailing `┃` at the scrollbar column, separated from content by a space. Box borders and bars inside text stay; a separately styled scrollbar beside a box is removed and the box's border kept, and at that column a styled `   └ ` tool-result connector is not a border, even when it shares one SGR run with the scrollbar. Repeated, separately styled scrollbar cells outside boxes give the column even when herdr reports another pane width (Copilot 1.0.100-1 can draw the scrollbar one column inside that edge); without that evidence the pane width is used, never unstyled bars. Wrap detection runs on the original rows at that width; without a known layout width rows stay unjoined. No version bump: only read normalization changes. Copilot prompt boxes keep one continuous dark background while wrapping, without adding indentation to copied text.
  - Copilot's `wraps` and `splits` (as for Claude Code, below) cover its prose under `●` and its sent prompts, read from the screen alone. A sent prompt is a shaded box from a `▄` row to a `▀` row whose first row is `❯`, the text and an `HH:MM` timestamp; Copilot wraps the text before that timestamp like wrap-ansi with `trim: false`, so the width comes from the box, not the pane. A row joins the next only where Copilot certainly broke it after a word: it ends with one space in the text's style and the next word would not have fit. Full rows (ending at a word, or a long token such as a URL, a path or CJK text cut at the width, and the row after, which may start with a hidden space), blank rows, rows starting with a space and a box whose top row scrolled away stay as they are, since a typed newline looks the same. When a prompt's first row joins, the phone moves the timestamp after the joined prompt, and spaces joining shaded rows keep the shade.
  - Claude Code wraps its prose at the pane width with real line ends, which `recent_unwrapped` cannot undo. For a Claude Code agent, `agent.read` and each changed watch push list the rows that continue a paragraph wrapped at the layout width: `wraps` (after a space) and `splits` (inside a word), on `TerminalRead`, and on `agent.output_patch` only when they changed. The width is that of the widest row made only of `─` from column 0 that is no wider than the pane (the input box's rules, which Claude Code draws at exactly the terminal width; wider rows are scrollback from before the pane narrowed), else the pane width from herdr `pane.layout`. Prose rows join the way `agent.draft` reads the input box (below), hidden column after a full row included; a blank row there still ends the paragraph. A run of wide characters cut one column short of the edge, where the next one did not fit, splits only when it is a word longer than a row, so Korean words keep their spaces. Only these rows count: prose under an indent-0 `⏺` or `※` row, at exactly the hang of the row above (for a numbered item also at its number's indent, where Claude Code 2.1.303 continues items separated by blank rows; a list item on the `⏺` row itself, as when a reply starts with `1.`, hangs past its marker like the items below it); and a shaded sent prompt's rows, which Claude Code wraps 3 columns short of the terminal width (after `❯ ` and one column of padding), after a row it ended with a space in the text's style where the next word would not have fit. Never list items, tool call headers (their `⏺` blinks while the tool runs, so an indented row such as `Bash(…` right after a blank row counts as one; a prose row such as `foo(bar)` inside a paragraph still joins), tool output under `⎿`, box and table rows, the input box or the status line. The `pane.layout` width is 1 to 3 columns wider than the terminal (1 for a single pane, 2 or 3 in a split), enough to read a soft wrap as a typed newline. A zoomed tab, or a width herdr does not give, joins nothing. Claude Code's true black background (a standalone `48;2;0;0;0`, which its logo uses) becomes the default background in both, so it does not show as black cells on the phone. With line wrapping on, the phone shows the text with those rows joined (collie-core's `TerminalSnapshot.reflowed`) and wraps it at its own width; with it off, it shows the Mac layout unchanged.
  - Codex's `wraps` and `splits` (its prose under `•` and its sent prompts under `›`) use the width of the widest blank row shaded from column 0 that is no wider than the pane (the blank rows of its composer and sent prompt boxes, which Codex pads with their background to exactly the terminal width; wider rows are scrollback from before the pane narrowed), else the `pane.layout` width, which is 1 to 3 columns too wide here as well (codex-cli 0.163.0 and herdr 0.9.5: 205 columns for a 206-column rect, 101 and 100 for two 103-column split panes).
- `agent.prompt` refuses blocked agents, but herdr's `agent.send_keys` does not. collied rejects `agent.prompt` for an agent it sees as `blocked` (re-read with `agent.get` just before the call). `agent.send_keys` and `agent.type_text` reach a blocked agent as manual input over the paired session, without a nonce or expiry ([Prompts without decisions](#prompts-without-decisions)); only `approval.decide` checks those.
- **Scrolled-up Claude Code.** While Claude Code's fullscreen transcript is scrolled up on the machine, a permission prompt scrolls out of view with it and herdr reports the agent idle, so keys would answer it unseen. collied refuses `agent.send_keys`, `agent.type_text` and `agent.prompt` to a Claude Code agent that is not blocked, with `agent_not_ready`, when the visible screen (`pane.read source=visible format=ansi`, read just before the write) shows the "Jump to bottom" or "N new messages" banner. `protocol::jump_banner` matches it as Claude Code draws it, centered over whatever row is there on an SGR background with a space of padding each side: on any row, a background run that is exactly the padded label, alone or with its hint; or, since herdr writes no escape between the banner and a prompt's text in the same style, a padded label and hint inside a background run, centered on the row within half a display column.
  - `agent.scroll_bottom {terminal_id}` (Drive class, audited with the terminal, idempotent so no `op_id`) sends Claude Code's Ctrl+End (`scroll:bottom`) as the fixed bytes `ESC[1;5F` through `pane.send_text` (herdr 0.9.3 has no key name for it), only to a `claude` agent that is ready or blocked and only while the banner shows; nothing the phone sends becomes input. Ctrl+End never moves a dialog's selection, and a prompt it brings back is `blocked` again with a new `state_change_seq`, so its approval is raised again. The phone shows a Jump to bottom button while `TerminalSnapshot.jump_banner` is set for a Claude Code agent, with the key strip off.
  - Limits: text quoting the banner reads as scrolled up only when drawn the same way (a prompt row, diff line or other background text holding exactly the padded banner, or holding it padded at the row's center), until it scrolls away. A banner drawn without color (`FORCE_COLOR=0`) or in reverse video is not detected. A prompt that appears while the transcript is already scrolled up is not seen as `blocked`, so no approval or notification is raised until it is scrolled back down.
- **Claude Code notices.** Claude Code answers its notices above the input box (the "Heads up" tip `1: Learn more   2: Knew this already   0: Dismiss`, the explanation after Learn more `1: Understood   2: Chat in main session   0: Dismiss`, the feedback rows after a Dismiss, the session rating `1: Bad    2: Fine    3: Good    0: Dismiss`) with a single keypress, which a prompt cannot carry (herdr pastes it and ends it with Enter). `protocol::notice` reads any notice's options and labels from the screen by one rule, not a list of known notices:
  - Anchor: the last row starting at column 0 with `❯`, directly below the box's top rule (a row of `─`, or a renamed session's `─── <title> ─` with exactly one `─` after the title). A dialog replaces the box, so it never matches, and a box whose rule reads otherwise gives no options.
  - Between the options and the rule: at most three blank rows (the box's top margin, which a hint draws over, and two more seen on a real screen) and right-aligned hint rows (indented three or more spaces, such as `● high · /effort`).
  - Options: rows indented two spaces whose cells all read `<digit>: <label>`, digits exactly 1 to n (n up to 4) then `0: Dismiss` last, so a wrapped text row that looks like an option breaks the order; each label non-empty, at most 64 characters, with no control or format character and no `:`.
  - Lead: above the options, a row starting at column 0 with `✦` (tips) or `●` (rating) and a space, then rows indented two spaces or blank. The lead row may carry the first options after its text (`✦ Dismissed.   1: That was helpful   2: Didn’t understand   0: Dismiss`), with the rest wrapped whole onto the option rows directly below it. Transcript rows start with other glyphs (`⏺` reply on macOS, `❯` prompt, `✻` finished turn), so a reply ending in that shape does not match; on Linux Claude Code marks replies with `●` (see the threat model). When the lead holds a blank row, as an explanation does between its header, cards and options, the options must be set off by a blank row above and sit directly on the box's top margin (or the two blank rows above a hint), with no other blank row below them, since the cards are text a side agent wrote and each ends with a blank row. Anything else gives no options.
  - `agent.answer_notice {terminal_id, digit, label}` (Drive class; `digit` `"0"` to `"4"`, `label` as the phone showed it; audited with the terminal, digit and label; no `op_id`, since a replay is refused once the notice is gone) sends that digit alone through `pane.send_text`, no Enter. collied sends it only to a `claude` agent that is ready (never `blocked`, where a digit could pick a permission option), with no "Jump to bottom" banner, and only when the visible screen read last lists that digit with that label directly above an empty input box: notices reuse digits, so a tap on a changed screen is refused. The dim placeholder counts as empty, so a digit never lands in a draft, and a second tap during Claude Code's debounce is refused. collied then holds the input box lock until the box shows something other than empty or the digit, for up to 1 s: Claude Code shows the digit for 400 ms, clears the box and runs the option, which can fill it, and a prompt pasted meanwhile would submit that fill.
  - The phone shows the options as buttons from `TerminalSnapshot.notice` for a Claude Code agent that is not blocked or scrolled up, 600 ms after it first saw them (Claude Code ignores a digit typed sooner and leaves it in the box), hides them after a tap until the next screen, and restores them with the error if collied refuses and no newer screen arrived.
  - What each option does is Claude Code's. Understood marks the topic known. Chat in main session fills the box with the explanation as a quoted note (`Here is a note offered by a side agent:`), unsent (Claude Code submits it only when it has no input box, and collied answers only while an empty one shows), which the phone's prompt field shows on the screen's next visit through draft sync. On the feedback row after a Heads up's Dismiss, 1 to 3 log a feedback event about the tip (enums and counts, never the tip's text or the transcript) and 1 also marks the tip known; 4, with the box empty, fills it with `/plugin disable cc-plugin-you-should-know@builtin`, unsent: tips turn off only when it is sent, and Enter from the key strip is refused while the box starts with `/`; 0 closes the row. Internal builds also list `4: Disable` on the Heads up: the first 4 relabels it `Press again to disable`, the second fills the box with the same command, unsent. A Claude Code plugin whose band draws this shape is answered the same way, and its option's code runs (see the threat model). What follows a rating (`y`, `n` or `d`, a free-text field, `[1]` for `/feedback`) takes another shape and is answered on the machine.
- Prompt text rejects ESC and C0/C1 controls because herdr pastes it with bracketed paste.
- Residual race (herdr side): herdr checks the foreground agent before queuing the text and the delayed Enter. If the agent exits in between, the shell receives the prompt. Closing it needs a conditional input in herdr (`expect: {terminal_id, state_change_seq, foreground pid}` on `agent.prompt` / `agent.send_keys`); to be proposed upstream.
- Mutations (`agent.prompt`, `agent.send_keys`, `agent.type_text`, `task.new` (with or without `new_folder`), `task.archive`, `terminal.run`, `terminal.send_keys`, `attachment.begin`, `attachment.commit`) carry a client `op_id`; collied keeps a per-peer outcome cache so a retry after a dropped connection returns the first result instead of re-running.
- **Task folders.** `task.options` also returns `roots`, the canonical `[tasks] roots`. `task.folders {path}` (Drive class; read-only, so no `op_id`; audited with the requested path and `ok folders=<n>`, plus ` truncated`, never the names) lists the folders directly inside a folder under the roots. collied canonicalizes the path, finds its root and opens it one component at a time from the root with `O_DIRECTORY | O_NOFOLLOW` (`openat`), so a folder swapped for a symlink after the check fails rather than leading outside. It refuses (`folder is hidden`) when any folder below the root starts with a dot or, on macOS, carries `UF_HIDDEN`, so `~/.ssh` or `~/Library` is never listed. It keeps entries whose names are valid `FolderName`s (1 to 255 bytes, no `/` or `\`, no control, format or invisible character, no leading dot or surrounding whitespace) and that are, by `fstatat` without following, directories or symlinks resolving to a directory under the roots, skipping `UF_HIDDEN` entries on macOS. It scans at most 10,000 entries, sorts case-insensitively and returns at most 500 (`truncated` when any were left out) with the canonical path; nothing inside the folders is read.
  - `task.new` takes an optional `new_folder` (a `FolderName`): `cwd` is the parent, opened and refused when hidden the same way, and a path reaching 1024 bytes is refused. collied creates the folder with `mkdirat(parent_fd, name, 0755)` (umask applies; an existing entry, symlink included, is `folder already exists`), checks that `<parent>/<name>` resolves under the roots to that folder (same device and inode), then starts the agent there; no `git init`, no file. The audit target is `<path> (created)`, or `<cwd> new_folder="<name>"` when it was not created or the check after failed (the error then names the folder left in place). The `op_id` covers the whole request, so a retry replays the first result instead of failing on the folder it made. If the start fails, the folder stays and the error says so.
  - Only the phone keeps the base folder, per machine (`taskBases` in `prefs.json`), in the canonical form `task.folders` returned, so a folder collied refuses is never stored, and drops it with the machine. The New Task sheet lists it once per opening (never per keystroke), completes names locally and sends `<base>/<name>`, which collied checks like any `cwd`; browser and completion picks fill the full child path from the canonical listing, for task folders and worktree sources alike. Browsing does not cancel the form; only dismissing the sheet does. The prompt has the agent prompt's keyboard-collapse control, which clears focus without changing the prompt or attachments.
- **Clone.** `task.new` takes an optional `clone` (a `CloneSource`), exclusive with `new_folder` and `worktree`: `owner/repo` (GitHub), `https://host[:port]/path` or `git@host:path`, every path segment ASCII letters, digits, `.`, `_` or `-`, starting with neither `.` nor `-`. Any other transport, a local path, userinfo, a query, `..` or a leading `-` is refused at parse time, on the phone and in collied. The folder is the last segment without `.git` and must be a `FolderName`; collied creates it inside `cwd` as for `new_folder` (an existing entry fails before anything runs), then clones into it: `owner/repo` with `gh repo clone -- owner/repo <folder>` when `gh` is in `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` or `~/.local/bin`, else, and as the second attempt when gh exits 4 (not logged in) and left the folder empty, `git clone -- https://github.com/owner/repo.git <folder>`; a URL with `git clone -- <url> <folder>`.
  - The child gets null stdin, no `GIT_*` variables from collied's environment, `GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, no `GH_TOKEN` or `GITHUB_TOKEN`, and through `GIT_CONFIG_COUNT` `protocol.allow=never` with only `https` and `ssh` allowed (`file`, `ext`, `git` and `http` explicitly denied), which outranks config files and survives a `url.<base>.insteadOf` rewrite. It runs in its own process group, killed 75 s after the first attempt or when dropped.
  - A failed clone returns the tail of git's stderr (at most 1000 bytes, without control or invisible characters) and removes the folder if it is empty again, else names it. The audit target is `<cwd> clone="<source>"`, or `<folder> (cloned) clone="<source>"` after a successful clone; if the agent then fails to start, the clone stays and the error names it. The phone waits 165 s for the reply.
- **Pull request worktree.** `task.new`'s `worktree` can be `{"mode": "pull_request", "number": N}`, N from 1 to 2^32 - 1 (else refused at parse time). collied lists the repository with herdr as for Create, then runs `gh pr view N --json headRefName,headRefOid,isCrossRepository` in its checkout, with the linked pull request read's `gh` and environment (30 s). A pull request from a fork (`isCrossRepository`) is refused: its branch is someone else's code, and a project's agent settings in it would run on the machine. The untrusted head branch must pass the typed branch name rules (ASCII letters, digits, `/`, `.`, `_` and `-`, no `..`, no leading `-`, no trailing `/`, at most 255 bytes) and `git check-ref-format --branch`, and the head commit must be 40 or 64 lowercase hex digits. The checkout path `.worktree/<branch with / as ->` must not exist.
  - collied then runs `git fetch --no-tags --no-recurse-submodules --no-write-fetch-head origin -- +refs/heads/<branch>:refs/remotes/origin/<branch>` with the clone's environment (no `GIT_*`, no prompts, HTTPS and SSH only, own process group), checks that `origin/<branch>` is the head commit gh named (an `origin` that is not the pull request's repository, or a push in between, fails with `try again`), and creates the branch with `git branch --track -- <branch> origin/<branch>` unless it exists. An existing local branch must be at that commit, else the task is refused (`a local branch <branch> exists at another commit ...; open it with Open or delete it`) and the branch is not moved. herdr's `worktree.create` then checks it out and the task continues as Create. The gh read, the checks and the fetch share one 75 s budget. The audit target is `<cwd> pull_request=<N>`. The phone waits 165 s for the reply.
- **Resume.** `task.sessions {cwd}` (Drive class, no `op_id` since it only reads, audited with the path and `ok sessions=<n>`, never the prompts) lists up to 20 recent sessions of a folder that resolves under the roots, newest first by the transcript's mtime, for the allowed kinds among `claude` and `codex`, leaving out sessions a herdr agent already reports as its `agent_session`.
  - Claude Code sessions are the `<uuid>.jsonl` files directly in `~/.claude/projects/<project dir of cwd>/`. Codex sessions are the rollouts under `$CODEX_HOME/sessions/YYYY/MM/DD/` (newest folders first, at most 10,000 listed), plain `.jsonl` or compressed `.jsonl.zst` (Codex compresses rollouts idle for 7 days; when both forms exist, only the plain one is listed and looked up), whose first line is `session_meta` with that exact `cwd`, the file name's id and a `cli` or `vscode` source (not `codex exec` or a subagent).
  - Of each kind only the 400 newest files are opened, with the summaries' `O_NOFOLLOW | O_NONBLOCK` open, and only their first 256 KiB (64 KiB for a plain rollout's `session_meta` line) are read. A compressed rollout is decoded once, to its first 256 KiB, with the decoder's window limited to 8 MiB (Codex writes 2 MiB); the decoder holds back a window before it yields, so each head decodes at most the window plus 256 KiB, and whether the file is longer than its head is judged on the decoded bytes. Chat and the status readers use only plain rollouts: Codex decompresses a rollout before appending, so a live session is never compressed.
  - Each entry has the kind, the session id (a lowercase UUID, `SessionId`), the first line of the first human prompt (Claude's first main-chain `user` record with `origin.kind` `human`, a slash command giving its marker and its output skipped as for `last_prompt`; Codex's first `UserMessage` or `user_message` event), cleaned and capped at 160 characters like `last_prompt`, and the mtime. When the head holds no complete prompt, the session is listed with an empty one if the transcript is longer than the head (the prompt sits in a line the head cuts, such as one with an inline image, or after it), and left out otherwise. The prompt line goes to the phone only: never logged, audited or pushed.

## Tailscale (libtailscale, pinned commit, never tagged upstream)

- libtailscale `main@d1dc45d` (bindings 0.2.0, with the listener fd-passing fix 258321b) as a git submodule. Upstream pins tailscale.com v1.104.1; patch 0001 only raises its `go` directive to 1.27.3, and patch 0011 only raises tailscale.com to v1.104.2 in `go.mod` and `go.sum`, since no upstream commit uses it yet. Requires Go ≥ 1.27.3; builds use `GOTOOLCHAIN=local`, `-mod=vendor` (vendored with `go mod vendor`, below), `-trimpath`, `-buildvcs=false`, `-ldflags=-w`.
- **`tailscale_getremoteaddr` was unsafe for identity before 0.2.0**: its map was keyed by the Go-side fd number, so with concurrent fd churn it returned the wrong peer 17% of the time in testing. 0.2.0 sends each connection's address in a fixed 64-byte record with its fd and keys the map by the received fd; collie still never calls it. `tailscale_loopback` would open a 127.0.0.1 TCP listener (SOCKS5 + LocalAPI) on the machine and is never used either. What the series (patches 0002 to 0010) changes:
  1. `tailscale_accept_with_addr` returns the peer `ip:port` from the record that carries the fd (upstream's record holds the IP only). A per-listener lock keeps concurrent accepts from reading between the pieces of a record whose `MSG_WAITALL` read was cut short, and the short-read path keeps the control message (upstream drops it and miscounts on `EINTR`). A failed accept closes any fd it received, and an accept that waited for the lock re-checks that the listener is still open. `crates/tailnet/tests/end_to_end.rs` checks that every accepted connection's address and whois match its dialer, from four source addresses, with eight threads accepting at once from a backlog of queued records and with one accept loop.
  2. `tailscale_whois_json(sd, addr)` via the in-memory LocalClient (same mechanism as `tailscale_status_json`).
  3. Disable log upload to log.tailscale.com in Go (`TS_NO_LOGS_NO_SUPPORT`), since a c-archive snapshots the environment at load and a later `setenv` is invisible to Go.
  4. Guard the per-handle `lastErr` with a mutex (also where `getremoteaddr` sets it): upstream writes it unsynchronized, a Go data race on a string when one handle is used from several threads.
  5. Keep the Go copy of each accepted fd open until C has received it: macOS's unix-socket GC can dispose of a socket whose only reference is in flight, and the peer's first bytes are lost (reproduced at about 1 in 150 connections).
  6. `tailscale_dial_timeout` and `tailscale_set_advertise_tags`.
  7. Socketpair proxy: non-blocking Go end so close always delivers EOF (a lost shutdown wakeup left readers hanging), shutdowns through `Control` so they never reach a reused fd number, cleanup exactly once as soon as either direction ends (upstream waits for both), no fd-number-keyed map.
  8. `UserLogf` discarded: tsnet otherwise prints the interactive login URL to stderr every few seconds.
  9. Listener socket close waits for in-flight `sendmsg` (and item 5 sends each fd inside its `os.File` `Control`), so no fd number can be reused under a send.
  10. `tailscale_rebind(sd, default_if)`: records `default_if` (the interface NWPathMonitor reports) with `netmon.UpdateLastKnownDefaultRouteInterface` on Apple platforms, as Tailscale's own apps do, so new sockets bind to it instead of netmon's cached default. It injects a netmon event and waits (1.5 s at most) until netmon has published it, so netmon re-reads the interfaces (through a routing-table sysctl, not its route socket) and a move to another interface publishes a major link change (engine rebind, DERP reconnect, control connection closed) before the call returns and the links redial. Then it runs the LocalAPI `rebind` and `restun` debug actions (magicsock `Rebind`, which re-binds the UDP sockets, pings each DERP connection, reconnects one that does not answer within 3 s and forgets the peers' direct paths, then `ReSTUN`). On iOS netmon has no time-jump check, and iOS can defunct its route socket while the app is suspended (XNU exempts only local and system sockets), after which netmon only logs read errors and never sees another change; without this the node keeps binding to the Wi-Fi interface the phone left.
  11. `logtail.Disable()` next to `TS_NO_LOGS_NO_SUPPORT`: with uploads off, every log line was still written to the `tailscaled.log*.txt` buffer, read back and compressed. `crates/tailnet/tests/end_to_end.rs` asserts both files stay empty.
  12. `tailscale_close` first cancels a context every dial derives from. netstack's close aborts only the TCP endpoints registered when it starts, then waits for those registered later, so a dial racing it held the close, and the node restart, up to its 5 s timeout; collie-core closes a replaced node while its dials are in flight.
- The iOS archive is built with `-tags=ios,ts_omit_portmapper`: no NAT-PMP, PCP or UPnP probes of the Wi-Fi gateway on every netcheck. collied keeps its port mapper, so a direct path to a phone behind a hard NAT can still form from the Mac's side.
- Vendored module patches (`patches/<import path>/<file>.patch`, applied after `go mod vendor`; go.sum still verifies every module):
  - tailscale.com `tsnet/tsnet.go`: when advertised tags are unspecified, preserve the existing requests through the sanitized `LocalBackend.Prefs()` API before startup. Fresh nodes stay untagged; an old tagged node can be observed and rejected without first removing its requests or forcing reauthentication. Explicit nonempty requests keep upstream behavior.
  - tailscale.com `ipn/ipnlocal/peerapi.go`: never open the kernel peerapi listener when netstack is present. Upstream binds it to every interface in netstack mode, which exposed a TCP port to the LAN. `crates/tailnet/tests/end_to_end.rs` and `crates/e2e` assert the process has no kernel TCP listener; `collied doctor` checks the running daemon the same way.
  - gvisor `tcp/connect.go` + `stack/stack.go`: a SYN reusing a 4-tuple in TIME-WAIT is handed to the forwarder instead of dropped (was the 63 s dial stall).
  - tailscale.com `wgengine/netstack/netstack.go`: close link queues before aborting endpoints so `tsnet.Server.Close` cannot hang.
  - tailscale.com `wgengine/magicsock/magicsock.go`: `TS_DEBUG_MAGICSOCK_BIND_LOOPBACK=1` binds the UDP sockets to 127.0.0.1 and ::1 instead of every interface. Only the tailnet tests set it, next to `TS_DISABLE_PORTMAPPER`, so the macOS application firewall never prompts for a newly built test binary; collied and the app leave it unset.
- Every patch is applied with `patch --fuzz=0`, so a hunk whose context lines changed fails the build, naming the patch. A hunk whose unchanged context only moved still applies at the new position, so a bump still needs upstream's changes to those files reviewed.
- Bumping: move the submodule, rebase the patches and review upstream's changes to the files they touch. A patch that no longer applies is redone by hand on the new version, never forced. `crates/tailnet/testcontrol` requires the same tailscale.com as libtailscale's patched `go.mod` (`crates/tailscale-sys/tests/versions.rs` reads the build's copy). To run a newer tailscale.com than upstream pins, run `go get tailscale.com@vX.Y.Z` and `go mod tidy` in a copy of the submodule with the series applied, save the `go.mod`/`go.sum` diff as a patch and do the same in `testcontrol`; drop the patch once upstream pins that version or a newer one.
- What control sees: Hostinfo `App` `libtailscale`, `Package` `tsnet`, `IPNVersion` `1.104.2-ERR-BuildInfo` (the tailscale.com version; `-ERR-BuildInfo` because of `-buildvcs=false`) and `GoVersion`. libtailscale reports no version of its own, so control cannot tell 0.2.0 from an older libtailscale on the same tailscale.com. What Tailscale keys its libtailscale notice on is unknown: collie's nodes were flagged while already reporting 1.104.1. Stamping the version with `-X tailscale.com/version.longStamp=...` and `shortStamp` is an option to revisit once Tailscale says what it reads.
- Gate per connection, before the WebSocket upgrade: whois(peer) must show an untagged node, not shared in, owned by the owner user. The owner is the daemon's verified positive embedded self user before listening; the optional `[tailnet] owner_user_id`, the persisted owner and every paired phone must agree. A first pairing cannot choose or replace that owner. Then:
  - paired `StableID` with a pinned TLS key → full session (`hello` first, then the allowlist). While a pairing window is open, `pair.complete` from a paired phone goes through the same code and y/N confirmation as a new phone and replaces its record (a phone that removed the machine while it was unreachable pairs again without a revoke). A paired phone's `unpair` revokes it as `collied peers revoke` does: collied answers, then removes it, drops its push tokens and closes its sessions. The app sends it when the machine is removed while connected;
  - unpaired (or paired without a TLS key), while a locally opened pairing window is active → pairing-only session: `hello` and `pair.complete` only, one attempt, then close;
  - otherwise answer a fixed `403` without reading the request, close, and log; the phone treats 403 as final and stops retrying.
  - At most 4 live sessions per node: a fifth evicts that node's oldest (a phone reconnecting after iOS killed its sockets is never locked out). Global cap 64. Revocation cancels in-flight replies and re-checks authorization before every frame.
- Phone: takes the Mac's IP from its own netmap (`tailscale_status_json`), from the entry with the Mac's DNS name, the `StableID` and user pinned at pairing, checks untagged, unshared ownership with whois, then `tailscale_dial`s that IP; no DNS lookup ([tailnet.md](tailnet.md#pairing-and-connection-authorization)). It never uses `tailscale_loopback` (iOS reclaims that listener on suspend).
- `tailscale_up` blocks until Running and is not cancellable; collied drives its own state machine from `status_json` (`BackendState`, `AuthURL`) and always calls `tailscale_start` first.
- Accepted fds are AF_UNIX socketpairs: await readability with `AsyncFd`, then `tailscale_accept`, then `set_nonblocking`, then `tokio::net::UnixStream`.
- magicsock binds a UDP socket on real interfaces: that is the WireGuard tunnel itself and the one unavoidable non-tailnet socket. No TCP listener exists outside the tailnet.

## Mutual TLS

Inside the tunnel, after the whois gate and before the WebSocket upgrade: TLS 1.3 only, with RFC 7250 raw public keys (no certificates), ECDSA P-256 with SHA-256 only, no session resumption (a resumed session would skip the key check). Each side pins the other's key by the SHA-256 of its SubjectPublicKeyInfo (`KeyPin`, base64url). The shared verifiers are in `crates/tls`.

- collied makes its P-256 key on first start (`tls-key.json`, PKCS#8, 0600 in the data dir). Its pin is in the pairing QR (`k=`, invite `v=2`), and the phone keeps it as the machine's `key`. A new key means pairing every phone again.
- The phone's key is a Secure Enclave key (`Identity.swift`), non-exportable, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, so lock-screen decisions can connect. collie-core holds only its public key and asks the app to sign each handshake (`IdentitySigner`). The simulator uses a software key.
- A full session needs the phone's pinned key (`peers.json` `tls_key`). A pairing session takes any P-256 key, and confirming the pairing records it. A phone paired before mutual TLS has no key: the gate treats it as unpaired, so it pairs again through a window (`collied pair`, scan), which replaces its record.
- A peer the gate rejects still gets the fixed clear `403` before any TLS, so nothing from it is parsed. The phone recognizes it from the first bytes it read (`Sniff`) and stops retrying. A machine that presents another key is a pin violation; collied refusing the phone's key arrives on the phone's first read (TLS 1.3 checks the client after the client's side is done) as `KeyRefused`. Both stop retrying and ask to pair again.
- After the handshake collied runs the gate again under the peers, pairing and sessions locks (`server.rs` `connection`). A different decision, such as a revoke, a pairing or the window closing during the handshake, refuses the connection. The per-node session cap and the registration happen under those same locks.

## Negotiated protocol compatibility

Revision 26 is the first negotiated baseline. The supported floor is 26 (`PROTOCOL_MIN_VERSION`) and the ceiling 29 (`PROTOCOL_VERSION`). Revisions 3 through 25 used exact matching and have no retained codecs: update both peers once to reach the baseline, without changing their paired keys.

`hello.protocol_version` offers the highest supported revision; the optional `protocol_min_version` offers the floor, and omitting it means a singleton range at the offered maximum. The daemon selects the highest common revision and returns it as `protocol_version`, its own range as `protocol_min_version` and `protocol_max_version`, and the selected `capabilities`. A reversed or zero range, a duplicate capability, an unknown request field or a malformed parameter is rejected. An empty intersection closes the session with `unsupported_protocol`, the daemon's maximum and which side to update. The phone rejects a selected revision outside the common range, a non-highest selection and capabilities it did not implement.

Omitted offer capabilities mean exactly the baseline set, currently `terminal_grants_v1`; an explicit `[]` opts out. Unknown offered names are ignored and never echoed. The baseline phone omits its singleton floor and baseline capability set, so its hello has the same fields as revision 25 and a strict revision-25 daemon reaches its version refusal instead of rejecting a new field. There is no fallback connection and no attempt to send revision-25 operations. Offers with a wider range send their floor explicitly, which revision 26 already accepts; the current phone offers 26 to 29, so a revision-25 daemon rejects its hello as malformed.

`terminal_grants_v1` identifies the existing P-256 terminal grant codec and the optional pairing `terminal_key`. Without it, the phone omits that key and refuses terminal methods locally; the daemon rejects an unsolicited key or terminal method and never serializes terminal challenge or grant results. Every request and every daemon result or event passes through the negotiated codec before serialization. The revision-26 codec covers the complete baseline, including current request parameters and enum variants; unknown events cannot be emitted. Paired sessions, pairing and short-lived approval or bootstrap connections all negotiate through the same `Session::hello`. TLS pinning, whois, pairing windows and authorization still come before the protocol session.

Rules for new revisions: retain the current and previous two negotiated revisions, raising the floor only once three real codecs exist. Every wire change supplies request, parameter, response or event field and enum variant gates for each retained revision before the advertised range widens. A future relay grant or encrypted payload format needs its own implemented capability and codec; the terminal capability promises nothing about those formats. Never claim pre-baseline compatibility by widening a range. Before removing a revision, publish the new floor in the release notes and the update guide, and test both upgrade orders with serialized fixtures for every retained revision and for peers below the floor. The checked-in compatibility fixtures exercise the real revision-26 to 29 codecs against offers and selected results that retain them; synthetic 30/31 ranges test negotiation arithmetic, not claimed codecs.

## Approvals

The agent reconcile (`approvals.rs`) issues one approval per `blocked` `terminal_id`: `{approval_id (16 B), terminal_id, agent_label, workspace_label, snippet, tool, reason, options, choices, accepts_input, has_text_field, supports_note, nonce (32 B), created_at_ms, expires_at_ms}`. `expires_at_ms` is `created_at_ms + approval_ttl` (`ServerConfig`, `approvals::TTL` = 600 s; not a `collied.toml` key). The screen comes from `agent.explain` (matched rule id; never exposed, since its output carries raw pane text) and `pane.read source=detection`.

- **Menu.** Only Claude Code's select menu is answered: agent kind `claude` and a rule in `prompt::CLAUDE_MENU_RULES` (herdr claude manifest 2026.10.11.1). The menu is the last numbered block on screen, numbered from 1 without gaps, with exactly one `❯`, in the dialog after the last rule (a numbered block above it is old output); a horizontal rule directly between two options belongs to it (Claude Code 2.1.289 draws one above a question's "Chat about this") and does not start the dialog region. Anything else still raises an approval, with no options: the phone shows it, nothing can be decided.
  - Renamed sessions: herdr 0.9.5's `live_blocked_form_named_session` is a question in a session named with `/rename` or `--name`, where Claude Code draws the name on a rule (`─── <name> ─`) under the form's footer, with its task panel, if any, below it. That rule takes nothing from the phone by itself. Under it only, `prompt::without_session_name` drops the name rule and what follows before anything else reads the screen, and reads the rest as `live_blocked_form`, so the menu, snippet, alert body, keys and settings picker check see the form as in an unnamed session. Its check is looser than herdr's regex and relies on herdr having matched: the last rule on screen must carry text after its dashes (a plain box border never does, so a menu typed into an idle renamed session's input box is not read), the last line above it must end in "Esc to cancel", and below it must be only blank lines and task panel rows (`N tasks (...)`, `◻`, `◼` or `✔` rows, `… +N pending`). Anything else is read whole under herdr's rule and raises an approval with no options. Known limit: a footer wrapped inside "Esc to cancel" (a very narrow pane) is not cut, so that question is answered in the terminal. With Claude Code 2.1.300 in a renamed session, the permission prompts, the dynamic workflow prompt (`dynamic_workflow_prompt`, whose footer is not a form footer) and the settings pickers (`live_blocked_form`) draw no such rule and match as before (fixtures in `crates/collied/tests/fixtures/claude-2.1.300`).
  - Folder trust: the one unnumbered menu read is Claude Code's folder trust prompt (since 2.1.289: "No, exit" first, then "Yes, I trust this folder"; rule `live_blocked_form`), in the dialog after the last rule, with no numbered line, exactly one `❯` line, its options one line each at the cursor's label column, a blank line and the body above, a blank line and a hint below with nothing indented past the cursor, every option mapping to its own decision and one carrying trust wording. A wrapped or misaligned label, a second or missing cursor, an unknown option, a partial screen or any other unnumbered menu is not read. Its options are then handled as a numbered menu's (decisions, keys, cursor fingerprints).

Every agent can instead be answered by hand through the session's terminal buttons and composer ([Prompts without decisions](#prompts-without-decisions)). A pending approval ends when its snippet no longer matches the screen, so a new prompt under a still-blocked agent is not shown with the old command. Permission and trust fixtures cover these paths.

The agent screen still shows a suppressed picker, and its arrows, Enter and Esc answer it like any blocked prompt ([Prompts without decisions](#prompts-without-decisions)). Tests run screens captured from Claude Code 2.1.294 (`crates/collied/tests/fixtures/claude-2.1.294`) and, in a renamed session, 2.1.300 (`crates/collied/tests/fixtures/claude-2.1.300`).
- **Options.** Each decision (`approve`, `approve_always`, `deny`) maps to exactly one option label (`Yes` / `Yes, proceed` / `Yes, I trust`; `Yes, and don't ask again` and similar; `No` / `No, ...`). A decision matching zero or several options is not offered; neither are other options, such as Claude Code 2.1.289's "Yes, and switch to auto mode". A menu with no approve or approve-always option is not a permission prompt and offers no decision at all, not even `deny`: questions (`AskUserQuestion`), plan prompts and other free-form menus.
- **Choices.** `choices` is the menu as read, whenever one parsed (permission prompts included): `{index (0-based), label, current}`, `current` on the `❯` option. Labels have controls, bidi and format characters stripped and are capped at 120 chars (`limits::MAX_CHOICE_LABEL_CHARS`). An approval with no `options` is answered by choosing one: `approval.decide {decision: "choose", choice: <index>}`. A permission prompt never takes `choose`: picking its options by index would bypass the decision they map to (Deny sent as Esc).
- **Note.** `supports_note` is set when the menu offers `approve` or `deny` and "Tab to amend" shows under its last option (Claude Code 2.1.289's footer "Esc to cancel · Tab to amend"; the body above the options can quote any text, so it does not count).
- **Tool.** `collied hook`, registered as Claude Code's `PermissionRequest` hook, reads the hook input (`hook_event_name`, `session_id`, `tool_name`, `tool_input`) and sends `{session_id, tool_name, shown}` over the control socket, `shown` being what the dialog shows of the call: for Bash the command, then Claude's description; else the file path, URL, query or pattern (other tools send nothing). It never answers (no output, exit 0, a 2 s limit), so Claude Code shows its dialog as usual, collied running or not. Claude Code 2.1.289 runs the hook beside the dialog, not before it, and a session's dialogs can be answered before collied looks, so a report names an approval only when its dialog shows the call: each `shown` part must be a run of whole dialog lines once whitespace is removed (wrapping only splits lines, and a shorter command never matches inside a longer line), and the dialog must offer decisions (the hook does not fire for `AskUserQuestion`). collied keeps the last report per session (64 sessions at most, each for the approval TTL). With a matching report the approval's `tool` is `{name, summary}` (every line kept, cleaned like the context, at most 600 chars with the name) and the alert context is `<Tool>: <summary>`; otherwise the screen's context.
- **Reason.** Claude Code can ask even in auto or bypass mode and says why in the dialog only: its `PermissionRequest` hook input (2.1.308: `session_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `prompt_id`, `permission_mode`, `effort`, `hook_event_name`, `tool_name`, `tool_input`, `permission_suggestions`) has no reason field. Claude Code prints the reason under the command block's closing `╌` rule, at the question's margin, then a blank line (or the deny countdown, which is taken out first), `Do you want to ...?` and option 1 of the menu. 2.1.308 starts each row with `│ ` as it wraps (fixtures in `crates/collied/tests/fixtures/claude-2.1.308`, the hook input included); 2.1.295 in an unattended session prints plain rows (`crates/collied/tests/fixtures/claude/bash-countdown.txt`, transcribed). Rows are all barred or all plain, as the last one is.
  - `prompt::without_reason` reads it there only, for agent kind `claude` with a parsed menu and the dashed rules paired before it: rows joined with spaces, terminal escape sequences (CSI, OSC, two-character) dropped and whitespace collapsed; the approval's optional `reason` is the result cut at 200 chars (`limits::MAX_SNIPPET_CHARS`) with `…`. A reason with any other control, bidi or invisible format character, or one that only repeats whole lines of the dialog (the command, Claude's description), is not set and the screen is read whole. A set reason's rows are taken out of the screen before anything else reads it, like the deny countdown, so the menu, snippet and context never see them.
  - The reason as shown is hashed into the fingerprint and every cursor fingerprint, so no decision is made on a stale reason, and it counts in drift. The alert context is the context, then the reason on its own line, inside the encrypted display body. The phone cuts the alert body at 600 characters, so with a reason the context is first cut with `…` to leave it room. The Live Activity shows only the first lines of the context, so there the command comes first and a long one can push the reason out.
  - No version bump: `reason` is an optional, additive field on a server-to-phone type that every retained codec passes whole; an older app ignores it, and an older collied sends none.
- **Snippet and labels.** Snippet: the end of the dialog (for a menu, its last 12 body lines), at most 200 chars, in whole lines (a line is cut, with a leading `…`, only when it alone does not fit), without Claude Code's tips (the same margin and dashed-rule rule as the context below). Labels: at most 64 chars. Both have controls, bidi and format characters and box borders stripped.
- **Fingerprint.** `state_change_seq` only moves on status changes, so a new question under a still-`blocked` agent would not change it. The approval is bound to SHA-256 over the length-prefixed agent kind, rule id, `terminal_id`, agent session id, dialog region (last horizontal rule through the last option, with the cursor; spinners and status lines outside it are excluded) and reason. collied also keeps one fingerprint per option: the region as it reads with the cursor on that option.
  - Claude Code's deny countdown (`⚠ Claude Code will automatically deny this request in M:SS, to avoid blocking progress on an unattended session`, or `about N minutes` / `about N seconds` in place of `M:SS`; since 2.1.295, in a session it takes for unattended) changes every second, so `prompt::without_deny_countdown` takes it out of the screen text before anything reads it, for the approvals and the drive paths that type into a dialog alike. It does so only for agent kind `claude`, only when the dialog's last option block parses as a menu, and only where Claude Code draws it (below the dialog's last `╌` rule when it has any, with the rules paired, else under its top rule, then a blank line, the question and option 1 of that block), at the dialog's margin, in that exact wording on one line or wrapped over up to three, with nothing else on its lines. A copy in the transcript or the command stays. The fingerprints, snippet and context never see it, so its ticking neither reissues nor supersedes the approval. The time is not read: expiry and alerts are as for any approval, and when Claude Code denies on its own the agent leaves `blocked` and the approval ends.

### `approval.decide`

1. Rate limit per paired `StableID`: 1/s, burst 5 (`rate_limited`).
2. Claim. Any attempt on a pending approval burns it, whatever the result; a burned id answers `approval_already_resolved`, an unknown one `approval_not_found`.
3. Expiry, nonce (constant time), decision offered. `choose` is offered only when `options` is empty, for an index inside the menu; anything else is `invalid_params`. `choice` is set exactly when `decision` is `choose` (checked by the decoder). A `note` (a one-line `PromptText` of at most 200 characters with no bidi or invisible format character, checked by the decoder, so the amend field still parses once it wraps: the parser takes an option wrapped onto at most 4 rows) goes only with `approve` or `deny`, and only on an approval with `supports_note`; otherwise `invalid_params`.
4. Re-read the screen: still `blocked`, same `state_change_seq`, same fingerprint, else `superseded`. Re-check that the peer is still authorized.
5. Keys, from a fixed set (`up`, `down`, `enter`, `esc`), never pane text:
   - Deny is a single `esc` when its label ends in `(esc)`, or on the folder trust prompt, whose "Esc to cancel" exits like "No, exit". It does not depend on the cursor.
   - Otherwise the arrows to the target option, 150 ms pause, re-read: the fingerprint must equal that option's cursor fingerprint (else `superseded`), peer re-checked, then `enter` in its own call. Arrows and Enter are never sent together: lost arrows would confirm another option. Digit shortcuts are not used; their select or submit behaviour varies across Claude Code versions.
   - `choose` always takes this path (arrows, re-read, `enter`), whatever the option's label: it never sends `esc`.
   - With a `note`, Approve and Deny also take it (Deny by arrows, never `esc`), and before `enter`: peer re-checked, `tab`, then polls (every 100 ms, up to 1 s) until the target option reads as its amend field (`Yes, and tell Claude what to do next` or `No, and tell Claude what to do differently`, case-insensitive prefix, changed from before Tab) with the cursor on it and every other option and the body unchanged; peer re-checked, the note typed with herdr's `pane.send_text`; polls until the option reads `Yes, <note>` or `No, <note>` (whitespace ignored, wrapped lines included) with the rest of the dialog unchanged; peer re-checked, then `enter`. Each poll also requires the agent still `blocked` with the same `state_change_seq`. On any mismatch nothing more is sent, not even `esc` (in the amend field it cancels the whole prompt): `superseded`, and the next reconcile issues a new approval for what the screen then shows.
6. Settle: poll `agent.list` every 250 ms for up to 3 s (`approvals::SETTLE`) for the agent to leave `blocked` or move its `state_change_seq`.

The decide budget is 6 s from the claim to the last key; no key is sent after it. With the 3 s settle, a decision answers in under 10 s.

| Outcome | When |
|---|---|
| `applied {decision, by}` | final key sent, agent left `blocked` within the settle |
| `unconfirmed {decision, by}` | final key sent (or its send timed out, it may have arrived), agent still `blocked` |
| `chosen {choice, by}`, `chosen_unconfirmed {choice, by}` | the same two for `choose`; their own outcomes so an older app decodes them as `other` rather than failing on an unknown decision. A multi-question form stays `blocked` on its next question: `chosen_unconfirmed`, then a new approval |
| `superseded` | fingerprint, seq or cursor mismatch; amend field or note not shown; budget spent before the final key; bad nonce; decision not offered; peer no longer authorized; herdr failed; on reconcile, the agent left `blocked` or moved seq without a decision |
| `expired` | past `expires_at_ms`, at decide or on reconcile |

Every attempt is audited with its decision (`choose <index>` for a choice, `<decision> with note` with a note) and result, including replays, rate-limited and expired ones (a run of frames over the per-peer frame limit logs only its first, as `rate_limited`, and never reaches this limiter); sent keys are logged as `terminal=<id> keys=<keys>`. The note itself is never logged.

**Reissue.** A resolved approval is never reused. If the agent is still `blocked`, the next reconcile issues a new approval (new id and nonce), sent at once to live sessions. Its alert is rate limited per terminal: a new blocked episode, a changed screen (seq or fingerprint) or an expired previous alert always alerts; the same prompt reissued within 30 s of the last alert does not, so bad attempts cannot flood the phone. Alerts carry `terminal_id` as APNs collapse id and `thread-id`, so a new alert replaces the dead one on the phone.

**Drift.** `state_change_seq` does not move on a new question under a still-`blocked` agent (the next question of a form, one answered on the Mac) or on a dialog that finishes drawing after the approval was built. So each reconcile re-reads the screen of every pending, undecided approval of a `claude` agent and supersedes it when what it tells the phone changed: snippet, `reason`, `options`, the menu labels, `accepts_input`, `has_text_field` or `supports_note` (the cursor alone does not count, so arrows do not reissue). The same reconcile rebuilds it. Within 30 s of the last alert of that blocked episode the rebuilt approval does not alert, so typing on the Mac cannot turn into an alert stream.

### Prompts without decisions

Manual input works on permissions, trust prompts, questions and plans for every agent. Every displayed terminal button stays enabled, including Codex's Shift+Left. The session composer sends a typed answer whenever the agent is blocked, an approval is pending, or a Codex question editor is open.

- `agent.send_keys` forwards the closed key list, batches included, after checking the live agent identity and peer authorization. There is no approval rule, menu, decision or question-footer check, and blocked startup prompts also accept input. For a Claude Code agent that the fresh read shows not blocked, keys and typed answers still respect a scrolled transcript and a mirrored slash command, even if the phone holds stale approval metadata.
- `agent.type_text {op_id, terminal_id, text}` sends bracketed-paste text and Enter in one ordered `pane.send_input` write. It does not select a free-text option, read an answer back, or bind input to a prompt fingerprint; the terminal buttons focus the intended control first. Text can contain newlines and tabs; unsafe controls, bidi and invisible formatting characters are rejected, and the 32 KiB prompt limit applies.
- The phone queues terminal keys and typed answers together, including answers sent from the in-session approval card. Earlier navigation, including Shift+Left, finishes before an answer is submitted; later keys follow it. Adjacent keys can still be batched. A failed input cancels queued actions with a visible error, and an agent-to-shell transition discards pending agent input.
- Manual input relies on the paired session, not an approval nonce, expiry or LocalAuthentication. It can grant permissions, accept plans or trust a folder, and a changed prompt receives whatever the user sends.
- `accepts_input` and `has_text_field` remain descriptive approval metadata for older clients and the optional answer field; they do not restrict session input.
- `agent.prompt` stays the normal prompt API and still refuses blocked agents; the composer routes blocked answers through `agent.type_text` instead. Attachments stay available for the next normal prompt. Structured `approval.decide` actions, notes, notifications and Live Activities work as above. Older daemons can still refuse manual input, so the app and collied update together.
- Authorization is re-checked before every herdr write; both methods carry an `op_id` through the outcome cache. Audit: keys to a blocked agent are logged with target `<terminal_id> blocked keys=<keys>`; `agent.type_text` with the terminal and result only, never the text.
- collie-core: `type_text(machine_id, terminal_id, text)`; `ApprovalDecision::Choose { choice }` on `decide`, reported back as `Applied`/`Unconfirmed` with that decision; `decide(..., note)`, a one-line note of at most 200 characters with Approve or Deny (checked before sending); `PendingApproval.choices`, `.accepts_input`, `.has_text_field`, `.supports_note`. The lock-screen path sends no note.
- No version bump: the method, `choices`, `accepts_input`, `has_text_field`, `supports_note`, `note`, the `choose` decision and the two outcomes are additive. An older app ignores `choices` and decodes the new outcomes as `other`; an older collied sends no `choices` (it defaults to empty) and no `accepts_input`, `has_text_field` or `supports_note` (all default to false), and answers `choose` and a `note` with `invalid_params` and `agent.type_text` with `unknown_method`.

## APNs

- `[apns]` in `collied.toml`: `key_id`, `team_id` (10 uppercase alphanumerics), `bundle_id`, and the key's location. `key` and `key_path` together is an error, as is a store for the other OS. `collied apns test` sends a test alert to every registered device of a paired phone.

| Key location | macOS | Linux |
|---|---|---|
| `key = "keychain"` | the default when omitted | config error |
| `key = "systemd-creds"` | config error | the default when omitted ([APNs key on Linux](#apns-key-on-linux)) |
| `key_path` (a 0600 file owned by the user, opened without following symlinks) | legacy; `collied doctor` warns | the fallback when systemd-creds is unavailable; `collied doctor` warns while systemd-creds works |

- Keychain item (macOS): generic password in the login keychain, service `dev.rbstp.collied.apns`, account = key ID. Its ACL trusts only the program that stored it, recorded by its designated requirement, so a rebuild signed with the same Developer ID Application identity (team `RM3UT3MMSR`) and identifier `dev.rbstp.collied` reads it without a prompt; any other program prompts or is refused.
- `just collied-install` (macOS) builds collied in release, signs it (`Developer ID Application: ... (RM3UT3MMSR)`, identifier `dev.rbstp.collied`, hardened runtime, timestamp), installs it to `~/.cargo/bin/collied` as a fresh inode and restarts the launchd agent if it is loaded. A plain `cargo install` build is ad hoc signed and cannot read the item unattended.
- `collied apns import <AuthKey_ID.p8>` (macOS), run from the signed binary: needs `[apns]` ids, refuses a file named for another key ID, reads the file with the `key_path` checks, checks it is an ES256 key, stores it (an existing item is kept), reads it back and compares, rewrites `key_path` to `key = "keychain"` in `collied.toml` (atomic, same mode, never through a symlink), then asks y/N before deleting the file (only if it is still the same inode).
- `collied doctor` (macOS) checks the signature (Developer ID requirement and identifier, `codesign` line), reads the item with user interaction disabled (what it reads is what the daemon reads unattended), signs a provider token as a dry run, and warns about any `.p8` left in `<data dir>/apns`.
- Tokens arrive by `push.register` and are stored per `StableID` in `push.json` (0600, atomic), with the device's notification key (below). Each token carries its environment (Debug builds: sandbox, TestFlight: production); one collied keeps a client for each. Every send re-checks the pairing (a registration racing a revoke never gets an alert); `Unregistered` and `BadDeviceToken` drop the token; revoking a peer forgets its tokens. Direct sends use a queue of 64 alerts, dropped when full, and 10 s per send; the relay's policy is [below](#relay-sender).
- Approval alert: push type `alert`, priority 10, `apns-expiration` = approval expiry, `apns-collapse-id` = base64url of the first 16 bytes of SHA-256(`terminal_id`). A device whose Live Activity for that terminal shows approvals gets the approval on the activity instead, and the alert only if the activity push fails or the approval is still pending 2 min later ([Approval on the activity](#approval-on-the-activity)).
- Approval clear: once the agent on a terminal whose approval alerted is no longer blocked (answered in the terminal or from any device, or gone), collied pushes `{"aps":{"content-available":1},"approval_id":…,"node_id":…}` to every registered device: push type `background`, priority 5, `apns-expiration` 0, no collapse id. Expiration 0 means APNs never stores it: APNs keeps one undelivered push per app, so a stored clear would displace a pending alert. It names the approval the phone's alert carries (a quiet reissue keeps it, a later alert for the terminal replaces it), so there is at most one clear per alert. The record is in memory only: an alert whose agent moves on while collied is stopped gets no clear. The app, woken in the background (`remote-notification` mode), removes the delivered alerts with that `node_id` and `approval_id` and does nothing else. iOS may delay or drop it; whenever the app runs it also removes the alerts of approvals no longer pending.
- Done alert: when an agent's turn of 30 s or more ends, on the 1 s reconcile after the approvals pass. A turn starts when collied sees the agent go `working` and ends when it next shows `done` or `idle`; `blocked` inside it keeps the start (its time counts), while `blocked` to `idle` (a denial, Esc) and `unknown` end it without an alert. The first poll of an agent never alerts; a turn already under way when collied first sees it (a collied restart, a new pane) is timed from that sight. The 30 s, equal to the approvals' alert gap, skips quick replies and slash commands and caps a flapping agent at one alert per 30 s per terminal. The record is in memory only.
  - Push type `alert`, priority 10, `apns-expiration` 0 (as for the clear), `apns-collapse-id` = base64url of the first 16 bytes of SHA-256(`terminal_id`), so one notification per terminal: a done alert replaces that terminal's previous one and the next approval alert replaces it. It cannot replace a pending approval: done needs the agent out of `blocked`, which supersedes that approval, and the one send queue keeps the order. `mutable-content: 1` runs ColliePush for the encrypted title and body, including PR watch wake and archive-on-merge alerts.
  - A device that registered with `mute_done` (the app's "Notify when an agent finishes" setting off, stored in `push.json`, omitted when false) gets none. A followed agent's Live Activity still gets only its silent status update, so the done alert is the one alert. The app in the foreground shows no banner or sound for the done alert of the agent on screen.
- Live Activity update tokens are stored next to the device's token and pushed to with their own headers: [Live Activities](#live-activities).

| Public alert field | Value |
|---|---|
| `aps.alert` | `{"title":"Collie","body":"An agent needs attention"}`; done alerts use `An agent finished` |
| `aps.thread-id`, collapse ID | base64url of the first 16 bytes of SHA-256(`terminal_id`) |
| `aps.mutable-content`, `aps.sound` | `1`, `default` |
| `node_id`, `event_id`, optional `approval_id` | opaque machine, fresh event and approval lookup IDs |
| `enc` | versioned authenticated display envelope, canonical unpadded base64url |

The original alert carries no category. ColliePush adds `APPROVAL` locally only after authenticating display content that offers both Approve and Deny. An extension timeout, unavailable key or failed decryption leaves the generic original without approval controls. The app authenticates encrypted responses again before classifying a decision. The private terminal ID is restored locally after decryption for session navigation. Background approval clears carry only `node_id`, `approval_id` and `aps.content-available: 1`.

### Relay sender

`[push.relay]` selects the fixed publisher endpoint `https://collie-push.rbstp.dev/v1/send`; `[apns]` selects direct delivery for self-built apps. Configuration rejects both together. `collied setup` sets up the relay by default, with no APNs credential, and `collied setup --direct-apns` keeps the key-import path. `collied apns test` uses the selected sender and reports acceptance, never display confirmation. [relay.md](relay.md) describes the deployed relay.

No version bump: optional `relay_grant` registrations and `hello.push_mode` require both `relay_grants_v1` and `encrypted_display_v1`. The configured sender determines `none`, `direct` or `relay`; no endpoint comes from the phone. Grants persist only beside their own device or activity in private `push.json`, redacted in diagnostics. HTTP sends carry only the grant, in a sensitive Authorization header, and the strict v1 encrypted or generic envelope, never a caller-provided destination, topic or URL. Redirects are refused, responses are capped at 1 KiB and each attempt at 15 s.

Relay delivery uses a separate bounded worker: the 64-job ingress, at most 64 pending encrypted destinations, 64 recent activity cadence records and 64 routed-approval deduplication records. Routine updates keep only the newest state per activity and go out at most once per 60 s per agent and phone, unchanged refreshes included. Ready urgent updates, clears, alerts and ends bypass that cadence and run before ready routine work, while a future urgent retry cannot block ready routine work. If cadence tracking fills, a conservative global routine pause keeps the same limit before a record is replaced. Direct APNs keeps its own cadence and send order.

Network failures, timeouts, 429, 5xx and unexpected non-JSON responses (including Cloudflare error 1027 HTML) enter bounded exponential backoff with random jitter. Retry-After seconds or dates are clamped to one hour; a daily quota resets within the next 24 hours at most. Routine daily exhaustion pauses only routine work, leaving the reserved urgent budget usable; other outages pause all queued attempts. The server enforces installation-wide quotas across machines; the remaining budget is unknown locally. Non-approval work expires after two minutes; live approval work lasts until its approval expires, capped at one hour. A restart loses all work: there is no durable payload queue and no exactly-once claim, so an ambiguous accepted send can be duplicated.

Before every attempt, retries included, the worker checks the current pairing, exact destination token and grant generation, grant and approval expiry, live approval state and activity replacement or end. A clear or newer activity state replaces obsolete pending work. Only an authenticated `410 invalid_route` removes the exact token or grant that failed; stale invalidations keep replacements. Configuration and authorization errors keep registrations for repair or renewal. An activity failure keeps the encrypted approval-notification fallback. The local control status and doctor show counts, the earliest grant expiry, the last send error and retry or reset times, without grants, destinations or payloads. A push outage does not block the tailnet or control tasks.

### Encrypted display envelope

- The phone generates a 32-byte notification key per paired machine, stored in the shared Keychain (`AfterFirstUnlockThisDeviceOnly`) and in a 0600 App Group mirror excluded from backups and protected until first unlock, which lets CollieWidgets decrypt without Keychain access. Only the authenticated tailnet `push.register` sends this key to collied, which keeps it beside the token in private `push.json` and never logs it. Pairing again rotates it; unpair or revoke removes it.
- No version bump: the additive `display_binding` registration field and the replacement APNs and ActivityKit codec require the explicitly negotiated `encrypted_display_v1` capability. Revision 26's omitted capabilities still mean only `terminal_grants_v1`. A peer without the encrypted codec cannot register push or activity tokens. Persisted registrations without the encrypted-display marker or activity binding send no private display content and stay disabled until refreshed. There is no plaintext compatibility path.
- `enc` is canonical unpadded base64url of `header || nonce(12) || ciphertext || tag(16)`, ChaCha20-Poly1305 with a fresh random nonce. `header` is binary `version(1 byte = 1) || kind(1 byte) || node_id_length(1 byte) || scope_length(1 byte) || node_id(UTF-8) || scope(UTF-8) || event_id(16 random bytes)`. Node and scope use 1 to 64 ASCII letters, digits, underscores or hyphens. Kinds are `1` alert, `2` activity state and `3` private static attributes. AAD is the bytes `collie.push.v1` and a zero byte, the header, and SHA-256 of the 32-byte destination notification key, so the key binds the receiving phone and machine, and the authenticated header binds kind, machine, scope and event. The public `event_id` is the header event in unpadded base64url. The widget reads that event from the envelope because ActivityKit exposes only `content-state`.
- For alerts, scope is the opaque thread ID. Plaintext is `{"v":1,"title":...,"body":...,"terminalId":...,"offersApproval":...}`, with `approvalId` only for approval alerts. ColliePush compares the authenticated machine, thread, event and optional approval with the public lookup fields, then restores title, body and routing locally. The body is the approval context when present; done and agent alerts carry their own complete body. Unsupported versions, noncanonical encoding, oversized inputs and failed authentication produce no private text or controls.
- Each activity starts with a fresh phone-generated UUID `bindingId` before ActivityKit assigns its activity ID. The app sends `display_binding: {node_id,binding_id}` with its token over the tailnet. Initial and later state both use this scope and kind `2`, with plaintext `{"v":1,"state":...}`. Static attributes keep only opaque machine, terminal, node and binding IDs and a kind `3` envelope containing `{"v":1,"machineLabel":...,"title":...}`. Initial and local updates serialize only ciphertext, like remote update and end state. A widget checks the envelope against its own immutable node and binding before using any state. Missing keys, including before first unlock after a reboot, show a neutral `Collie` state without approval controls.
- Limits: envelopes 3,800 encoded characters, APNs payloads 4,096 serialized bytes, static activity attributes 1,536 bytes, every encrypted initial, update or end state 2,400 bytes, and their combined size 4,000 bytes to leave ActivityKit framing room. The remote sender always reserves the full static-attribute allowance; the phone checks both caps and the actual combined size before every local update. An oversized alert is dropped; an activity that cannot be encrypted or fit triggers the approval notification fallback where it applies. Alert bodies are visibly truncated at 1,800 JSON-escaped bytes, and activity approval context at 600 bytes before its inner command seal, keeping whole Unicode scalars.
- Still observable: IDs, generic categories, priority and urgency, timing, size and update or end lifecycle. Public activity relevance is omitted remotely and zero locally, and activity alert text is generic. The raw APNs token stays a delivery destination. No push carries an approval nonce.
- [protocol/push-display-vectors.json](protocol/push-display-vectors.json) supplies exact Rust and CryptoKit vectors for all three kinds and relay-compatible public payloads. [protocol/live-activity-content-state.json](protocol/live-activity-content-state.json) describes the private state before the outer seal. Its inner approval command uses the [notification-vector.json](protocol/notification-vector.json) seal, authenticated by approval ID; that inner seal never appears outside the authenticated display envelope.
- Context (`prompt::context`, at most 600 chars with `…` when cut, controls, bidi and format characters stripped, lines joined with `\n`, which the NSE keeps): from the dialog after the last horizontal rule, up to the last option block. A Claude Code Bash prompt gives `Bash: <every non-empty line between the header and the last "Do you want to" question>`. Claude's description (under the command, or above it since Claude Code 2.1.289) is included, since plain text cannot tell it from a command line, and nothing inside the command block is ever dropped: the approver acts on this text, so a command must not be able to hide its own lines (a line starting `Tip:`, a blank line, a fake question or option). `Tip:` lines are skipped only at the dialog's own margin (indent of at most one column) and never between the first and last dashed rule (`╌`): Claude Code 2.1.289 prints the command there, at that same margin; older versions indent command lines further. Another tool prompt gives `<Tool>: <target>` (`Edit: src/main.rs`); else the question line; else the dialog's first line (with the next one when it ends in `:`, as on the trust prompt).

## Lock-screen approval

- Category `APPROVAL` has two actions, Approve and Deny (no "approve always"), both `authenticationRequired`: iOS makes the user unlock the device first, then launches the app in the background without UI.
- `AppModel.decideFromNotification` holds a background task assertion and calls `decide_from_notification(node_id, approval_id, decision, budget_ms: 20000)`. The budget is capped at 20 s; 0 is refused. It is a one-shot session, independent of the connection supervisor: start the node from cached state (never a login), wait for the pinned Mac in the netmap, dial, `hello`, take the nonce from the cached snapshot or `approval.list`, then `approval.decide`. It never retries past the budget.
- Immediate `Unauthorized` (no waiting) when Tailscale is not set up on the phone, the node reports `NeedsLogin` or `NeedsMachineAuth`, the netmap violates the pin, or `hello` reports the phone unpaired.
- The report carries the outcome and per-step timings (node up, connect, lookup, decide), logged on device. A follow-up local notification in the same thread never claims success unless the outcome is `applied`:

| Background outcome | Follow-up | Opens the approval |
|---|---|---|
| `applied` | "Approved/Denied: agent. The agent moved on." | no |
| `unconfirmed` | "..., not confirmed": keys sent, agent still looks blocked | yes |
| `expired` | expired, nothing was sent | no |
| `superseded` | the prompt changed, nothing was sent | yes |
| `already_resolved`, `not_found` | no longer pending, nothing was sent | no |
| `unreachable` at `decide` | could not confirm the decision reached collied | yes |
| `unreachable` earlier, `unknown_machine`, `unauthorized`, `failed` | "Couldn't reach collied, open to decide" | yes |

- Tapping the alert opens the matching agent session on the Agents tab; the iPhone has no separate Approvals tab (the Apple Watch keeps its approval list). A pending approval is resolved by node and approval id before navigation, and a validated notification thread opens the agent after the approval has ended. Loading and missing-machine errors stay visible. Structured in-app approval actions pass LocalAuthentication (`deviceOwnerAuthentication`, a fresh `LAContext` each time); manual terminal input is separate.

## Attachments

The Agent screen attaches a photo or a file to a prompt: the phone uploads it over the tailnet session, collied stores a private copy on the machine and returns its absolute path, and the app inserts that path into the prompt draft. Claude Code then reads the file from disk like any path in a prompt. Nothing is sent to herdr.

### Flow

1. `attachment.begin {op_id, name, size, sha256}` answers `{upload_id}` (16 random bytes, hex). `name` (`AttachmentName`: 1 to 64 characters, no control, bidi or format characters, no `/` or `\`, no surrounding whitespace, not `.` or `..`) is only a hint; `size` is 1 byte to 20 MiB; `sha256` is lowercase hex of the whole file.
2. `attachment.chunk {upload_id, offset, data}` in order: `offset` must equal the bytes received so far, `data` is base64 (standard, padded) of 1 byte to 32 KiB, so a chunk frame stays under the 64 KiB frame cap. collie-core sends one chunk at a time and awaits each reply.
3. `attachment.commit {op_id, upload_id}` answers `{path}` once the received size equals `size` and the SHA-256 matches; otherwise the partial file is deleted and the error is `invalid_params` (size) or `checksum_mismatch`.
4. `attachment.abort {upload_id}` is best effort and always answers `ok`.

An upload is bound to the session (and peer `StableID`) that began it: another session, even of the same phone, gets `not_found`. Nothing resumes across connections: closing the session drops its uploads, and collie-core reports the upload as interrupted. `begin` and `commit` go through the `op_id` outcome cache like the other mutations, so a commit retried after a dropped reply returns the stored path. Authorization is the `agent.prompt` gate: a paired, full session, re-checked on every frame and again before `begin`, each chunk and the commit.

collie-core: `upload_attachment(machine_id, name, data, progress)` checks the name and size locally, computes the SHA-256, then runs begin, chunks and commit, calling `progress.on_progress(sent, total)` after each acknowledged chunk; any failure sends `attachment.abort`. `max_attachment_bytes()` returns the 20 MiB limit. UniFFI 0.32 does not forward Swift task cancellation to Rust, so the app cancels with `cancel_uploads(machine_id)`, which fails the upload with `Cancelled` and aborts it on the Mac.

No version bump: the methods, responses and error codes (`too_large`, `checksum_mismatch`) are additive. An older collied answers `unknown_method`, which collie-core reports as "update collied".

### Limits

| Limit | Value |
|---|---|
| File size | 20 MiB (`limits::MAX_ATTACHMENT_BYTES`), checked by the phone, the protocol decoder and collied |
| Chunk | 32 KiB decoded, in order, never past the declared size |
| Uploads in flight | 2 per session (`rate_limited` beyond) |
| Idle upload | dropped, with its directory, after 60 s without a chunk |
| Stored bytes | 200 MiB: committed files (the larger of length and allocated blocks) plus the declared size of every upload in flight; `begin` answers `too_large` beyond |
| Stored entries | 1000 entries under the root, uploads in flight included, so many tiny files cannot exhaust the disk or slow the scan `begin` runs; `begin` answers `too_large` beyond |
| Chunk rate | own bucket per paired `StableID`, 128/s, burst 128 (4 MiB/s); collie-core backs off and retries a rate limited chunk up to 8 times. Other attachment frames use the shared 20/s bucket |

### Storage

- Root: `ServerConfig::attachments_dir`, by default `~/Library/Caches/dev.rbstp.collied/attachments` on macOS and `$XDG_CACHE_HOME/collied/attachments` (else `~/.cache/collied/attachments`) on Linux (no spaces, so the path reads cleanly in a prompt). Created 0700; an existing root that is a symlink, owned by someone else or not exactly 0700 stops collied at start.
- Each upload gets a fresh `<root>/<16 hex>/` (0700, `create_dir`, fails if it exists). Data goes to `.part` opened `create_new` with `O_NOFOLLOW`, mode 0600; the commit fsyncs it and renames it, inside that directory, to the sanitized name. Files are never executable.
- Sanitized name: `[A-Za-z0-9._-]` kept, each run of anything else becomes `-`, leading dots and dashes dropped, at most 64 characters keeping an extension of up to 16 alphanumerics, `attachment` when nothing is left (`.env` becomes `attachment.env`).
- One audit line per committed upload: `attachment.commit`, target = sanitized name, result `ok size=<bytes> sha256=<first 12 hex>`. `attachment.begin` is audited with the sanitized name; chunks and aborts are not. Content and base64 are never logged.
- `collied doctor` prints an `attachments` line: root, mode, bytes stored.

### Cleanup

- Session close: its uploads in flight are dropped and their directories removed.
- Every 10 s: uploads idle for 60 s are dropped.
- At start and every hour: entries of the root older than 24 h are removed (symlinks are removed as links, never followed). At start, directories still holding a `.part` from a previous run are removed too.

## Files from Chat

Chat turns file paths in agent messages and tool records into links, and a tap opens a read-only preview. The phone recognizes absolute paths with at least two components (so `/compact` is not one), relative paths that start with `./` or have a folder and a last component with an extension (`src/main.rs`, not `and/or`), bare names with a common extension (`README.md`, `out.png`; not `Node.js` or `e.g.`), and Markdown links with no scheme or `file:`. A trailing `:line` or `:line:column` is dropped; tokens with `..`, `://`, `*`, `$`, `=`, `@` or `\` and hidden names are not linked. In Terminal, an agent session's selection menu shows Open when no http link is selected and the words the selection touches, read whole across soft-wrapped rows like a link, hold exactly one such path; it opens the same viewer. Open is not offered while the terminal cannot tell how rows wrapped. collied decides what may be read.

### Flow

1. `file.open {terminal_id, path}` (Read class; `path` 1 to 1024 bytes, no control characters) answers `file_opened {download_id, name, size, kind, sha256}`.
   - collied takes the agent's checkout as `agent.changes` does (`foreground_cwd`, else `cwd`, through `resolve_cwd`), joins a relative path to it, refuses `..`, requires the result under a task root, then opens the parent one component at a time from the root with `O_NOFOLLOW` (`open_beneath`) and the file with `O_NOFOLLOW | O_NONBLOCK`.
   - `open_beneath` refuses a folder starting with a dot or carrying `UF_HIDDEN`, except the folders of the agent's checkout path itself when the file lies below the checkout, so a worktree in `<repo>/.worktree/<branch>` opens its files. Any hidden folder below the checkout, and every hidden folder on a path outside it, is still refused. A checkout that is, or lies inside, a hidden folder (an agent started in `~/.ssh` or under `~/Library`) exposes the regular files below it, except hidden files and anything in a hidden folder below it, as the threat model notes.
   - It refuses a hidden name, a symlink, a folder and anything but a regular file, each with a plain message (`invalid_params`). `kind` is `image` (PNG, JPEG, GIF, HEIC, WebP by extension), `pdf`, `text` (other files whose first 8 KiB are UTF-8 without a NUL) or `other`; an unknown kind decodes as `other`. A file over 1 MiB for text or 20 MiB otherwise (`limits::MAX_TEXT_FILE_BYTES`, `MAX_FILE_BYTES`) is refused with `too_large` and its size, from `fstat`, before any content is sent: the 20 MiB cap before anything is read, the text cap after the 8 KiB that tell text apart. `sha256` is computed from the open descriptor.
2. `file.chunk {download_id, offset}` answers `file_chunk {data}`: up to 32 KiB of base64 from `offset`, read with `pread` from the same descriptor, so a chunk frame stays under the 64 KiB frame cap. A file that shrank fails with "The file changed while it was read"; one rewritten in place fails the phone's checksum. Chunks draw from the attachment chunk bucket (128/s).
3. `file.close {download_id}` always answers `ok`.

A download is bound to the session and peer `StableID` that opened it, at most 2 per session (`rate_limited` beyond), and closed by `file.close`, at session end or after 60 s without a chunk; another session gets `not_found`. Nothing is copied, cached or written on the machine. `file.open` is audited with `<terminal_id> path="<path>"` and its outcome; chunks and closes are not, and content never reaches a log or a push.

collie-core: `open_file(machine_id, terminal_id, path)` runs open, then chunks with 4 in flight (a rate limited chunk is retried up to 8 times), checks each chunk's length and the SHA-256 of the whole file, and always sends `file.close`, waiting at most 1 s for its answer since collied also drops the file with the session. A `not_found` chunk reads as an interrupted transfer, which the viewer offers to retry. `cancel_downloads(machine_id)` stops a transfer when the viewer closes; it cuts the chunks short but lets a pending `file.open` answer, so the file it opened is closed too. The viewer keeps the bytes in memory, writes a copy to a fresh folder in the app's temporary directory (complete Data Protection) for Share, and removes it when it closes. Copy puts the text, the image, or the file data under its type on the pasteboard. Text uses the Git diff wrap setting.

## Draft sync

Claude Code keeps unsent text in its input box, and herdr's `agent.prompt` pastes after it. For agent kind `claude` only (other kinds ignore all of this):

- `agent.draft {terminal_id}` answers `{text}`: the box's text, `""` when it shows only its dim placeholder, `null` when there is nothing the phone may pre-fill (another agent kind, no box, or an opaque box). It reads `pane.read source=visible format=ansi` through `sanitize_ansi`.
  - The box is the last block on screen between two horizontal rules drawn from column 0 (the top one may carry a label), whose first row starts at column 0 and whose other rows are indented two spaces, so a typed row of `─` never closes it. A first row other than `❯` (bash mode's `!`), or a collapsed paste or image placeholder (`[Pasted text #1 +40 lines]`, `[Image #1]`, `[...Truncated text #1 ...]`, dim or not), makes the box opaque: its screen text is not its content. Dim text in a `❯` box (placeholder, completion hints) is not typed text.
  - Claude Code 2.1 soft-wraps the draft with wrap-ansi `{hard: true, trim: false}` at the terminal width minus 4 and hides the space at each wrap: a row the next word would not have fit on joins the next with a space, a full row that split a long word joins without one, and a row starting with a space follows a typed newline. After a full row the space before the next word takes the next row's first column, unseen, so that row holds one column less and shows blank before a word as wide as a row. Where the rows allow more than one text, a full row of one word continues as a split word as far as the rows allow (a word longer than a row starts where it is unless that takes more rows), the word after a shorter row reads as long as that before choosing between a soft wrap and a typed newline, and after any other full row a soft wrap reads before a split word.
  - Controls, bidi and format characters are dropped, trailing whitespace trimmed per row and at the end, and the text capped at 32 KiB.
- `agent.prompt` takes an optional `expected_draft`, what the phone last saw. Once the agent passes the ready check, collied reads the box before the paste and fails closed:
  - an empty box: the prompt goes ahead;
  - no box, or an opaque one: `draft_not_cleared`, nothing sent (whatever replaced the box may still take the paste, and an opaque box may be a shell command or hold content the phone never saw);
  - a selection below the box: `input_unfocused`, nothing sent, and `agent.draft` answers `null`; the phone tells the user to press ↑ (the key strip's ↑ reaches the agent) and send again. Verified on Claude Code 2.1.310 in herdr 0.9.5: `down` on the box's last row selects the background task pill (`1 shell`, in SGR reverse video) and then the agent list below it (selected row starting with `❯` at column 0). The box draws as before, but a paste may be dropped and herdr's Enter opens the tasks dialog or switches agent, so without this check `agent.prompt` answered ok for prompts that never arrived (#588). `up` gives the box the selection back. Prompts queued while Claude Code works are drawn above the spinner, outside the box, which shows `Press up to edit queued messages` as its placeholder, so they read as an empty box, are never cleared, and a prompt sent then queues after them;
  - a draft equal to `expected_draft` (both normalized): clear it, then re-read every 100 ms for up to 1 s until the box is empty, else `draft_not_cleared`, nothing sent;
  - any other draft, or no `expected_draft`: `draft_changed`, nothing sent. `ErrorBody.draft` carries the current text so the phone can show it and send again to replace it. The audit line is `draft_changed` alone: draft text is never logged.
- Clearing, verified on Claude Code 2.1.310 in herdr 0.9.5 for a draft of N visual rows with the cursor anywhere: N times `ctrl+e`, `ctrl+u`, `backspace` (clear a row and join it to the one above; a no-op on an empty first row), which empties the cursor's row and those above it, then N-1 times `ctrl+k`, `ctrl+k` (join the next row, then clear it). Never `down`, which selects the background task pill on the last row while a task runs; never `ctrl+c` (interrupts a working agent) or `ctrl+d` (exits Claude Code on an empty input); none of the keys used interrupts a working agent. Batches of at most 16 keys, authorization re-checked before each. collied sends these keys itself, whatever the phone's `Key` allowlist holds. herdr has no `delete` key name.
- The phone loads the box's text into an empty prompt field once per visit to the agent's screen and remembers that it came from the machine until the phone edits it (keyboard, dictation, paste). Meanwhile, a non-null `last_prompt` that differs from the last one seen makes it read `agent.draft` once: an empty box means the prompt was sent on the machine, so the field empties and its attachments stay. `last_prompt` comes from human prompts only, so text deleted on the machine, an approval, a background task's turn or `last_prompt` going null leave the field alone. Unedited loaded text shows up to five lines (two in landscape) without focus.
- No version bump: the method, response, field and error codes are additive. An older collied answers `agent.draft` with `unknown_method`, which collie-core returns as no draft, so the phone never sends it `expected_draft`. An older app sends no `expected_draft`, so a Mac draft refuses its prompt rather than being appended to. An older app reads `input_unfocused` as `unrecognized` and shows collied's message; an older collied never sends it.
- **Slash command mirror.** While the phone's draft starts with `/`, only its command token (up to the first whitespace) is mirrored into the box, so Claude Code's command menu shows on the machine and in the phone's terminal view.
  - `agent.slash_draft {terminal_id, command, expected_draft}` (Drive class, idempotent so no `op_id`, audited with the terminal only) takes a `SlashCommand`: `""`, or `/` and up to 63 of `A-Z a-z 0-9 _ : . -` (nothing that could end the paste early). collied runs, in order: the ready check (never `blocked`, launch pending, or another agent or session) for a `claude` agent with no "Jump to bottom" banner; `replace_draft` with `expected_draft` as for `agent.prompt`; for an empty `command`, nothing more; otherwise the ready check and banner again, a visible read that must show an empty `❯` box (else `agent_not_ready`), authorization, then one `pane.send_text` of `ESC[200~`, the command, `ESC[201~` (herdr 0.9.3 has no paste without Enter), then a visible read every 100 ms for up to 1 s until the box holds exactly the command. Only then does collied reply and release the lock: a paste takes up to about 110 ms to render, and a next call reading the box empty would paste after it (`/stat/statu`). Other text by then gives `draft_changed` with it, an empty or unreadable box `agent_not_ready`; nothing more is written. Never Enter, never a key. A paste that did not land heals on the next call.
  - The phone mirrors only keyboard typing in the prompt field (the iOS keyboard's dictation and paste count; the app's own dictation, paste, restored drafts and text it sets never reach the machine), only for a Claude Code agent that is not blocked or scrolled up, while not dictating or sending, and only while it knows the box's text and that text is empty or a command. Calls start 150 ms after the last keystroke, one at a time toward the latest draft. Typing after the first space changes nothing on the machine; when the draft stops starting with `/` or empties, the box is cleared once. A `draft_changed` showing the command this screen last asked for (a lost reply) is replaced; any other text pauses the mirror and is shown until the next send, so machine text is never replaced unseen. A reopened screen trusts the box's text only when it is a bare command equal to its draft's token. The phone compares tokens, not text, and names the box's text as collied last read it, so a hint Claude Code draws after a completed command (`/rename  [name]`, indistinguishable by color) never triggers a write and is cleared by the send.
- Key strip: hidden until the composer's Keys button (right of the attachment menu) shows it, for every session (`keysShown` in `prefs.json`). Shift and Control are selected on the phone and never sent alone: the next key goes out as one `Key` (`shift+tab`, `shift+left`, `ctrl+enter`, or Control with a typed letter) and the selection clears, so collied still sees only its closed list. Key shortcuts (`strip-shortcuts.json`, this phone only) send one `Key`, or text through `agent.prompt` with `expected_draft: ""` (refused as `draft_changed` while a Claude Code box holds unsent text; Codex and Copilot CLI take it after any text there), or, for a Terminal shortcut only, through `terminal.run`. A shortcut whose key name the app no longer knows is hidden.
- Picking a command: ↑ ↓ on the key strip move Claude Code's highlight and ⇥ takes it. The mirror catches up before keys; after keys sent while the box held a command, the phone reads `agent.draft` 150 ms later and takes the box's command into its draft, keeping its own arguments (`/mod opus` and ⇥ gives `/model opus`; a bare command gets a trailing space). A missed read is caught on send: a `draft_changed` whose command extends the draft's updates the draft the same way and is shown before sending again; any other command is shown and left alone. ↑ or ↓ leaves the box's text unchanged, so Send is refused after them until ⇥ or an edit. ⏎ and ⌃⏎ are off while the box holds a command no prompt covers, and keys queued before the mirror landed lose their Enter. collied enforces it too: `agent.send_keys` with `enter` or `ctrl+enter` to a Claude Code agent that is not blocked is refused (`agent_not_ready`) when the box starts with `/`. `agent.prompt`, `agent.send_keys` and `agent.slash_draft` share one lock, so another session's input never lands between a mirror's read and its paste. Only the phone's send runs a mirrored command: it waits for a mirror call in flight, then `agent.prompt` clears the token (it equals `expected_draft`) and pastes the whole draft with Enter. A partial command runs Claude Code's top match, as a typed one does.
- Codex and Copilot: collied refuses `agent.slash_draft` and the phone never calls it. collied cannot read their input box, so it could neither check nor clear it, and their prompts paste after whatever it holds, so a mirrored token would lead the prompt sent.
- Residual: text typed on the Mac between collied's read and its clearing keys is cleared too; text typed after the empty re-read is appended to by the paste. A typed newline exactly where the next word would not have fit reads as a space. When Claude Code limits the box to a viewport (a draft taller than its visible rows), only the visible rows are read and cleared, so the re-read refuses the prompt.

## Context and inbox

herdr reports each agent's session id (`agent_session.value` in `agent.list` and `session.snapshot`, set by its SessionStart hooks, so it follows `/clear`, resume and compaction). collied maps it to the agent's own transcript and derives four optional `Agent` fields: `context_left` (0 to 100), `last_line` (the first non-empty line of the latest reply), `last_prompt` and `last_activity_ms` (the transcript's mtime). No version bump: the fields are additive, and `Agent` is server-to-phone, so an older app ignores them and an older collied leaves them out.

- **Live Claude Code session**: herdr's id can be stale (a session restarted while herdr's server was down) or name a client that only shows another conversation (`/resume` of a background session), and a pane running `claude attach <id|name>` has none, since the attach client fires no hook and has no `sessions/<pid>.json`.
  - So for a Claude Code agent collied asks herdr for the pane's foreground pids (`pane.process_info`, every 10 s per pane and when the pane id changes). It keeps only the pids, plus the last argument of a foreground `claude attach <target>` (an `argv` of exactly three, the first named `claude`), never the rest of `argv` or `cmdline`; a failed call keeps what was last listed. It reads `sessions/<pid>.json` for each, with the transcript's open, capped at 64 KiB. A file counts only when its `pid` matches its name, the pid answers `kill(pid, 0)`, the process started no later than the file's `startedAt` (2 s of slack, for Linux's whole-second start time), and its `cwd` is the pane's. When every such file agrees on one `sessionId`, it replaces herdr's (logged once per terminal, ids only).
  - Otherwise, for a pane running `claude attach <target>`, the session is the one live process whose `sessions/<pid>.json` has `kind` `bg` and, like Claude Code's own resolver, a `jobId` the target (1 to 8 lowercase hex) starts or equals, or else a `name` equal to the target (Claude Code also takes part of a name, case-insensitively; collied does not). The same pid checks apply, without the `cwd` one, since the client can be started anywhere. No match or more than one, and herdr's id stands. The attach client's agent view can open another session without its `argv` changing, so a named record is followed only while the pane's terminal title (herdr's `terminal_title_stripped`), which Claude Code sets to the shown session's name, equals that name; a record without a name has no such check and can be shown over another session the client opened. On Linux the target is lost if Claude Code overwrites its `argv` with a process title; the pane then keeps herdr's id.
  - From that session, collied follows where its transcript says the conversation went, reading its last 64 KiB: the latest `continued-in` record (`continuedInSessionId`) whose target's transcript is in the same project directory, or a `/resume` (`system` `local_command` with `commandRun.command` `resume`) whose output ends `running in the background (<8 hex>)`, taken only when exactly one live process has a `sessions/<pid>.json` with `kind` `bg`, that `jobId`, a `sessionId` starting with it, the same project directory and that transcript, with the same pid checks. A later reply or human prompt in that session drops the hand-off. At most 4 hops; a loop or a longer chain keeps the starting session.
  - Chat history, `context_left`, `last_line`, `last_prompt` and `subagents` all read the session found. For the summaries it is cached per terminal: worked out again when herdr's id or the pane's pids are refreshed, and the hand-offs followed again when the starting transcript's size or mtime moves.
- **Claude Code**: `projects/<cwd with every non-alphanumeric character as '-'>/<id>.jsonl` under `CLAUDE_CONFIG_DIR` or `~/.claude`, else `projects/*/<id>.jsonl` for a session started in another directory.
  - Usage: the latest main-thread (`isSidechain: false`), non-`<synthetic>` assistant entry's `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`, as Claude Code's auto-compact indicator counts it (its status line leaves out `output_tokens`); after a `compact_boundary` entry with no reply since, its `compactMetadata.postTokens` instead.
  - Window: not in the transcript. collied takes the session's `context_window.context_window_size` from the status line tap ([Plan usage](#plan-usage)) when it has one, else infers it from the model: 1M for Opus 4.7 and later, Sonnet 5 and later and Fable, 200K otherwise, and 1M once the usage passes 200K. So an Opus 4.6 or Sonnet 4 session with the 1M window shows too little left until it passes 200K (0% from 167K, then 78% at 210K), and one held to 200K on a 1M model shows too much.
  - Percentage: counts down to Claude Code's auto-compact point, as its "% until auto-compact" indicator does: `round((W - 33000 - used) / (W - 33000))`, 0 past it. Claude Code 2.1.314 compacts at the window less `min(max output tokens, 20000)` less 13,000, which is 33,000 for current models. With auto-compact off, collied counts down to the full window. It takes auto-compact as off only when `settings.json` in the same config dir has `autoCompactEnabled: false`, where `/config` writes it; it re-reads that file (a regular file, at most 64 KiB, symlinks followed) only when its size or mtime changes, and the transcript cache is keyed by the result. The agent's environment (`DISABLE_AUTO_COMPACT`, `DISABLE_COMPACT`), project and managed settings, the legacy `autoCompactEnabled` in `~/.claude.json` and a smaller auto-compact window (`autoCompactWindow`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`) are not read, so such a session's ring can differ from Claude Code's.
  - Prompt: the latest of the last `user` entry with `origin.kind: "human"`, the last prompt sent while Claude is working (the `queued_command` attachment Chat shows) and the last `last-prompt` entry, except that a `last-prompt` entry after a mid-turn prompt is passed over: Claude Code keeps writing the turn's first prompt there. A `!` shell command (a `user` entry starting `<bash-input>`, with no `origin`) after the mid-turn prompt still makes the `last-prompt` entry after it, such as "!git status", the prompt. So the Inbox "You:" line, the phone's draft clearing and its arrival check before a resend also follow a mid-turn prompt. A skill or custom slash command entry (its origin is also `human`) gives its marker, such as "/review pr 12", as Claude Code's own `lastPrompt` does, and a `<local-command-stdout>` entry is skipped.
- **Codex**: `sessions/YYYY/MM/DD/rollout-<local time>-<id>.jsonl` under `CODEX_HOME` or `~/.codex`. The id is a UUIDv7, so the UTC day it was created and the day on each side are searched. ## Linked pull requests

Each `Agent` can carry an optional `pull_request`: `number`, `state` (`open`, `draft`, `merged`, `closed`), `checks` (`passing`, `failing`, `pending`, `none`), `url`, `failing_checks` (the names of failing checks), `remarks` (reviews plus comments) and `conflicting`. No version bump: the fields are additive on a server-to-phone type, and both enums read an unknown value as `unknown`.

- **Daemon**: a task beside the reconcile loop wakes every 30 s. It does nothing unless a phone is connected (`events.receiver_count() > 0`) or a paired phone has "Archive when the PR merges" on (then, with no phone connected, it reads only the agents it could archive; see below), and `gh` is in `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` or `~/.local/bin`; without `gh` every agent loses its pull request.
  - For each agent it takes the checkout as `agent.changes` does (`foreground_cwd`, else `cwd`, through `resolve_cwd`, so only inside the task roots), then the repository root and branch with git; an agent outside a repository or on a detached head has none. It reads the pull request with `gh pr view --json number,state,isDraft,url,statusCheckRollup,mergeable,reviews,comments,headRefOid --jq '.reviews |= length | .comments |= length'` in the checkout, with no argument (gh finds the current branch's pull request itself, so no branch name reaches the command line), so reviews and comments reach collied as counts only, never their text.
  - Cadence: at most once per 2 minutes per checkout and branch. A pull request the last good read found `MERGED` is kept instead of read again while the checkout's `HEAD` (`git rev-parse --verify --quiet HEAD`) is still its `headRefOid`; a kept result is read again at least every 30 minutes, so a new pull request opened from the same commit is still found. Open, draft and closed pull requests, and an entry whose last read failed, are read every 2 minutes. "no pull requests found" caches none; any other failure (no login, network, timeout) keeps the last value for one refresh, then shows none, and logs nothing. A read whose branch changed while `gh` ran is dropped. Any change to what the phone is shown sends `flock.changed`.
  - `gh`, here and for `gh poi`, runs with a fixed path, `GH_PROMPT_DISABLED=1`, no `GH_TOKEN`, `GITHUB_TOKEN` or enterprise token variables, null stdin, a timeout (30 s here) and `kill_on_drop`. A state other than the four, or a `url` that is not `https://` or holds whitespace or control characters, drops the read. `failing_checks` holds at most 10 distinct names of failing check runs (`name`) or status contexts (`context`), in rollup order, each without control or format characters or `"` and cut at 100 characters, as for a watch. `conflicting` is `mergeable` being `CONFLICTING`.
- **Checks**: from `statusCheckRollup`. A status context's `SUCCESS` passes, `PENDING` and `EXPECTED` are pending, anything else fails; a check run not `COMPLETED` is pending, a `SUCCESS`, `NEUTRAL` or `SKIPPED` conclusion passes, any other fails. Any failure makes `failing`, else any pending `pending`, else `passing`; an empty rollup is `none`.
- **Phone**: a badge with the state's icon and color and the number, plus a check icon while the pull request is open or a draft, on grid cards, Inbox rows and the agent screen's header. Tapping it opens the `url`, only when it is `https`, except on the agent screen, where it opens a menu: Open PR, then the prompts that apply. While the pull request is open or a draft: Fix failing checks when `checks` is `failing`, Address review comments when `remarks` is above 0, Resolve conflicts when `conflicting`; Explain this PR always. Each fills the composer with one line holding the `url` (and, for failing checks, the quoted `failing_checks` names), appended after a blank line to any draft, and sends nothing.
- `collied doctor` warns when `gh` is missing or `gh auth status` fails.

### Watching a pull request

For a Claude Code agent whose linked pull request is open or a draft, the session menu offers "Watch PR" with an interval of 2, 5, 15 or 30 minutes. While the terminal has a watch, whichever pull request it follows, the menu offers "Stop watching #N, every M min" instead. `Agent.pr_watch` (`number`, `url`, `every_minutes`) carries it, and the badge shows "Watching" (only the eye on grid cards) when it follows the linked pull request. `agent.watch_pull_request {terminal_id, watching, every_minutes}` starts or ends the watch. Starting needs `every_minutes` of exactly 2, 5, 15 or 30, a Claude Code agent, its linked pull request open or a draft with a URL of the form `https://host/owner/name/pull/number` in GitHub's characters, the agent's checkout on a branch, `gh` installed and `gh auth status` passing (otherwise the error asks to run `gh auth login` on the machine). Stopping takes no `every_minutes`. Watching the same pull request again only changes the interval. Watches belong to the machine, one per terminal, kept in `pr-watches.json` (0600) in the data directory with the interval, the checkout and branch, and the `StableID` of the phone that started them, so a watch survives a restart.

- **Reads**: a daemon task beside the reconcile loop ticks every 30 s and reads each watched pull request when its interval has passed since the last read (at once for a new watch, a watch started again, and after a restart), with or without a phone. It runs `gh api graphql --hostname <host>` in the data directory, with the owner and name as `-f` variables and the number as `-F`, in the linked pull request read's environment. The query asks for the signed-in user, the state, `mergeable`, the head commit, the base branch's required check names (`baseRef.branchProtectionRule.requiredStatusChecks.context` and `baseRef.rules.nodes.parameters.requiredStatusChecks.context` from `RequiredStatusChecksParameters`), the head commit's rollup state with its check runs and status contexts (name, outcome, `isRequired`), and the author, URL and time of the last 20 comments and 20 reviews. It asks for no body, so no comment or review text reaches collied.
- **Wakes**:
  - A check that fails: each check once until it passes again or the head moves.
  - All required checks passing: once per head commit. The required names are the base branch's, from its protection rule and rulesets, plus any listed check marked `isRequired`. Each must be listed and pass, so a required check that has not reported yet holds it, and so does a rollup state of `EXPECTED`. An optional check failing or running does not hold it. With no required check, every listed check must pass and the rollup must not be `PENDING` or `EXPECTED`. A required check from a rule the signed-in user cannot read is known only once it reports.
  - A comment or review newer than the newest one seen, by someone other than the signed-in `gh` user. The time is compared and URLs break ties within a second, so a deleted comment that lets an older one into the window wakes nothing. The first read only records what is there.
  - `mergeable` turning `CONFLICTING`; `UNKNOWN` keeps the last answer.
  - An empty check list keeps the last check state. Changes queue on the watch until the agent takes them.
- **Prompt**: while changes are queued, each tick looks for the agent in `agent.list`. Only an idle or done Claude Code agent whose checkout is still on the watched repository root and branch is woken; otherwise the wake waits (after the agent moved to another branch, say). The wake goes through `Driver::prompt` and all its guards with no `expected_draft`. An agent that has just started working, a box holding text, a scrolled screen or a blocked agent refuses it, nothing is cleared, and it is tried again on the next tick. Right before the write, the status read again also refuses an agent that is no longer Claude Code, and the authorization check confirms the watch still exists for that URL and its phone is still paired, so "Stop watching" or a revoke during the attempt types nothing.
  - The prompt is one line naming at most 10 changes: `Pull request #N (<url>) changed: check "<name>" failed; new review <url>; ...`.
  - Check names lose controls, format characters and quotes and are cut at 100 characters. Comment and review URLs must be `https://` without whitespace or control characters.
  - A head move drops queued check changes. A queued failure, pass or conflict that no longer holds before the wake is dropped.
- **After a wake**: an audit line (`pr.wake`, the terminal id, the summary and the pull request URL) and an alert "Woke \<agent>" with the summary (for example "CI failed on #123") through the done alert path, so `mute_done` silences it.
- **Wake prompts in Chat**: after a wake, collied remembers the exact prompt text, the summary and the time for that terminal in `pr-wakes.json` (0600) in the data directory, never in the log or a push. It keeps the last 20 per terminal, apart from the watch so they outlive it (a merge ends the watch right after its last wake) and a restart, and drops a terminal's list once its pane closes or its agent exits (the terminal is missing from a non-empty `agent.list` read by the watch task, which also runs while wakes are remembered and no watch is active).
  - `agent.history` sets `HistoryMessage.origin` (`kind: "pr_watch"` and the summary) on a main-thread user message whose text equals a remembered prompt for that terminal, and `Agent.last_prompt_origin` is set when `last_prompt` equals a remembered prompt's first line cut the same way, so the Inbox also marks a prompt that differs only after that cut. Marking compares text only, not who typed it: re-sending a wake's exact text also shows as a wake. Wakes are keyed by herdr's terminal id, which herdr assigns anew when it restores a session after a reboot, so earlier marks are lost then.
  - Chat shows a marked message as one collapsed "PR watch: \<summary>" row with the eye that expands to the full prompt; grid card previews and the Inbox show the same line instead of the prompt. The app shows an unknown `kind` as an ordinary message. No version bump: both fields are optional and additive on server-to-phone types, which no retained revision decodes strictly, so an older app ignores them and an older collied sends neither, showing the wake as an ordinary prompt.
- **Stops**: the watch ends, with anything queued, when:
  - the pull request is merged or closed;
  - 10 wakes in a row were made only of comments and reviews (a wake with any other change resets the count);
  - 8 reads in a row failed (no `gh`, no login, network, an unreadable answer);
  - the terminal is no longer in a non-empty `agent.list`;
  - the phone that started it is revoked or unpairs, or is no longer paired when the task ticks (a revoke while collied was stopped);
  - the user picks "Stop watching".
  The menu and badge follow through `flock.changed`.

### Archiving when the pull request merges

A merged pull request's badge reads "Merged" (only the icon on grid cards), and the session menu puts Archive first. Settings > Sessions > "Archive when the PR merges" (off by default, `archiveOnMerge` in `prefs.json`, absent until the user picks it) makes collied archive the task itself. collie-core sends `task.archive_on_merge {enabled}` (Drive class, audited with `enabled=`) to every connected machine when it changes and to each machine at the start of every session, after `push.register`; the app sets it at launch only once the user has picked it, so a phone that never did leaves the Macs' setting alone. collied keeps the `StableID`s of the phones that turned it on in `archive-on-merge.json` (0600) in the data directory, so it holds with no phone connected and across a restart. It is on while any phone in that file is still paired. Any phone turning it off empties the file, so a `StableID` a phone no longer uses (a reinstall) cannot keep it on; a revoke or unpair removes that phone.

- **When**: on the linked pull request task's 30 s tick. While the setting is on and no phone is connected, the task still runs, with one herdr snapshot per tick, only for agents that pass the workspace check below, at the same once per 2 minutes per checkout and branch, so a merge is noticed within about 2 minutes either way. Those reads do not change the pull requests a phone is shown. Only a fresh `gh pr view` that finds the pull request `MERGED`, or a kept merged result (see above), makes the agent a candidate, at most once per 2 minutes; a value cached within those 2 minutes never does, and a candidate that fails a check is tried again at the next fresh or kept read.
- **Checks, all read fresh in this order** (`Driver::archive_if_merged`):
  1. The setting is on.
  2. A herdr snapshot in which the terminal's workspace is a linked worktree and every pane of that workspace is an agent that is idle or done with no subagent running. A plain shell pane, an agent working, blocked or unknown, a Claude Code agent with a running subagent, one whose transcript cannot be read, or one whose subagent scan left something out (more than 8 workflow directories, or files past the 8 opened per scan that were never read before) holds it.
  3. `git status --porcelain --untracked-files=normal --ignore-submodules=none` in the checkout prints nothing (ignored files do not count; a submodule with changes, untracked files or a commit other than the recorded one does, whatever `.gitmodules` or the config say; the repository's filter commands are blanked as for diffs), and `git ls-files -v --recurse-submodules` lists no assume-unchanged (lowercase tag, as `core.ignoreStat` sets) or skip-worktree (`S`) entry, in the checkout or a submodule, since `git status` does not look at those files.
  4. `gh pr view --json number,state,headRefOid` again, which must still say `MERGED` with the same number.
  5. `git merge-base --is-ancestor HEAD <headRefOid>` (a 40 or 64 hex character id only), so the checkout holds no commit the pull request does not.

  Then `Driver::archive_merged` runs the archive of `task.archive`: it checks the workspace again on its own snapshot, refuses a regular folder (it never only closes the pane), and, after its last authorization check and right before `worktree.remove`, requires the checkout herdr is about to remove to be the one whose pull request was read, and runs the git checks on it once more. Its authorization check is that a paired phone still has the setting on, so turning it off or revoking the phone stops an archive in flight before the removal. Unlike a manual archive it does not run `gh poi`, which deletes every merged branch and removes other clean worktrees of the repository, whatever their agents are doing.
- **After**: one audit line per archive attempt that reached `archive_merged` (`collied`, `task.archive`, the terminal id, `PR #N merged: <result>`); candidates that fail a check before it are not audited. On success, one alert "Archived \<agent>" with "PR #N merged" through the done alert path, so `mute_done` silences it, and `flock.changed`.

## Git reads

Git changes, the archive checks and the pull request branch checks run git in the agent's checkout through one builder (`git::git_command`), which treats the repository's config as untrusted: null stdin, no `GIT_*` variables from collied's environment, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, `core.fsmonitor=false`, `diff.external=` and an 8 s timeout. Diffs pass `--no-ext-diff` and `--no-textconv`, and `diff` and `status` blank the repository's `filter.<driver>.clean` and `.process` commands. In a partial clone (for example `--filter=blob:none`), a diff that needs a missing blob would fetch it from the remote, running programs the repository configures such as `remote.<name>.uploadpack`, `core.sshCommand` or a credential helper. `GIT_NO_LAZY_FETCH=1` stops that fetch (git 2.45, and the 2.39.4 to 2.44.1 security releases). On older git, an empty `GIT_ALLOW_PROTOCOL` refuses every transport, overriding any `protocol.*.allow` in the repository's config, and a blank `fetch.bundleURI` on the command line, which the fetch inherits, keeps it from starting `git-remote-https` for a bundle URI before that check (its setup can run a credential helper for `http.sslCertPasswordProtected`). Such a read fails instead.

## Conversation history

`agent.history` is a read method on the paired connection. The phone sends a terminal ID and optionally `before` or `after`, plus a case-insensitive `query` for search. Cursors bind the agent kind, session UUID, file device and inode, byte offset and a hash of the preceding 64 bytes; replacement, truncation, changed cursor bytes or a session change reset the page. The daemon resolves the live agent before reading and verifies its identity again before replying. A missing agent identity or an unreadable file returns `available: false` with a distinct `unavailable_reason`. Session identity comes from herdr, never a folder or recency guess; reporting a missing identity lets the next poll recover. An existing empty transcript returns `available: true` with no messages. An older daemon rejects the additive method and the phone keeps Terminal available. No version bump.

- Copilot CLI uses the conversation selected for the pane (Live Copilot conversation in [Context and inbox](#context-and-inbox)) instead of herdr's ID, which can be stale after `/new`; while that selection is missing or ambiguous, the reply is `available: false` with its own reason and nothing is read. Because `/new` can switch conversations without changing herdr's ID, the daemon selects the conversation again from the agent's current title and pane processes after the read, and refuses a page read from another session. Copilot names a session automatically after its first prompt (`name` in `workspace.yaml`, with `user_named: false`), and the selection accepts that name like one the user set.
- `latest: true` (revision 27, with no cursor or query) reads only the last two user messages and the last two assistant text messages, in conversation order, from the same 2 MiB tail window with the same per-record caps, within 40 KiB. Tool calls, results, events, subagent records and empty or whitespace-only text never count (thinking and reasoning are never read, except a Claude progress update written as thinking, below); a record mixing text and tool calls counts only its text; the reply carries no cursors. Fewer come back when the window holds fewer.
- The reader uses the context summaries' Claude and Codex transcript locations, and Copilot CLI's `session-state/<session>/events.jsonl` under `COPILOT_HOME` (default `~/.copilot`). A blocking worker reads at most a 64 KiB format header and a 2 MiB history window without holding the shared transcript mutex. Only newline-terminated records are consumed, so a partial append is retried. Backward pages and forward updates carry distinct cursors; replies hold at most 40 message blocks and 40 KiB of serialized messages, below the 64 KiB transport limit. Oversized records are skipped with an explicit notice and cursors still progress. Large text is truncated on UTF-8 boundaries for display; search matches before truncation. No transcript content or search text is written to audit, push or notification state. Stable record and block IDs prevent duplicates across pages and reconnects.

**Claude.** The reader takes main-thread user and assistant content blocks, `tool_use` and `tool_result` included, and excludes synthetic replies, foreign session records and user records the harness injected rather than the user typed (`isMeta`, such as skill text and subagent hand-backs, compaction summaries, and `task-notification` origins).

- A subagent hand-back and a task notification leave a one-line `event` message instead: "Subagent finished: \<description>", the description (or agent type) from the subagent's meta file, and "Background task finished", since the notification has no structural status or summary field.
- A slash command (a user record with no `promptSource` and not `isMeta`, whose string content starts with `<command-name>` or `<command-message>` and names a `/` command) leaves its name and arguments, such as "/effort high", and its `<local-command-stdout>` record is left out; a typed prompt always has a `promptSource`, so it is never taken for one. None of these lines carries other record text; each is capped at 120 characters without control characters and left out of search.
- A `!` shell command (a user record with no `promptSource` and not `isMeta`, whose string content is `<bash-input>CMD</bash-input>`) shows as the user's message `! CMD`, so search and the grid Chat preview see it, and the record that follows it, `<bash-stdout>OUT</bash-stdout><bash-stderr>ERR</bash-stderr>`, as one `tool` result with no call ID: stdout, then stderr when it is not empty, on the next line, both without terminal escape sequences (removed before truncation and search); a command with neither leaves no result. Chat shows a `tool` result with no call ID and no parent call as its own collapsed activity row, never grouped with the tool calls around it.
- A prompt sent while Claude is working is written only as an `attachment` record (`attachment.type` `queued_command`, `commandMode` `prompt`, `origin.kind` `human`) once Claude Code absorbs it into the running turn; its `prompt` (a string, or text and image blocks) shows as an ordinary user message at that record's place, so it also reaches search and the grid Chat preview. A prompt that waits for the turn to end is written as a `user` record with `promptSource` `queued` instead, never as both, so neither shows twice. Other attachments and queued commands (task notifications, subagent hand-backs, coordinator messages) stay hidden.
- Claude 5.1 and later (parsed from `message.model`, such as `claude-opus-5-5`: a family name, a major version and an optional one- or two-digit minor) write the short progress update before a tool call as a second thinking block of the same message, after the reasoning block, instead of a text block. Claude Code writes each block as its own record sharing `message.id` and numbers it in `apiBlockIndex`. Since thinking blocks lead a message, a main-thread thinking block at index 1 or later (`apiBlockIndex` plus its position in the record) on such a model is that update and shows as ordinary assistant text, reaching the grid Chat preview and, by the same rule, `last_line` (the Inbox latest reply and the watch); the rule needs no neighboring record, so a page or tail window that splits the message still shows it. A lone or first thinking block stays hidden as reasoning, as does every thinking block of an older model, a synthetic reply or a subagent record.
- No version bump for any of these: each arrives as an ordinary message.
- Subagents: Claude Code keeps each subagent's records in `<session>/subagents/agent-<id>.jsonl` beside the session's transcript, with `agent-<id>.meta.json` naming the parent Agent call (`toolUseId`). The reader adds a subagent's records, tagged with that call's ID in `parent_call_id` (additive, no version bump), right after the Agent call; forward pages also add them after its hand-back (`origin.from`), so an open Chat gets the steps when a background subagent finishes. It opens these files like the transcript (no symlink, non-blocking), only for an id of letters and digits and only through real directories under the session's own directory. The subagent files read for one page share one more 2 MiB tail window, plus up to 64 KiB of each file's head for its prompt, and the page is marked omitted when records in between are left out; a subagent that does not fit what is left of it starts the next page. Subagent records get the same per-record caps and count toward a page's 40 blocks and 40 KiB: a subagent larger than the room left keeps its first step and its latest ones and marks the page as omitted, and its call starts the next page only when not one step fits. Context and the last line still ignore subagents.

**Codex.** Current Codex (0.160 and later, or a header window containing `item_completed`) uses `UserMessage` and `AgentMessage` completion events for conversation text, avoiding their overlapping `response_item` messages; older Codex uses `response_item` messages. Both read `function_call` and `custom_tool_call` and their outputs with call IDs; encrypted reasoning and internal instructions are excluded.

**Copilot CLI.** The file must start with a `session.start` naming the selected conversation. The reader shows typed `user.message` content with no `source` or `source: "user"` (other sources, such as autopilot, `skill-*` or `agent-<id>` outside a subagent, were injected and are left out; a subagent's `agent-<id>` prompt is kept), `assistant.message` content and each of its `toolRequests` as a call, and `tool.execution_complete` results (`result.content`, or `error.message` for a failed call) paired by `toolCallId`. `tool.execution_start` duplicates the request and is not shown; reasoning, system prompts, hooks, model and usage records are excluded. A `system.notification` of kind `agent_idle` or `shell_completed` leaves "Subagent finished" or "Background task finished" as an `event` line. Copilot writes subagent records into the same file, marked with the child's `agentId`; they are tagged in `parent_call_id` (no version bump) with their `parentToolCallId`, or for the child's prompt, which has none, with the `toolCallId` of its `subagent.started` or of another record of that child in the same 2 MiB window. A child record whose call cannot be found in the window is left out rather than shown as the parent's conversation. Record IDs come from each event's `id`.

**Phone.** The SwiftUI session keeps its composer and approval paths and switches only the content area. Chat projects records into a lazy conversation timeline: text replies stay visible and consecutive tools form one collapsed activity row, pairing calls and results by call ID. Activity row IDs survive prepends and appended results; idle polls do not rebuild the timeline. An Agent call's disclosure nests its subagent's prompt, tool calls (collapsed) and reply, matched by `parent_call_id` wherever the call sits in the loaded timeline, and its activity row counts the subagent steps. Search keeps every matching record visible and highlights matched text. Chat keeps an ID-based scroll position, loads older pages on demand, and polls only the appended portion while visible and in the foreground. Search scans bounded batches back to the beginning, stops when cleared or when Chat closes, navigates matching messages by stable ID, and once the older scan completes polls for new matches. Native Liquid Glass controls expose search, activity disclosure, Copy and return-to-latest. Terminal keys and wrapping stay in Terminal, with a Chat handoff button for interactive prompts. Terminal scrollback stays bounded because it controls repeated screen snapshots and still serves shells and unavailable transcripts.

## Plan usage

Claude Code passes the plan's limits only to the status line command, as `rate_limits.five_hour` and `rate_limits.seven_day` (`used_percentage`, 0 to 100, and `resets_at`, Unix seconds) on its stdin, on each refresh: a new reply, `/compact`, a mode change, or a window reaching its reset. It stores them nowhere on disk except a cache refreshed by `/usage` (in `~/.claude.json`, which also holds account data collied should not read). Codex's rollout `token_count` events carry `rate_limits`, but `primary` and `secondary` are null for credit-metered workspaces, so the daemon asks the local Codex app-server for `account/read` and `account/rateLimits/read` every five minutes and keeps only `individualLimit`'s used credits, allowance and reset date. A confirmed sign-out, or a successful response without a limit, clears the Codex reading and publishes the change to the phone; a failed fetch keeps the last reading. Codex manages its own OAuth token. Copilot's premium quota comes from GitHub's `GET /copilot_internal/user`, which also answers for a seat an enterprise assigns (Copilot below).

- **Tap**: `collied statusline` reads the status line JSON from stdin (at most 1 MiB), keeps the two windows (percentage rounded and clamped to 0 to 100, reset time in ms) and, for a lowercase-UUID `session_id`, `context_window.context_window_size` (1K to 100M), and drops the rest (`spend_limit` included). It merges them into `usage.json` (0600) in the data dir under an exclusive `flock` on `usage.lock`, so concurrent sessions do not lose each other's windows, then replaces the file atomically without `sync_all` (a full drive flush on macOS; the next refresh redoes a lost write).
  - Each session reports the limits from its own last reply, so they merge per window: the later `resets_at` wins, and within the same window the higher percentage, since usage only grows there; a window missing from one session's input is kept until its reset time. `recorded_ms` moves only when the input agrees with the merged result, so a quiet session's older figures neither replace newer ones nor look fresh.
  - An unchanged value is stamped again at most once a minute, and an input that changes nothing leaves the file alone, since the status line runs several times a second while a reply streams. Input without `rate_limits` keeps the last limits, so a session before its first reply does not erase them. At most 64 sessions' windows are kept, the oldest seen first out. It starts no runtime and prints nothing; the README line runs it in the background.
- **Daemon**: `Transcripts` holds the reader. It re-reads `usage.json` only when its size or mtime changed (`O_NOFOLLOW`, regular file, at most 64 KiB): for `flock.snapshot` and `approval.list`, when it derives a `claude` agent's transcript (for the session's window), and on the reconcile loop's 1 s herdr poll, which costs one `fstat`. The plan belongs to the machine, not a session, so it goes out on the snapshot as `Flock.plan_usage` (`five_hour` and `seven_day`, each `used_percent` and `resets_at_ms`, and `recorded_ms`), with or without a Claude Code agent open. When it changes and a phone has a session open, that tick sends `plan.usage` for a present plan or `flock.changed` to refresh a cleared one; the phone's core applies it to its cached flock. There is no separate timer. The session's window replaces the model table for `context_left`, and the transcript cache is keyed by it too. No version bump: the field is additive on a server-to-phone type, and an older app ignores the unknown event.
- **Phone**: the Agents tab has a segmented control, Agents and Usage, above the chosen layout; the layout picker is disabled while Usage shows. Usage shows one card per machine with a plan recorded: the machine and how long ago it was recorded ("just now", "3m ago", "1d ago"), then a Claude Code row with "5-hour usage limit" and "Weekly usage limit" blocks, a Codex row with a "Monthly usage limit" block when Codex reports an individual limit, and a Copilot row with a "Monthly premium usage" block when collied read one.
  - Each block is a title, a full-width bar with an elapsed-time tick, then the amount used on the left (percent for Claude; used and allowed credits for Codex and Copilot, or requests when the Copilot seat is not token-billed, or "Unlimited" with no bar for a seat without a cap) and the reset on the right (the 5-hour reset as a clock time, the weekly one as a countdown, Codex and Copilot as a date). Copilot use past the allowance keeps the bar full and shows the real amount.
  - A window past its reset is hidden. Claude data over 5 minutes old and Codex and Copilot data over 10 minutes old are dimmed. A `TimelineView(.everyMinute)` redraws the card while it is on screen; nothing is fetched beyond the list's cache refresh.
- **Copilot**: a task beside the Codex one runs `gh api --hostname github.com copilot_internal/user` every five minutes, with or without a phone, with the linked pull requests' `gh` setup (fixed binary path, `GH_PROMPT_DISABLED=1`, no `GH_TOKEN`, `GITHUB_TOKEN` or enterprise token variables, null stdin, a 30 s timeout, `kill_on_drop`): the user's own `gh auth login`, github.com only, so collied needs no host setting (GitHub Enterprise Cloud with data residency, `*.ghe.com`, is not read).
  - `--jq` reduces the answer inside `gh` to `token_based_billing`, `quota_reset_date`, `quota_reset_date_utc` and `quota_snapshots.premium_interactions`, so the login, account id, tracking id, organization and enterprise lists and service endpoints never reach collied.
  - collied keeps `used` (`entitlement` minus `remaining`, held at 0 or above, plus `overage_count`, so use past the allowance counts whether GitHub reports it as a negative `remaining` or in `overage_count`), `limit` (`entitlement`), `unlimited`, `token_based_billing` and `resets_at_ms` (from `quota_reset_date_utc`, else `quota_reset_date` as UTC midnight), as `copilot` in `usage.json` and on `PlanUsage`.
  - No `gh`, `gh` exit code 4 (no login), an HTTP 404, an answer without `premium_interactions` or an `entitlement` of 0 on a limited seat clears the reading; any other failure (network, timeout, a malformed answer, a reset already past) keeps the last one. The chat and completions quotas are not read. Nothing from `gh` is logged, audited or pushed. No version bump: `copilot` is an optional, additive field on a server-to-phone type, which an older app ignores.
- **`collied doctor`**: `plan usage` says when the tap last recorded the limits and how many sessions' windows it holds, or warns that it has recorded nothing. `copilot` says when the daemon last read Copilot's premium usage, while that reading is under 10 minutes old; otherwise it asks GitHub once itself and says that the usage is readable, that there is no `gh`, login or premium quota, or why the read failed.

## Token cost

The Usage view's "Tokens and cost" card reads `usage.costs` (revision 28, a read method) with a range (`today`, `7d` or `30d`) and the phone's current UTC offset in minutes (within 18 hours), so days end at the phone's midnight; the one offset applies to the whole range, so after a daylight saving change the earlier days are off by an hour. The reply carries `scanning`, the token totals (input without cached input, output, cache read, cache write), the estimated cost and cache savings, one cost per day of the range, oldest first, and at most 32 model rows by cost (then tokens), each with its agent, model id, tokens, and `cost_usd` and `cache_savings_usd`, both null when the model has no price. Totals cover every model, listed or not, and only priced models add to costs. The audit log leaves the method out, like `flock.snapshot`, since the card polls it.

- **Sources**: the transcript readers' roots: Claude Code's `projects` (every `*.jsonl`, subagent and workflow transcripts included), Codex's `sessions/YYYY/MM/DD/rollout-*.jsonl` and `rollout-*.jsonl.zst`, and Copilot CLI's `session-state/*/events.jsonl`. The walk never follows a symlink (directory entries are typed without following them, and files open with `O_NOFOLLOW` and `O_NONBLOCK` and must be regular), skips names starting with `.`, descends at most 5 levels and lists at most 20,000 files per root, counting only files modified in the last 32 days (by `lstat`). When a root hits the cap, indexed files missing from the listing are kept rather than forgotten. Codex compresses a rollout idle for 7 days to `.jsonl.zst` and decompresses one it resumes, writing the new form before removing the old; while both forms exist, only the plain file (same session id) is listed, as Codex itself reads that one.
- **Claude Code**: `assistant` records with `message.usage`: `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` and its `cache_creation.ephemeral_1h_input_tokens` part, with `speed: "fast"` and `message.model`. Sidechain records count; `<synthetic>` records are skipped. Claude Code writes one record per content block, and a resumed session repeats earlier records in its new file, so a record counts once per `message.id` plus `requestId` across all files, kept by the first file (in path order) to read it. A message's block records repeat its input and cache counts, but a streamed message's earlier ones (seen in subagent transcripts) carry a partial `output_tokens`; the file keeps the output it counted for each key and adds only the increase when a later record of the same key, in this scan or a later one, reports more.
- **Codex**: `event_msg` `token_count` events with `info.last_token_usage` (`input_tokens` includes `cached_input_tokens` and `cache_write_input_tokens`, which are subtracted), under the model of the latest `turn_context`. A call with more than 272,000 input tokens, cached included, is marked long. An event is skipped when its `total_token_usage` equals the last counted one (Codex repeats unchanged events), or before any `turn_context`. When the counters restart (`total_token_usage` equals `last_token_usage`), Codex can later replay that first request of the new sequence: the first request's timestamp and `last_token_usage` are kept (as a hash), and a restart to that exact event again is skipped without changing the last counted total. A later request that restarts with the same counters at another time still counts, and a zeroed `total_token_usage` forgets the kept first request. Current Codex forks and subagent rollouts start their own counts rather than copying the parent's `token_count` events (checked against 0.163 rollouts), so no fork suppression is needed.
- **Copilot CLI**: `session.usage_record` events, one per model call, the main agent's and each subagent's: `data.usage.model`, `inputTokens` (which includes `cacheReadTokens` and `cacheWriteTokens`, and marks the call long above 272,000), `outputTokens`. Current Copilot CLI writes the model and the cache split; a record without a model (as in the scrubbed `copilot-subagents.jsonl` capture) counts under `unknown`, with no price. Copilot bills premium requests, so its cost is an API-equivalent estimate and the card says so.
- **Model ids**: at most 64 characters of letters, digits and `._:/[]-`, else `unknown`, so only plain ids leave the machine.
- **Index**: `usage-costs.json` (0600) in the data dir keeps, per transcript path, its device and inode, its size, the offset just past its last complete line, Codex's current model, last counted total and current sequence's first request (as hashes), the token sums per 15-minute UTC slot, model, fast mode and long call, and the hashed Claude keys it counted with their slot and output.
  - A scan reads each file from its offset to its size in 1 MiB chunks and consumes only newline-terminated lines (a line over 8 MiB is skipped), so a partial last line is read again once complete. A file whose size is unchanged is not opened past `fstat`. A file that shrank, or whose device or inode changed, is read again from the start after its counts and keys are dropped.
  - A compressed rollout cannot be read from an offset, so it is decoded (with the pure-Rust `ruzstd`) and read whole whenever its device, inode or size changes; the decoder's window is limited to 8 MiB as for Resume, decoding stops past 512 MiB of output, and a file that decodes past that, or fails to decode, is recorded with no counts until it changes.
  - Slots and keys older than 32 days are dropped at the end of each scan, and so are files that disappeared or went quiet. The index is encoded under the lock and replaced atomically after the lock is released, when a scan changed it; a format change bumps its version, and an index of another version is discarded and rebuilt. A file that a resumed copy deduplicated against and that is later deleted takes the shared records with it until the copy is read again from the start.
- **Scans**: `usage.costs` starts a scan on its own thread unless one runs or one finished in the last 15 s (monotonic clock), then answers at once from the index, so a cold scan never holds up the request or the connection. The scan holds the index lock only to merge one file, so a reply during a cold scan has the totals so far and `scanning: true`. A first scan of about 4 GB of transcripts takes a few seconds; a later one, a fraction of a second.
- **Prices**: `crates/collied/data/prices.json` holds LiteLLM's `model_prices_and_context_window.json` entries for `anthropic` and `openai` chat and responses models: input, output, cache read, cache write and one-hour cache write rates per token, OpenAI's rates above 272K input tokens, and the fast-mode multiplier. `just prices` refreshes it, and LiteLLM's license beside it, from the commit pinned in the justfile; collied fetches nothing at runtime.
  - Lookup lowercases the id, drops a `[...]` suffix (Claude Code's `[1m]`) and a provider prefix, writes Claude ids with `-` for `.` (Copilot's `claude-opus-5.5` is Claude Code's `claude-opus-5-5`), then tries the id without a trailing `-YYYYMMDD`.
  - A cache rate the table lacks is the input rate; a missing one-hour rate is the plain cache write rate. A long call uses the above-272K rates where the table has them; only OpenAI's above-272K tier is applied, not other tiers such as Claude Haiku 5.5's above-100K rates. Fast mode multiplies every rate. Cache savings are cache reads times the input rate less the cache read rate.
- **Phone**: each machine's card asks on appear, when the range or the machine's link changes, and on pull to refresh, then every 2 s while `scanning`. A failed read keeps the figures already shown for the same range, and retries while they are still partial; a new range starts from a spinner. Token sums saturate rather than overflow. A session below revision 28 refuses the method locally and the card asks to update collied on that machine. Swift Charts draws the daily cost for 7 and 30 days.

Security: [Agent transcripts on the Mac](threat-model.md#agent-transcripts-on-the-mac).

## Starred agents

- `agent.star {terminal_id, starred}` (Drive class: audited and rate limited) stars or unstars a pane and sends `flock.changed` so every session refetches. Starring reads `session.snapshot` and answers `not_found` for a terminal herdr does not list; unstarring reads nothing, so it works for a pane already gone.
- collied keeps the stars in `stars.json` (0600, data dir), one set per machine shared by all of the owner's paired phones, as `terminal_id` to `pane_id`. herdr gives every pane a new `terminal_id` when it restores its session (after a reboot) but keeps the `pane_id`; a cross-workspace move does the reverse. On each `flock.snapshot`, and every second in the reconcile loop while a star is not in that tick's `agent.list` at the pane it was last seen in (a shell pane, a closed pane, a restore or a move; with or without a phone connected, one more `session.snapshot` per tick), collied keeps a star whose terminal is listed (updating its pane id), moves one whose terminal is gone to the terminal now in its pane, and drops the rest. A snapshot with no pane changes nothing, since herdr answers before it restores its panes. `pane_id` still never leaves the machine.
- The snapshot carries them as `Flock.starred` (additive, no version bump, but the app and collied update together since client params deny unknown fields). A star survives an app reinstall (the first snapshot after pairing again lists it), a phone offline or reconnecting (the phone never prunes; it shows what the cached snapshot lists), an agent exiting (its pane stays) and a herdr restore. It goes when its pane closes, or when a phone removes the machine (`unpair` clears them all). Starring needs the machine reachable. Gaps: a pane id that herdr reuses for a new pane within about a second (or while herdr is unreachable) takes the old star with it, and a move followed by a herdr restore in that window loses the star. Closing every pane keeps their stars, since an empty list is not trusted, and a new pane that gets one of their pane ids inherits that star.

## Terminals

A pane with no agent is a plain shell: herdr keeps the pane, with its `terminal_id`, when the agent in it exits (verified on 0.9.3). The phone lists such panes, shows their screen and types into them, under the rules below. Security: [Shell input from the phone](threat-model.md#shell-input-from-the-phone).

### Opt-in

```toml
[terminals]
enabled = true   # false, the default, when the section or the key is absent
```

- Read at start (`ServerConfig.terminals`); a change needs a restart, which ends every session. No method changes it, and `collied.toml` is rewritten only by `collied apns import` and `collied setup`'s push step.
- Off: `flock.snapshot` has `terminals: []` and no `terminals_enabled`; every `terminal.*` request but `terminal.lock` answers `terminals_disabled` ("terminals are off on this machine; set [terminals] enabled = true in collied.toml and restart collied") before any herdr call, audited. `terminal.lock` answers `ok` whatever the setting.
- `pane.read` reads agent panes only, whatever the setting: a shell is read through `terminal.watch`, under a grant.

### What is a shell

- A pane is a shell when its `PaneInfo.agent` is absent and its `terminal_id` is not in `session.snapshot.agents` (which lists an agent herdr is still launching before its pane reports it). collied reads this from a fresh `session.snapshot` before every write, never from a cache, and also refuses while an approval is pending on that `terminal_id` (hook-driven approvals are keyed by it, and report sooner than herdr's process detection).
- `flock.snapshot` lists shells as `Terminal {terminal_id, workspace_id, label, cwd}`: `label` is the name given in herdr (`herdr pane rename`), `cwd` the foreground process's, else the pane's. Titles a program sets (`terminal_title`, which a zsh theme fills with the running command) never leave the machine. The phone titles a shell by its label, else its folder, else "Terminal". A shell created on the machine appears with the next snapshot; an agent exiting changes the flock and sends `flock.changed`.

### Grants

- **Terminal key.** The phone has a second Secure Enclave P-256 key besides its TLS key (`TerminalKey.swift`, Keychain item `dev.rbstp.collie.identity`/`terminal`), created with `[.privateKeyUsage, .userPresence]` and `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`: every signature needs Face ID or the passcode, and removing the passcode destroys it. The simulator uses a software key behind a LocalAuthentication prompt; a device never falls back to one.
- **Registration.** `pair.complete` carries `terminal_key` (base64url of the 91-byte SubjectPublicKeyInfo). collied checks it is a P-256 key and not the session's TLS key (an app sending its TLS key would sign without Face ID), else the pairing fails (audited `invalid terminal key`). The y/N prompt on the machine shows `terminal key: none | new | unchanged | replaces the existing one`, and "replaces an existing pairing of this node" for a paired phone. The key is stored in `peers.json` (`terminal_key`); pairing again replaces the whole record, so a pairing without a key forgets it. The phone keeps the key it paired with in `machines.json` (`terminal_key`) and answers `TerminalKeyMissing` (pair again) without asking for Face ID when its current key differs: paired before this feature, the passcode removed since, or no Secure Enclave key at pairing.
- **Challenge.** `terminal.challenge {terminal_id}` answers `{terminal_id, challenge, ttl_ms: 60000}` once the peer has a key (`terminal_key_missing` otherwise) and the pane is a shell: 32 random bytes, one outstanding per session (a new one replaces it), 60 s. Issuing one is not audited.
- **Grant.** `terminal.grant {terminal_id, challenge, signature}`: any attempt burns the session's challenge. The signature is ECDSA P-256 with SHA-256, DER, base64url, over `u32be(len) || bytes` of `"collie terminal grant v1"`, the machine's node ID, the `terminal_id` and the challenge (`protocol::terminal_grant_message`, built the same way by collied and collie-core; collie-core takes the node ID from the machine pinned at pairing). collied verifies it with the stored key (`collie_tls::verify`, ring) and answers `{terminal_id, ttl_ms: 300000}`; otherwise `terminal_locked` with the reason (`no challenge was issued`, `challenge expired`, `challenge does not match`, `signature did not verify`).
- A grant covers one terminal in one session for 5 minutes from its issue (`ServerConfig.terminal_grant_ttl`, `terminal::GRANT_TTL`; not a `collied.toml` key) and is bound to the key it was verified against. At most 16 per session. Grants and challenges live in collied's memory only (`State.terminals`, lock order peers, sessions, terminals). They end with `terminal.lock`, the session, a revoke or unpair, a re-pairing of the phone (its record replaced), an agent seen on that terminal (by a write's check, the watch, or the 1 s reconcile), and a collied restart.

### Watch and input

- `terminal.watch {terminal_id, lines?, low_data?}` needs a live grant and shares the session's one watch with `agent.watch`: it emits the same `agent.output` and `agent.output_patch` events, reading `pane.read source=recent_unwrapped` with the same halving on herdr's line limit, and ends (`flock.changed`) when the pane closes or an agent starts in it. It reads nothing while the session has no live grant for that terminal under the peer's current key (expired, `terminal.lock`, a re-pairing); a new grant in the same session resumes it. `agent.watch {terminal_id: null}` stops either kind.
- `terminal.run {op_id, terminal_id, text}`: one line of `PromptText` (no newline, tab, ESC or other control, no bidi or invisible format character, checked by the decoder), sent with herdr's `pane.send_input {pane_id, text, keys: ["enter"]}`, the one ordered write `herdr pane run` makes (verified on 0.9.3 with sh and zsh: the line runs). On macOS herdr 0.9.5 refuses a line longer than the terminal's canonical input limit while the pane reads in canonical mode, such as a shell still starting (`pane_send_failed`, its message naming canonical mode); collied answers `too_large` with a message to wait for the prompt and try again, and keeps no other part of herdr's message.
- `terminal.send_keys {op_id, terminal_id, keys}`: the closed `Key` list (at most 16) through `pane.send_keys`. ctrl+d, ctrl+z and ctrl+r are not in it: adding them would widen `agent.send_keys` too. Nor are ctrl+j and ctrl+m, which submit like Enter without its checks, or ctrl+o and ctrl+t, which open Claude Code and Codex transcript views that the scrolled-up check may not see, so later keys could answer a prompt hidden behind them.
- Both go through the `op_id` outcome cache. Right before the herdr write collied reads the snapshot again (still a shell, else `not_found` "the pane now hosts an agent", and the terminal's grants are dropped), then checks the peer, its grant in the session that sent the operation under the peer's current key, and no pending approval (`terminal_locked` otherwise; never `not_paired`, which would stop the phone reconnecting). A retry from the phone's next session replays the first attempt, which still checks the first session's grant. herdr targets panes by `pane_id` only (a `terminal_id` is refused as `pane_not_found`) and reuses pane ids, so the snapshot is read again before each write. A herdr error from these writes keeps its code only, since its message may quote the input. There is no foreground-process check: ctrl+c and answers reach the program running in the shell.
- `terminal.lock` ends every grant of the session and a terminal watch, and answers `ok`.
- New shell panes (`tab.create`) are not offered: a follow-up.

## Menu bar app (macOS)

CollieBar (`Mac/`) is a separate XcodeGen project, so the iOS project and its recipes are untouched. Pure Swift with no packages, it never links CollieCore. A SwiftUI `MenuBarExtra` with `LSUIElement`, so no Dock icon.

- It talks to collied only over the control socket, as the CLI does, with three requests: `watch`, `pair` (then `confirm`) and `peers_list`. It opens no network listener and reads none of collied's data files (Open Audit Log hands `audit.log` to its default app, Console); peers come from `peers_list`, and with collied off the menu says so.
- `watch` is read-only and not audited, like `status`: collied answers `{"type":"watch","pending_approvals":N,"collied_version":"VERSION"}` at once, then one line each time the count of pending approvals changes, from a tokio watch channel the approvals update under their lock. It does not subscribe to the phone event broadcast, whose receiver count means a phone is connected. The open connection is the running state and EOF is off; the app retries a failed connect every 2 s, its only polling. The menu status uses the version reported by that connection, never the installed executable or app version, and clears it on EOF; an older reply without `collied_version` shows version unavailable. No version bump: `collied_version` is an optional additive field on the local control reply; the phone protocol is unchanged.
- While collied is off, Set Up opens `~/.cargo/bin/collied setup` in the system Terminal app. A private 0700 temporary command file quotes the executable path, removes itself and its directory before exec, and is removed if Terminal cannot open, so no Automation permission or shell interpolation in the launch API is needed. Setup keeps its installed-binary signature check and interactive authentication and pairing prompts.
- Turn Off, Turn On and Quit run `collied stop` and `collied start` through the executable named in the launchd plist (`ProgramArguments[0]`), with no shell, so launchd's semantics (disabled until `start`, across reboots) stay in one place. The socket cannot do it: a stopped collied has no socket, and launchd's `KeepAlive` would restart one stopped from inside. Quit leaves collied off until Turn On or `collied start`. A collied run by hand, not by launchd, is not stopped.
- Pairing matches `collied pair`: the QR (CoreImage, correction level M), then the candidate's device label, node name and `StableID`, login and user ID, the terminal key change and "replaces an existing pairing", every phone string escaped like `collied::printable`, and 60 s to answer. Pair is not the default button (Return does nothing) and is live only 1 s after the candidate appears, the window's form of the CLI's `tcflush`; one answer is sent, never on its own: at the end of the 60 s collied refuses. The invite is never shown as text, selectable, copied, logged or kept: only the QR image lives in the view's state. Window restoration is off, and closing the window closes the connection, which cancels the pairing as Ctrl-C does.
- Open at Login uses `SMAppService.mainApp`, off by default.
- `just mac-install` signs it with the Developer ID (team `RM3UT3MMSR`) and the hardened runtime, with no App Sandbox (it would block the socket and running collied) and no entitlements, so it needs no App ID or provisioning profile. Notarization (`just mac-notarize`) is needed only to run it on another Mac without a Gatekeeper prompt.
- Its unit tests have no host app, so they never launch it against the live collied's socket.

## Live Activities

The lock screen and the Dynamic Island show an agent only while the user follows it: off by default for every agent, at most 5 at once on the phone. The phone starts each activity itself, from the foreground; collied only updates and ends it. Push-to-start is not used: it is unreliable from background wakes.

### Phone and collie-core

- Following starts an `Activity` (`pushType: .token`) with the agent's current state. Each token from `pushTokenUpdates` goes to that agent's Mac with `register_activity_token(machine_id, activity_id, terminal_id, token_hex, binding_id)`; every foreground registers the tokens of all running activities again. The title the app shows for the agent (its terminal title, at most 64 characters) is encrypted in the activity's static attributes, so the lock screen and the expanded island show it while collied's pushes keep the agent name or kind; it is fixed until the activity restarts. Unfollowing ends the activity at once and calls `end_activity(machine_id, activity_id)`.
- collie-core keeps the push and activity token registrations per machine in memory only and sends them on every connection, after `push.register`, since collied takes the APNs environment from it; calls are queued in call order, so the app registers push before its activities. An end the Mac has not acknowledged is sent with every connection until it answers, even after an app kill: collie-core keeps pending ends in `activity-ends.json` in the state dir (0600, atomic, written on every change), per machine id, each with its `activity_id` and the time it ended, nothing else, at most 16 per machine. At start it loads only the ends of paired machines that are under 8 h old (collied has expired the activity by then) and ignores an unreadable file; removing a machine drops its ends.

### Protocol

- `push.activity_token {activity_id, terminal_id, token, shows_approvals?, display_binding?}` and `push.activity_end {activity_id}`, both `MethodClass::Push`. `activity_id` is ActivityKit's `Activity.id` (`[A-Za-z0-9-]`, at most 64), `token` is the update token in hex (64 to 256 characters, redacted in `Debug`). `shows_approvals` (default false, omitted when false) says the activity shows an approval's command and its buttons; collie-core always sends `true`, since every activity the app starts carries the Mac's node id.
- No version bump: push and activity registrations require the negotiated `encrypted_display_v1`; peers without it keep ordinary tailnet operations but cannot register this codec. The optional activity binding is sent only with that capability.

### collied

- Stored in `push.json` (0600, atomic) under `activities`: `{stable_id, activity_id, terminal_id, token, environment, registered_at, shows_approvals, display_binding}` (`shows_approvals` omitted when false). A file without `activities` loads with none; an empty list is not written.
- Bound to the session's `StableID`: a device registers, replaces and ends only its own activities. The same `activity_id` or the same `terminal_id` from the same device replaces the old entry (the phone keeps one activity per followed agent, so an activity it never ended cannot hold a slot); a token is stored once. The environment is the device's own from `push.register` (`not_found` without one). At most 8 per device (`too_large` beyond). `push.activity_end` for an id the device does not have answers `ok`.
- Dropped on `push.activity_end`, on revoke, at start for peers no longer paired, on `Unregistered` or `BadDeviceToken` for that token, when the terminal is gone, and quietly (no push, audited as `ended: expired`) 8 h after `registered_at`, since ActivityKit ends an activity 8 h after it starts. The phone registers right after the start and again on every foreground; a registration of an `activity_id` collied already has keeps its `registered_at`, so the 8 h count from the first one.
- Updates come from the 1 s agent reconcile, after the approvals pass, never from terminal output. Per activity:
  - first sight (a new activity, a new token, or a collied restart): one update without alert, so the activity shows what the Mac sees;
  - content changed: an update, at most one per 2 s per activity (a change inside the gap goes out on the first reconcile after it); a status change alone never alerts on the activity (the end of a turn is the [done alert](#apns));
  - an approval routed to the activity ([below](#approval-on-the-activity)): sent in the same reconcile, whatever the 2 s gap;
  - nothing changed: the same content again every 10 min, to move the stale date while the Mac is up;
  - the terminal missing from two reconciles in a row: `end` with `dismissal-date` = now + 60 s, then the token is dropped. A missed `agent.list` (herdr down) changes nothing.
- Every send re-checks the pairing, like alerts. One audit line per register (`push.activity_token`, target `<terminal_id> activity=<activity_id>`) and per end (`push.activity_end` from the phone, or `ended: agent gone` and `ended: expired` from collied); tokens are never logged or audited.

| Header | Value |
|---|---|
| `apns-push-type` | `liveactivity` |
| `apns-topic` | `<bundle_id>.push-type.liveactivity` |
| `apns-priority` | 10 for the update that carries an approval alert, 5 for every other update, refresh and end |
| `apns-expiration` | for the update that carries an approval alert, the approval's expiry, as for the alert it replaces; now + 5 min for every other |
| `apns-collapse-id` | none |

```json
{"aps":{"timestamp":1791028800,"event":"update","content-state":{"v":1,"enc":"<authenticated envelope>"},
        "stale-date":1791029700,"alert":{"title":"Collie","body":"An agent needs attention"}},
 "node_id":"nMAC","event_id":"<opaque event>"}
```

- `timestamp`, `stale-date` (now + 15 min) and `dismissal-date` are Unix seconds. `alert` is present only on an approval alert. Public relevance scores are omitted so status does not leak through ranking.
- `content-state` is exactly `{v:1,enc}` for initial, local, update and end state. Its decrypted `state` keeps `status`, whole reference-date seconds in `statusSince`, agent `title`, optional known `kind`, workspace, count, optional approval ID and inner context, and local progress. The widget opens it with its attributes' node and activity binding. [protocol/live-activity-content-state.json](protocol/live-activity-content-state.json) describes its private fields; [protocol/push-display-vectors.json](protocol/push-display-vectors.json) holds the wire vectors.

### Approval on the activity

- A device that follows an agent gets that agent's approvals that offer Approve and Deny on the activity alone (any other, such as a question, a plan or a Codex or Copilot prompt, goes as the approval alert, without actions): one alert, the Dynamic Island expands, the command and Approve and Deny are on the activity, and no approval notification.
- Only an activity registered with `shows_approvals` takes the approval. An activity without a current encrypted display binding sends no private state; an urgent send that cannot be encrypted falls back to the encrypted approval notification.
- When `alert_due` lets an approval alert go out, every paired device without such an activity for that terminal gets the approval alert. A device with one gets, in the same reconcile, an update of that activity with priority 10, a generic `aps.alert` and encrypted content state containing `approvalId` and the inner context `enc`: the context sealed to that device's notification key exactly like the alert's `enc` (fresh nonce, AAD = `approval_id`, `{"v":1,"body":...}`; no `enc` without a key or a context), except that a context over 600 bytes once JSON-escaped is cut there with `…`, so the update stays under APNs' 4 KB with labels at their caps. The alert rules decide whether it alerts (a new episode or a changed prompt does, the same prompt reissued within 30 s does not), so an approval alerts once either way.
- A reissue that `alert_due` keeps quiet still reaches the activity, as an update with priority 5, no alert and the new `approvalId` and `enc`, so its buttons never decide a burned approval. It reaches no other device.
- Fallback: if the activity push fails (any APNs error, a network error or a dead token, which is dropped as usual), or the activity or the agent is gone by the time collied would push, the device gets the approval alert at once.
- Late fallback: APNs accepts a push to an activity the phone has ended (dismissed or ended by iOS while the app was suspended, Live Activities turned off, an update dropped by iOS's budget, or replaced by a later update while the phone was offline), and nothing tells collied. So an approval that alerted on an activity and is still pending and not being decided 2 min later also goes to that device as the approval alert, once (never twice with the early fallback). The cost: a user who has not answered within 2 min gets the notification as a reminder, and a dead activity delays the alert by up to 2 min. Both timers live in collied's memory; a restart reissues pending approvals, which alert again.
- The inner command `enc` is sealed once per device and approval and repeated inside freshly sealed outer envelopes on later updates (refresh, new token), so coalescing still sees an unchanged state. Once the approval resolves (applied, denied, superseded, expired) or the agent leaves `blocked`, the next update omits `approvalId` and `enc` and is a normal coalesced update without alert. An `end` never carries them.
- On the phone, `AgentActivityAttributes` carries the Mac's `nodeId`. The widget reads the protected notification-key App Group mirror, authenticates the entire state against its node and activity binding, then opens the inner command (`PushContext.open`) and shows it on the lock screen and in the expanded Dynamic Island (`privacySensitive`: redacted while locked). It shows a neutral display without buttons when state authentication fails, and "Approval needed" when authenticated blocked state has no command. Approve and Deny, shown only with a command that decrypts, are `Button(intent:)` with a `LiveActivityIntent` whose `authenticationPolicy` is `.requiresAuthentication`: iOS makes the user unlock first, then the intent runs in the app process and takes the notification actions' path (`decideFromNotification`, background budget; the nonce comes from the Mac over the tailnet).

## `collied setup`

One interactive command adds a Mac or a Linux machine, or updates one in place. It reuses the subcommands' code (`daemon::login`, `service::install`, `doctor::run`, `push::import`, the `pair` flow) through a small `setup::Host` trait, so the order and the skip rules are unit tested against a fake without touching launchd, systemd, the tailnet, the Keychain or systemd-creds. One `Host` implementation serves both OSes; only the service backend (`service::state`, `unload`, `install`, `log_tail`) differs. Each step checks its own done state, so a rerun resumes where the last one stopped:

| Step | Done when | Otherwise |
|---|---|---|
| login | the daemon answers `status` with backend `Running` (it serves the socket only once its node passes the ownership checks); a loaded job gets 20 s first, for a daemon just restarted by `just collied-install` | unload a loaded job without disabling it (a crash loop or a logged-out daemon holds the node lock or the socket), then `collied login`; if login fails, start the job again |
| service | the plist on disk is the one `install` would write, the job is loaded, and the daemon's `started_ms` is not older than the binary's mtime | `service install` (bootout, then bootstrap, so a restart), then wait up to 60 s for the daemon, up to 10 s of that while its netmap shows no untagged device, so a node that has just started does not trigger the policy hint; on a timeout print the last 20 lines of `collied.err.log`. A plist with another `--config` than setup's stops setup instead: run `collied --config <path> setup` |
| doctor | no fail line | stop: fix, then run setup again |
| push | `[push.relay]` or `[apns]` is in `collied.toml` | offer it. By default, add `[push.relay]` (a new file is created 0600, else the atomic rewrite keeps the mode). With `--direct-apns`, ask for the `.p8` (key ID from `AuthKey_<KEY_ID>.p8`), team and bundle IDs, append `[apns]` and run `apns import`, putting the old config back if the import fails. Then restart the service so the daemon reads it |
| pair | never: phones may need to pair again after an update | offer `collied pair` |

Before any step it refuses unless stdin is a terminal, so `yes | collied setup` cannot answer the pairing prompt, and unless the running binary is `~/.cargo/bin/collied` (a regular file, not a symlink; on Linux a packaged regular `/usr/bin/collied` also passes), on macOS also Developer ID signed as `dev.rbstp.collied` (the check `apns import` makes). So it never installs an unsigned agent or one pointing at `target/release`, which the next `cargo build` replaces. It never confirms a pairing: the `y` on the computer, after the `tcflush`, stays the only confirmation.

On Linux the service rows read:

| Step | Done when | Otherwise |
|---|---|---|
| login | as on macOS; "loaded" is any `ActiveState` but `inactive` and `failed`, so a unit waiting to restart after a crash (`activating`) counts; while a daemon answers, only `active` counts, so a foreground `collied run` beside a restart loop is refused as running outside the service | `systemctl --user stop` (the unit stays enabled), then `collied login`; if login fails, `collied start` |
| service | the unit file on disk is the one `install` would write (executable, `--config`, pinned `XDG_*_HOME`), the unit is loaded, and the daemon's `started_ms` is not older than the binary's mtime | `service install` (`daemon-reload`, `enable`, `restart`), then wait up to 60 s; on a timeout print the last 20 lines of `journalctl --user -u collied.service` |

Before deciding, `service::state` stops setup when the user manager loads `collied.service` from another file or applies a `collied.service.d` drop-in to it, when the unit pins another `XDG_DATA_HOME` than setup's (that data dir holds another node, and setup would log in a new one), or when the unit runs another `--config`. The direct APNs step is the same code: `push::import` encrypts the key with `systemd-creds` or falls back to the 0600 file, and never prints it.

Doctor's `service` line reports the same state on both OSes: `up to date`, or a warn naming what setup would do; it is skipped with a warn when doctor is not the installed binary, since the state compares the service against the running one. On Linux it adds that the unit stops at logout when the user does not linger (`loginctl show-user`).

The control socket's `status` reply carries `started_ms` (when the daemon started) and `user_peers` (visible untagged nodes belonging to the daemon's verified embedded user; visibility does not prove TCP reachability), both with serde defaults; an older daemon reports neither, which setup treats as outdated. The phone protocol is unchanged.

On macOS, interactive login without an auth key tries once per login to open the browser, after printing the URL and QR. Only an HTTPS URL with exact authority `login.tailscale.com` (optionally port 443) and no userinfo is opened, through `/usr/bin/open` with an argument array. Failure is nonfatal; noninteractive, auth-key and custom-control logins keep the printed URL.

The policy check uses what the embedded node can see. `collied login` prints Tailscale's last login error. Before any listener or control socket is exposed, startup requires a positive user-owned self identity, an own-address whois matching the self StableID and user without tags or sharing, and configured or stored owners and every paired user matching that identity. A restarted node reports `Running` from Tailscale's netmap disk cache, which can lack the user profiles, so its own-address whois answers "peer not found" until control sends the live map: `collied run` and `collied login` repeat the whole check while whois gives exactly that answer, up to their start deadlines (60 s and 10 minutes), then fail with the usual error. Any other failure, including a mismatch, stops at once. The gate has no first-phone-owner fallback. Connection admission and the post-TLS gate recheck the actual self identity and a fresh peer whois; changing the owner or tagging the running node refuses new sessions rather than rebinding trust. Local reauthentication requires stopping the daemon first.

Doctor's `reach` line reports same-user untagged netmap peers. Zero can mean a phone has not signed in or a restrictive policy hides it; setup prints the same-user TCP grant as administrator guidance without changing policy. Policies that already permit personal devices need no edit. User ownership gives the embedded daemon its user's network privileges, not a separate service tag's confinement. Both nodes have normal user key expiry. See [tailnet.md](tailnet.md) for scoped state reset, reauthentication and the physical-device and corporate VPN acceptance gap.

## Linux

collied runs on Linux with the same protocol, gate, allowlist and approvals as on macOS. What differs: the build, the paths, the service manager, the listener check and where the APNs key lives. Built and tested on Arch (systemd 261, herdr 0.9.3).

### Platforms and build

| Target | State |
|---|---|
| `aarch64-apple-darwin` | built and tested |
| `x86_64-unknown-linux-gnu` | built and tested |
| `aarch64-unknown-linux-gnu` | mapped in `tailscale-sys` (GOARCH `arm64`); needs a cross C compiler in `CC`; not built or tested |

### Paths

| What | macOS | Linux |
|---|---|---|
| Data dir | `~/Library/Application Support/collie` | `$XDG_DATA_HOME/collie`, else `~/.local/share/collie` |
| Attachments root | `~/Library/Caches/dev.rbstp.collied/attachments` | `$XDG_CACHE_HOME/collied/attachments`, else `~/.cache/collied/attachments` |
| Service | `~/Library/LaunchAgents/dev.rbstp.collied.plist` | `$XDG_CONFIG_HOME/systemd/user/collied.service`, else `~/.config/systemd/user/collied.service` |

- The data dir holds `collied.toml`, `tsnet/`, `tls-key.json`, `peers.json`, `peers.lock`, `push.json`, `status.json`, `stars.json`, `pr-watches.json`, `pr-wakes.json`, `archive-on-merge.json`, `usage.json`, `usage.lock`, `usage-costs.json`, `audit.log`, `control.sock`, `node.lock` and `apns/`. `status.json` (when collied first saw each agent's status, for the phone's "how long ago") is replaced atomically, 0600, without `sync_all` (a full drive flush on macOS): a power cut can lose those times, and they restart from when collied next sees each status.

- tsnet's upstream path logic creates an empty `~/.local/share/tailscale` (0700) for a non-root user. collied's node state is only in `<data dir>/tsnet`. A system tailscaled (root, `/var/lib/tailscale`) is untouched: the embedded node is a separate device with its own keys.

### Embedded node ownership

Both OSes use the same user-owned node rules. `collied status` keeps `tags:` for diagnosis; doctor fails if tags appear. E2E nodes have private userspace state and no tags, with a local control plane modeling same-user and foreign-user ownership. The Linux display-kind fixture changes only test netmap OS metadata; platform never authorizes a peer. Neither daemon calls the native Tailscale CLI, changes system routes or reads the system VPN's account or state.

### systemd user unit

`collied service install`:

1. Makes sure the data dir is private, canonicalizes the executable and `--config` path.
2. Writes the unit 0644 through `collied.service.tmp` and a rename. It is rewritten on every install.
3. `daemon-reload`, then checks that the user manager loads the unit from that file (`FragmentPath`). With another unit of that name, or a different `XDG_CONFIG_HOME` in the manager, the install fails there (the file written stays) instead of reporting success for a unit that never starts.
4. `enable`, then `restart`.

```ini
# Written by `collied service install`; rewritten on every install.
[Unit]
Description=collie daemon: herdr agents over the tailnet
Documentation=https://github.com/rbstp/collie
StartLimitIntervalSec=0

[Service]
Type=exec
ExecStart="<exe>" "--config" "<config>" "run"
Environment="XDG_DATA_HOME=<dir>"
Environment="XDG_CACHE_HOME=<dir>"
Environment="XDG_CONFIG_HOME=<dir>"
Restart=always
RestartSec=2s
RestartSteps=5
RestartMaxDelaySec=1min
UMask=0077
NoNewPrivileges=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectSystem=strict
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
ProtectClock=yes
ProtectHostname=yes
RestrictSUIDSGID=yes
RestrictRealtime=yes
RestrictNamespaces=yes
LockPersonality=yes
MemoryDenyWriteExecute=yes
SystemCallArchitectures=native
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK

[Install]
WantedBy=default.target
```

The `--config` pair is present only when `--config` was given. No `User=`, no socket activation, no listener.

**Quoting** follows systemd.syntax, per field:

| Field | Rule |
|---|---|
| `ExecStart=` executable | absolute UTF-8 path with no `"`, `'` or `\`, else install refuses; quoted, `%` doubled (systemd does not expand `$` there) |
| `ExecStart=` arguments | quoted; `\` and `"` escaped; `%` and `$` doubled |
| `Environment=` | the whole `KEY=value` quoted; `\` and `"` escaped; `%` doubled (`$` is literal there) |
| every field | control characters and paths that are not UTF-8 are refused |

A test runs `systemd-analyze --user verify` on a unit with such characters in its paths, where systemd-analyze and a user manager exist.

**Pinned XDG.** `XDG_DATA_HOME`, `XDG_CACHE_HOME` and `XDG_CONFIG_HOME` are pinned to what the installing CLI resolved, fallbacks included. Units started with the user manager (at first login, or at boot with linger) do not get `XDG_*_HOME` from the session (verified on the dev machine). The data dir, the attachments root and the herdr socket all derive from them: without the pin, the daemon could use another data dir than the CLI (control socket, peers) and look for another herdr socket. `HERDR_*` is not captured, as with launchd: `[herdr] session` in `collied.toml` picks a session.

**Restart.** `Restart=always` with a delay of 2 s growing over 5 steps to 1 min, and `StartLimitIntervalSec=0` so systemd never gives up: launchd's KeepAlive without a hot loop. collied exits when the tailnet listener fails for good, so the manager restarts it.

**Sandboxing** is best effort. In a user manager most of these settings rely on unprivileged user namespaces, and systemd skips them where those are unavailable. `ProtectSystem=strict` leaves the home directory and `/run/user` writable in a user unit. `UMask=0077` applies either way.

| Command | `systemctl --user` |
|---|---|
| `collied stop` | `disable --now`, then `reset-failed`: stopped, and off across logouts and reboots until `collied start`; the unit file stays. Fails when the unit file is not installed |
| `collied start` | `enable`, then `start` unless already active. Fails when the unit file is not installed |
| `collied service uninstall` | `disable --now` (when the file exists), remove the file, `daemon-reload`, `reset-failed`; refuses when the unit runs but its file is not at that path |

- Logs: the user journal (`journalctl --user -u collied`), no log files.
- A user unit runs while the user has a session; `loginctl enable-linger` keeps it running without one. The launchd agent likewise runs only in the GUI session.
- `just collied-install` on Linux: release build, copied to `~/.cargo/bin/collied` as a fresh inode (the running daemon keeps its copy until it restarts), then restarts the unit if it is active.

### Kernel TCP listener check

`tailnet::kernel_tcp_listeners(pid)` lists the kernel TCP sockets in LISTEN state that a process holds. It first checks that the pid is alive (signal 0).

- macOS: `/usr/sbin/lsof`, by absolute path. Its stderr must be empty except for exact copies of the three-line warning lsof prints for a mount point it cannot stat() (macOS mounts disk images under the temp folder); that warning only affects file system names of file rows, never socket rows. Any other stderr, or an exit other than 0 or 1, is an error, never an empty list.
- Linux: the socket inodes from the `socket:[N]` links in `/proc/<pid>/fd`, matched against the LISTEN rows (state `0A`) of `/proc/<pid>/net/tcp` and `tcp6`. The table header is checked. An fd closed during the listing is skipped, and so is a missing `tcp6` table when there is no IPv6 stack (no `/proc/sys/net/ipv6`); any other read or parse error is an error, never an empty list.

Used by doctor's `listen` line and by the tailnet `end_to_end`, e2e and collied server tests.

### APNs key on Linux

Each machine has its own APNs key (`.p8`, own key ID, revoked on its own in the Apple Developer portal), so a Linux machine pushes when the Mac is off. Same `[apns]` ids. The default store is `key = "systemd-creds"` ([APNs](#apns)).

- Credential name `collied-apns-<KEY_ID>`, file `<data dir>/apns/<KEY_ID>.cred`. The name is sealed in the credential: a credential renamed or copied for another key ID does not decrypt.
- systemd-creds is called as `systemd-creds --user --no-ask-password {encrypt|decrypt} --name=collied-apns-<KEY_ID> - -`: input on stdin, output on stdout (at most 64 KiB each way; the decrypted key is zeroized after use), never a file. collied runs `systemd-creds`, `systemctl`, `systemd-analyze`, `loginctl` and `journalctl` by absolute path, never from `PATH`: `/usr/bin`, else `/bin`, else `/run/current-system/sw/bin`. The name is always passed: an empty or missing name skips systemd's check of the sealed name.
- The credential file is read with the `key_path` checks (0600 regular file owned by the user, opened with `O_NOFOLLOW`).

`collied apns import AuthKey_<ID>.p8`:

1. The same checks as on macOS: `[apns]` ids, refuses a file named for another key ID, the `key_path` checks, an ES256 key. No signature check.
2. Encrypts it. collied writes the credential itself (0600, `O_NOFOLLOW`, atomic), since systemd-creds would write its output file with the umask's mode. The new credential is decrypted and compared before it is stored, and read back and compared after.
3. An existing credential that decrypts to the same key is kept, unless it has no TPM2 seal and the new one has: then the new one replaces it. An existing credential that no longer decrypts, or holds another key, fails the import.
4. Rewrites `[apns]` to `key = "systemd-creds"` (nothing to rewrite when no key line was there, since that is the default).
5. y/N to delete the original file, only if it is still the same inode.

If systemd-creds cannot encrypt (no systemd, no `systemd-creds.socket`, systemd older than 256, a container), import says so, copies the key to a 0600 file at `<data dir>/apns/AuthKey_<KEY_ID>.p8` (an existing file there is kept and must hold the same key), sets `key_path` to it and offers the same delete (not when the file imported is that copy). When `<KEY_ID>.cred` already exists, a failed encrypt fails the import: it never falls back to a plaintext file.

The daemon, `collied apns test` and doctor decrypt the credential each time they load the key.

**Seal.** An unprivileged caller cannot choose the key with `--with-key`: systemd's varlink service (`io.systemd.Credentials`, behind `systemd-creds.socket`) decides. It seals with the host key plus the TPM2 when a TPM2 is usable, the host key alone otherwise, and silently falls back to the host key alone if TPM2 sealing fails. So collied reads the seal from the credential header: the first 16 bytes after base64 decoding are the key type id (ids from systemd `src/shared/creds-util.h`, v261 and main). Doctor runs `systemd-analyze has-tpm2` only to warn that a host-only credential could now be bound to the TPM2. The dev machine (T2 Mac hardware) has no TPM2: host key only.

The first encrypt on a machine makes systemd create `/var/lib/systemd/credential.secret` (root, 0400). The credential stops decrypting after an OS reinstall, a machine-id change, a uid or user name change, or a restore to another machine: import again from the backup.

**Doctor** on Linux has no `codesign` line. Its `apns` line:

| State | Result |
|---|---|
| credential, host key | ok, "host key only (no usable TPM2)"; warn if a TPM2 is usable now (import again to bind it) |
| credential, host key and TPM2 | ok, "host key and TPM2" |
| credential, TPM2 only | ok, "TPM2" |
| credential, null key | fail, "null key, not encrypted" (integrity only) |
| credential, unrecognized seal | warn, "unrecognized seal" |
| credential missing or not decrypting | fail |
| `key_path`, systemd-creds works | warn: encrypt it with `collied apns import` |
| `key_path`, systemd-creds unavailable | ok: "0600 file fallback (systemd-creds unavailable): protected by its mode only" |

Whether systemd-creds works is a live probe, run only with `key_path`: doctor encrypts and decrypts a test value under the name `collied-apns-doctor-probe` (on a machine with no credential yet, that first encrypt makes systemd create the host secret). As on macOS, doctor then signs a provider token as a dry run and warns about any other `.p8` in `<data dir>/apns`.

**Storage difference.** Other unprivileged users cannot decrypt the credential, but any process of the same UID can, without a prompt: there is no per-application binding like the Keychain ACL that trusts only the Developer ID signed collied. Same-UID malware on Linux can read the key, not only use collied to send pushes. The 0600 fallback is protected by its mode only. Details: [threat-model.md](threat-model.md).

### `collied status`

On both OSes, `collied status` also prints `tags:` (`(none)` for an untagged node, `(not reported)` when the node status failed) and, when herdr answers, `agents: N` and one line per agent: status, name (else kind, else `agent`), workspace label (`?` when unknown), `terminal_id`, escaped for the terminal. The agents are what the phone would see: the daemon's herdr `session.snapshot`, mapped as for `flock.snapshot`. A flock too large for one control line is dropped and status prints `too many to list here`, so the status request, which is also the liveness probe, never fails on a large session. The control socket reply carries `tags`, `flock` and `flock_too_large`, all with serde defaults, so a newer CLI still reads an older daemon's reply.

## Apple Watch

- CollieWatch (embedded under `Collie.app/Watch`) and its CollieWatchWidgets complication hold no keys, never link CollieCore and never talk to collied. Everything goes through the phone over WatchConnectivity.
- Phone to watch: `updateApplicationContext(["state": WatchState JSON])`, sent only when it changes (a change to the agents alone only while the watch app is reachable, at most once a minute), from the app's 1 s poll loop once each machine has a snapshot or is known down, and on going to the background (then `live` is false). It carries at most 5 unexpired approvals (agent, place, the decrypted command, the snippet, Approve/Deny and menu choices, never Approve always, never a nonce), at most 30 agents as in the inbox, the newest Claude plan usage (5-hour and weekly windows), the newest Codex monthly reading, the newest Copilot monthly premium reading (percent used, capped at 100, whether the seat is unlimited, the reset and the reading time) and whether watch decisions are allowed. Texts are capped so it fits in an application context. Nothing is published from a background launch except a refresh's answer (below).
- Watch to phone: `sendMessage(["decide": {nodeId, approvalId, decision}])`, which wakes the iPhone app; the reply is `{title, body, answered}`: the follow-up text, and whether the watch need not offer the approval again (false when nothing reached collied). The watch first passes `deviceOwnerAuthenticationWithWristDetection` (a fresh `LAContext` each time).
- The phone (`AppModel.decideFromWatch`) re-reads `watchDecisions` from `prefs.json` on every request (off by default; turning it on needs `deviceOwnerAuthentication`), and decides only an unexpired approval, with an answer, that is in the last application context it sent (`WCSession.applicationContext`). Then it takes the lock-screen path, `decide_from_notification`, so the nonce, expiry, replay and fingerprint checks on the machine are unchanged.
- Watch refresh: `sendMessage(["refresh": true])`
  - When: the watch app becomes active (at most once a minute after the phone answered with its state, even with a Mac that did not: each such refresh of a locked phone runs up to its 15 s budget, so approvals from a Mac that comes back can reach the watch up to a minute later), opens from an alert, or receives an approval alert while in front; and from a background app refresh (`.backgroundTask(.appRefresh)`) the app schedules 15 minutes ahead on going to the background and at the start of each run, which watchOS may delay or skip. That one has the same once-a-minute limit and gives up after 20 s instead of 25 s, keeping the last state.
  - In the foreground the phone publishes and answers with its state. Otherwise (`AppModel.refreshForWatch`) it calls collie-core `approvals_in_background` (15 s budget): the lock-screen path's node start and pinned one-shot session per paired Mac, `approval.list` only, whose reply also carries the Mac's plan usage. The new approvals replace the last shown ones (a Mac that did not answer keeps its own), the newest listed plan usage replaces the last shown one (and a Mac's cached plan when newer, so the app's return does not publish the older plan before its next snapshot), the agents stay as last shown, `live` is false, and the result goes out as the application context, so decisions check it as usual.
  - The reply is `{state, silent}`, `silent` naming the Macs that did not answer; with no reply in 25 s the watch keeps what it has. With no reply, or a Mac that did not answer, it says it could not refresh. A failed `updateApplicationContext` gets no state in the reply.
- The watch app is the `UNUserNotificationCenter` delegate on the watch and registers `APPROVAL` without actions. Any response to an alert carrying `node_id` and `approval_id` opens that approval's detail (read-only unless watch decisions are on) after a refresh; nothing decides from an alert.
- Usage complication (`CollieUsage`): the watch app writes the plan usage to `watch-usage.json` in its own App Group container and reloads the complication.
  - `accessoryCircular`: four concentric rings, outer to inner, Claude 5-hour, Claude weekly, Codex monthly and Copilot monthly premium usage, all the same stroke width. Each fills clockwise from noon with percent used, colored on a smooth scale (bright green at 0%, yellow at 60%, orange at 80%, red at 90%, deep red at 100%). An unlimited Copilot seat shows a track with no fill, and "Unlimited" where the others show a percentage or countdown.
  - `accessoryRectangular` (Smart Stack and rectangular face slots): three `.accessoryCircular` gauges side by side, Claude, Codex and Copilot, each holding its logo. The Claude gauge is two half gauges split at the top: the 5-hour window fills the left half upward from its lower end and the weekly window, mirrored, the right half, each with its own color and elapsed tick, and their one-unit countdowns below their halves; VoiceOver reads each half as its own element. Codex and Copilot show their reset countdown below. The gauges share the rings' color scale and dim the unused arc.
  - White ticks mark elapsed time against used allowance, so fill beyond a tick means usage ahead of an even pace. The Codex and Copilot intervals start one calendar month before their reported reset, in UTC; the phone's Codex usage bar marks the same elapsed month.
  - Configuration: an `AppIntentConfiguration` with `UsageAgentsIntent`, three Bool parameters (Claude Code, Codex, Copilot), all on by default; `recommendations()` returns an empty list, which watchOS 26 takes as letting the owner edit the parameters from the watch face editor, the Smart Stack or the iPhone's Watch app. Each placed widget keeps its own values. The rectangular family shows only the chosen gauges, in order and at the three-gauge size, centered; the circular family shows only the chosen rings (two for Claude), outer to inner with the same spacing, and VoiceOver reads only those. With all three off, both show all three. The watch app's Usage list always shows every window.
  - Freshness: Claude, Codex and Copilot source timestamps travel independently with their readings; absent timestamps count as stale. A stale rectangular reading shows an orange dot beside its countdown; a missing or expired one shows a dim gauge with "No data" below. Missing circular tracks are dim and dashed, with `--` in the center when every shown ring is unavailable. A reset dims that ring until fresh usage arrives. The watch stores the time of the last successful phone receipt separately, so old data never makes its source timestamp fresh.
  - Timeline: elapsed-time markers every five minutes in one-hour batches, with entries at stale transitions and resets within that horizon, at most 19 entries per batch so watchOS never archives a full day of rectangular layouts at once. At the end it requests another timeline from cached data; empty or expired timelines retry after 15 minutes. Snapshot requests outside the widget gallery also read cached usage; sample values are for previews only. The watch republishes cached usage and requests a reload when opened or when it receives unchanged usage, at most once a minute; changed usage reloads at once. Usage colors update with any refresh or received context, including the background refresh. A failed cache write stays eligible for retry.
  - Both families link to `collie-watch://usage`, which opens a details screen with percentages, exact reset times, reading ages and the last phone sync. Its cards use watchOS 26 Liquid Glass inside a shared `GlassEffectContainer`, in a stable outer scroll view that keeps touch and Digital Crown scrolling.

## Client runtime

- One connection supervisor per paired machine in collie-core, each with its own backoff, request queue and link state, so a machine that is off affects only its own section.
  - Backoff 3, 4, 8, 16, 30, 60 s, reset after 30 s connected. While the phone's tailnet is offline it waits, re-checking every 3 s and at once when the node first reaches Running.
  - Auth failures stop the link; the next resume or manual retry dials again and checks everything, so a transient failure never strands a link until a relaunch. Only a known, wrong self identity is a self-ownership failure: a tagged self node, another user than the paired owner, an own-address whois naming another node or user, or a self node with a positive user and StableID but no Tailscale address (all three come from the same netmap self node). A self node without a positive user or StableID, or a failing own-address whois (a node restarted after a suspend answers "peer not found" from its netmap disk cache until control sends the live map), is retried like a failed status call.
  - A protocol version mismatch also stops, saying which side to update (collied sends its version in `unsupported_protocol`); requests meanwhile fail at once with that message, and the next resume or manual retry dials again, so an update needs no new pairing.
  - A machine the netmap reports offline is not dialed, since a 20 s dial to a dead peer occupies the node every machine shares. Its link is `Unavailable` ("offline", with the asleep reason below), re-checked locally after 3, 6, 12, then every 15 s (every 3 s for 30 s after a resume, and from 3 s again after any other outcome), dialed once online, and dialed anyway every 15 min in case control is wrong. Pairing, lock-screen decisions and each reconnect request (a resume or a manual retry) dial regardless, once, since the netmap can be stale right after a resume; an attempt that ends before the dial (failed status call, phone key not loaded) does not use that dial up.
  - A session that receives nothing for 45 s (collied pings every 15 s) ends as a timeout and reconnects, so a machine that slept or lost power does not stay Connected.
  - On foreground after 10 s or more in the background, reconnect at once (iOS suspends sockets without a close); shorter gaps get a 3 s probe. For 10 s after a resume, failures (the old session's close, a node rebuilding its paths or not yet running) retry after 0.5, 1, then 2 s with the link kept Connecting and no error shown; a failure from just before the resume is cleared and retried at once, the normal backoff restarts, auth failures still stop at once, and later failures use the normal backoff. A snapshot request cut off by the reconnect answers from the cache. A resume also moves an `Unavailable` link back to Connecting and dials it at once.
- Manual retry (`reconnect(machine_id)`): pull to refresh on the Agents list retries every machine, a tap on a machine's header retries that one. A live session gets the 3 s probe; any other link is dialed at once, past the offline flag.
- Offline reason: a link that is not connected carries an `OfflineReason` on `MachineFlock` for the cases the phone can tell apart from what each attempt already reads (the node's status, then the dial), with no extra polling. The link phase keeps the pill ("offline", "retrying"); the reason is the sentence under it.

  | Link | Detected by | Reason shown |
  |---|---|---|
  | `Offline` | the phone's node is not `Running` (or not started) | "This phone is not connected to Tailscale. Sign in again or check the network." |
  | `Unavailable` | the netmap reports the machine's node offline | "\<machine> is asleep or off. Last seen \<time> ago.", from the peer's `LastSeen` in the node's status; without one, or with Go's zero time, the last sentence is left out |
  | `Waiting` | the netmap reports the machine online and the dial is refused (`connection was refused`) or runs out its attempt (`context deadline exceeded`) | "\<machine> is online, but collied is not answering. Run collied start there." |
  | `Waiting` | any other dial error, including a dial forced past the offline flag | "Cannot reach \<machine>." |

  TLS, pin, hello and version failures carry no reason and keep their own messages. The classification reads libtailscale's error text, which a concurrent failure on the same node can replace (`check_unlocked` in the tailnet crate), so at worst a reason names another dial's cause. A dial to a machine that just powered off can also read as not answering until control marks it offline. The reason clears when the link goes back to Connecting, on an attempt or a resume.
- Connection errors appear in the Machines tab in a compact glass card, without a disclosure row: centered footnote text shows the offline reason, or the error itself when there is none, and a small glass clipboard button (44-point hit target) copies the full error without navigating or retrying; copying briefly swaps the icon for the green Done checkmark, without a visible label. The Agents layouts keep their connection status indicators and show only the offline reason, or a version mismatch saying which side to update, under a machine's section header. Debug terminal demos take `COLLIE_DEMO_CONNECTION_ERROR` to show these errors without a live machine.
- The Agents tab reads the core's cache every 3 s, which `agent.status` events keep current, and every 0.25 s while a machine waits for a dial or its first list, or for the node during the 20 s after the tab appears (an offline link with no error can also be a node that never runs, logged out or with no network). These fast reads touch the cache only: a machine whose last read failed is left to the 3 s read. The tab asks connected machines for `flock.snapshot` when it appears, on pull to refresh, after a close and every 60 s, which covers shells (no event lists them) and an older collied that sends no title changes. When reconcile first finds herdr unreachable, collied sends `flock.changed`; the refetch fails with `herdr_unavailable`, which collie-core keeps on the link's view until a snapshot works, so the list shows the outage and asks for a snapshot every 3 s until it ends.
- Node recovery, for a node whose paths died while the app was suspended. On cellular, carrier NATs silently drop idle UDP mappings and TCP state, so the home DERP connection looks open until its 120 s read deadline. On any network iOS can defunct the node's UDP sockets, after which wireguard-go's receive loop for them has exited (health "The MagicSock function ReceiveIPv4 is not running"); a rebind replaces the sockets without restarting the loop, so the node receives only through DERP until restarted.
  - Rebind: after a resume from a suspend or 10 s or more in the background, if no machine is connected 3 s later, the node is rebound (`tailscale_rebind`). Not sooner: a dial in flight during a rebind can stall for its whole 5 s attempt, and a healthy reconnect takes well under 3 s.
  - Restart: if no machine has connected 10 s after the resume while the node reports Running and a machine still dialing or failing is online (or the node cannot report status), and on a manual retry while dials fail, the node is restarted as a relaunch would: taken out of the slot, closed once only dial attempts hold it (a lock-screen decide holds it until answered), then a new node starts from the same state and every link redials. The close fails a dial in flight at once, so a restart does not wait out its 5 s; a link failed that way, or waiting for a node start, shows connecting rather than an error or offline. Measured with the phone on the Mac's Wi-Fi: every reconnect that came at all did so within 7 s of the resume, rebind included, while a node the rebind did not help stayed unreachable until a restart or relaunch, which connected within seconds.
  - Immediate restart: a node with the receive-loop warning is restarted at once, without the rebind or the 10 s wait, when a dial to a machine Tailscale reports online had already failed on it before the resume and nothing is connected, or when such a dial fails past the resume grace in the foreground. Measured on Wi-Fi: most resumes with the warning still connected within a second through DERP, but once a dial to the online Mac had failed, nothing connected until a restart, and waiting 10 s on each resume meant a short visit never got there.
  - Requests queued meanwhile wait for the new node. The old node is put back instead when a machine connects in the meantime (no session is cut) or the app is suspended (a waiting lock-screen decide gets it at once); a restart whose node another restart already replaced does nothing. The restart holds the node-start lock, so a waiting lock-screen decide gets the new node and two nodes never share the state dir. If the new node cannot start, the restart tries again at once, then the next resume or manual retry does.
- Network changes: the app watches the path with `NWPathMonitor` and reports the interface it routes through (Wi-Fi, cellular or wired, never a VPN tunnel; empty with no path) with `network_changed`; the first report is only recorded. On a move to another interface, or back after no path, once the path has held 1 s (it can flap at the edge of Wi-Fi), the node is rebound with the new interface. A live session then gets the 3 s probe and is redialed only if it fails: its TCP runs inside the node and survives the move once the node reaches the machine again, but iOS reports no error when it does not, so it would otherwise last until the 45 s silence limit. Every other link is redialed past the offline flag with the resume grace. If nothing connects within 15 s (three dial attempts) while the node reports Running and a machine still dialing or failing is online, the node is restarted as above. That check, like the 10 s one after a resume, is dropped when the path changed or a resume came since, and restarts only the node its flow started with. A move reported while the core is suspended rebinds the node at once, so a lock-screen decide binds to the new interface, and the redial waits for the next resume. A Wi-Fi network replaced by another on the same interface without a gap is not seen as a move.
- Diagnostics: each resume writes one line to the device log (subsystem `dev.rbstp.collie`, category `core`) with the background time, whether the core was suspended, the node's backend state and health warnings, and per machine the link phase before the resume, the time since its last dial, its last error and whether the netmap reports it online. Each path change is logged (`network path: en0 to pdp_ip0`), and rebinds and restarts with their reason and outcome; a restart logs when it closes the old node and how long it waited for its holders, then how long the close took. No keys, tokens or nonces.
- Snapshot plus sequence: `flock.snapshot` returns the `seq` it reflects; every event frame carries `seq`; the client drops `seq <= last applied`; unknown events still advance the cursor.
- Mutations are never replayed automatically, except a prompt to an unreachable machine: up to 5 attempts a minute apart (at once when the link reconnects while its agent screen is open), none later than 270 s after the first.
  - The app holds one prompt per agent from its first attempt, in memory only, so resends continue after the screen closes until the app process ends, and stop when the machine is removed. A screen opened meanwhile shows it with its spinner, even over text loaded from the machine's box; editing it, tapping the spinner, the agent exiting, or a different prompt sent from that screen stops it (the new one waits for any attempt in flight). If it ends without arriving and no screen shows it, it returns to the agent's saved draft with a one-time "may not have been sent" note. The agent's last prompt is compared only when read with the link up. Not detected: a new agent started in the same pane before the resend would receive it.
  - Each retry is `resend_prompt`, which collie-core sends only under the `op_id` an unanswered identical prompt still holds (kept 300 s of wall time from its first send; collie-core reports `Unreachable` only while it holds it) and otherwise refuses with `NotResent`, sending nothing; only the user's Send mints an `op_id`. collied replays an attempt that arrived instead of typing the prompt twice. Its outcome cache lives in memory for 600 s, so a collied restart forgets the `op_id`; before each retry the phone treats the prompt as sent when the agent's last prompt changed to its first line, which covers most of that case.
- Lock-screen approve and deny over an authenticated tailnet session has no prior art; the flow is under [Lock-screen approval](#lock-screen-approval), and its timings still need measuring on device.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| libtailscale has no git tags and lags tailscale.com releases | security updates can be ours to carry | pin SHA + patch series; track upstream (0.2.0 at `d1dc45d`) |
| Peer attribution race in `getremoteaddr` (fixed upstream in 0.2.0) | wrong peer authorized | `tailscale_accept_with_addr` (patch 0002); never call `getremoteaddr` |
| Go runtime size | ~20 MB per binary (iOS stripped), ~25 MB collied | measure per slice; Go archives built with `-w` |
| Cold start in a background launch | Approve from lock screen fails | tsnet state cached, node started from cache (never a login), 20 s budget cap, follow-up local notification on every outcome; measure on device |
| Suspend/resume leaves stale DERP/magicsock state | slow reconnects | re-dial on foreground, forced past a stale offline flag; rebind when nothing reconnects within 3 s; node restart when nothing connects within 10 s, at once when its UDP receive loop has stopped and a dial to an online machine fails; resume diagnostics in the device log |
| Wi-Fi to cellular leaves the node bound to the old interface | no reconnect until a relaunch | `NWPathMonitor` feeds the interface to the node; on a move: rebind with a netmon refresh once the path holds 1 s, live sessions probed and other links redialed, node restart when nothing connects within 15 s; path changes in the device log |
| herdr server load (status entry polls `pane.get` every 100 ms) | CPU with many panes | measure; fall back to `agent.list` polling if needed |
| UniFFI + Swift 6 | build friction | bindings compile in Swift 6 language mode; no async foreign traits on hot paths |
| APNs `.p8` is team wide | leak allows pushes to every app on the team | dedicated revocable key per machine; on macOS a Keychain item whose ACL trusts only the Developer ID signed collied; on Linux a systemd user credential, which any same-UID process can decrypt; payload never carries the nonce; limits in [threat-model.md](threat-model.md#same-uid-malware-on-the-mac) |
| APNs payload transits Apple | project names exposed | all alert and initial/update/end Live Activity display content is authenticated ciphertext; public generic text, opaque IDs, urgency, lifecycle, timing and size remain visible; nonces and decisions stay over the tailnet |
| Answering a blocked prompt outside approvals | bypasses nonce/expiry | collied refuses prompts while `blocked`; keys and typed answers reach a blocked agent only over the paired session, with authorization re-checked before each write; audited |
| Prompt delivered after agent exit | prompt runs as a shell command | foreground check before send; conditional input in herdr upstream |
| Retried mutations | duplicate prompts/tasks | `op_id` outcome cache |
| A paired phone writes files on the Mac | disk use, files an agent may read | size, rate, in-flight, 200 MiB and 1000 entry caps; private 0600 non-executable files in a 0700 cache dir; 24 h retention; [threat-model.md](threat-model.md#attachment-uploads) |
| Older app vs newer collied | decode failures | additive events/errors/statuses decode to `Unrecognized`; anything else bumps `PROTOCOL_VERSION` |
| Shell input from a paired phone | command execution as the user | off by default, `collied.toml` only; its own method class; a grant signed by a Secure Enclave key behind Face ID, per terminal, session and 5 minutes; the pane re-read before every write; audited without the text; [threat-model.md](threat-model.md#shell-input-from-the-phone) |

## Release sample workspace

Welcome and Settings open a clearly labeled, bundled sample workspace in Debug and Release builds. Its label and Exit button sit in the tab bar's bottom accessory, so its Agents screen reaches the top of the screen like the real one. Its core is a synthetic in-memory implementation of the agent and approval interfaces, with no daemon, relay, pairing or network client. Prompts, terminal input and approval decisions append visible local results. The sample authenticator is private to the view that constructs this core; real approvals keep device-owner authentication. The sample creates no Live Activities or push registrations.

Reset replaces the sample session and Exit dismisses it. Sample screens suppress persistence and cache pruning for real preferences, agent drafts, viewed changes, inbox markers, snoozes and layout order. New task is disabled in the sample. ## Desktop distribution

Desktop releases (collied for macOS and Linux, CollieBar, CollieTray) share the TestFlight version tag and exact source commit. TestFlight dispatches the desktop workflow from master with that tag and SHA, so the master-only signing environment accepts it; a protected master-only manual dispatch also publishes. One publisher owns each release: it rejects moved tags and mismatched source markers, keeps already uploaded signed packages when a draft is retried, and verifies a completed release without replacing its assets.

- macOS (26+, Apple silicon) packages are Developer ID signed, hardened and notarized; the daemon disk image and CollieBar are stapled, and the publisher and the installer check the daemon's strict signature and notarized requirement (an online ticket lookup). Linux x86_64 packages are built on Ubuntu 24.04 and checked against a glibc 2.39 floor. CollieTray is an architecture-independent Omarchy 4 Quickshell plugin.
- The packaged installer (`install.sh --replace`, or Homebrew's `collied-install --replace`, never run automatically) copies the daemon to a fresh regular `~/.cargo/bin/collied`, the path setup requires, and updates only the executable of an existing launchd plist or systemd unit, keeping its config, environment, data and stopped or running state. Linux packages may instead own a regular `/usr/bin/collied`, which setup and doctor accept when it is the running executable. Package operations run no root hooks against user homes or sessions.

[Desktop release downloads](desktop-releases.md) has the assets, installation, AUR adoption, release controls and validation gates. No protocol change or version bump.

## Push relay

The Worker and D1 implementation under `relay/` provides a bounded authenticated send contract, fixed topics, deterministic provider JWTs and atomic indexed installation and global quotas. The production relay runs on Workers Paid, released builds deliver through it, and an hourly Cron trigger runs its bounded retention cleanup. [relay.md](relay.md) has the contract, local measurements and retention bound. No version bump: no phone or daemon wire type changes.

## Attested push control validation

The relay authenticates installation enrollment with Apple App Attest (the pinned attestation root, and the CMS receipt checked independently against Apple Root CA G3) and later operations with assertions over a stateless five-minute HMAC challenge bound to the operation, exact destination, pairing, installation, environment and prior counter and epoch. One D1 transaction advances the replay and control counters and changes routes; a conditional zero-row update alone never authorizes a route. Registered generations and revocation epochs are checked on every send, and APNs expired or unregistered destinations revoke only the matching generation and destination.

The Swift client serializes control transactions across suspension points, keeps credentials in a ThisDeviceOnly Keychain record, pins the publisher endpoint and keeps pending offline revocations. It enrolls only for a paired daemon that reports relay mode through the negotiated capabilities; the daemon persists bounded redacted grants privately and reports its actual sender mode, so direct senders never trigger enrollment. [relay.md](relay.md#attested-control-contract) has the contract, limits, renewal and retention. No version bump: optional `relay_grant` registration fields are sent only with the implemented `relay_grants_v1` and `encrypted_display_v1` capabilities, the optional server-to-phone hello `push_mode` is omitted without relay negotiation, revision 26 remains the codec, and older peers never receive new request fields.

The isolated Free-plan benchmark failed the CPU gate for full App Attest verification, so production runs on Workers Paid with the single internal crypto actor and a provisional shared 250 ms CPU ceiling ([validation report](reviews/relay-free-tier.md)).

## Internal relay crypto prototype

Apple verification and APNs signing run in one internal SQLite Durable Object, separate from the public HTTP policy and D1 state. The actor derives verification policy from trusted deployment bindings, has no public HTTP handler, stores no application data and uses one fixed name; missing or exhausted compute fails closed, with no inline fallback. Shared per-location control and enrollment admission limits repeated verification from rotating sources; it is not a global spending cap. Local real-actor tests do not establish deployed Free-plan viability. See [relay.md](relay.md#internal-crypto-prototype). No version bump: the public relay and phone-daemon wire contracts are unchanged.

## Simulator relay isolation

The local Simulator relay ([simulator.md](simulator.md)) provisions a software P-256 identity into a private local D1 and a DEBUG Simulator container, through a separate entry that refuses enrollment and fixes sandbox APNs. Everything after it (control proofs, route commits, encrypted payloads, quotas) uses the production validators and, in a Miniflare harness, the production `RelayCrypto` class. Production has no local key, local send secret, synthetic enrollment verifier or unsupported-attestation fallback, its Worker graph excludes `relay/dev`, and a separately seeded development database never counts as evidence of production trust. The Swift identity import and mock destinations compile only for DEBUG Simulator, the daemon's loopback sender switch only with debug assertions, and the exact loopback ATS exception only into DEBUG Simulator bundles; Release uses the fixed HTTPS publisher endpoint. No protocol change or version bump.

## Isolated VM and Simulator tailnet

The [VM procedure](vm-simulator.md) runs the Debug daemon in an owned macOS guest and the Debug iOS Simulator on the host, with an account-free testcontrol server, DERP relay and mock publisher on host loopback, reverse-forwarded over task-key SSH to guest loopback ports 8788 to 8790 (each side runs its own STUN server on 8791). No owner Tailscale account, APNs key, home directory or Keychain enters the guest.

`COLLIE_VM_TEST=1` works only in Debug macOS and Debug iOS Simulator Rust builds. It requires a private `collie-vm-test` directory and a bounded private, non-symlink `vm-tailnet.json` with a synthetic test auth key, fixes the control URL at `http://127.0.0.1:8789`, and selects a separate data directory, state folder and Keychain namespace. The Simulator checks the Debug capability symbol before initialization, so a Release-profile core fails closed. Pairing pins, mutual TLS, owner checks, registration and relay proofs run their normal code, and the harness confirms only its expected candidate at the daemon's ordinary prompt. Release and physical-device artifacts exclude the test entry. No protocol change or version bump.
