# Threat model

Scope: collied on the Mac or on a Linux machine, Collie.app on the iPhone, the tailnet between them, herdr as collied's local backend, and APNs. On Linux collied runs as a systemd user unit. Both computer and phone use independent user-owned embedded Tailscale nodes without an OS VPN profile. Tailnet configuration is in [tailnet.md](tailnet.md), design in [architecture.md](architecture.md).

## Assets

| Asset | Where |
|---|---|
| Control of every shell and agent on the computer | herdr socket (0600, no auth: same UID means full control); reachable from the phone only through collied's allowlist |
| Mac node keys | `~/Library/Application Support/collie/tsnet` (0700) |
| Linux node keys | `<data dir>/tsnet` (0700), data dir `$XDG_DATA_HOME/collie`, else `~/.local/share/collie`. Separate from a system tailscaled's state (`/var/lib/tailscale`): the embedded node is its own device with its own keys |
| Phone node keys | app container `Application Support/collie/tsnet` (0700, `completeUntilFirstUserAuthentication`, excluded from backup) |
| Machine TLS key (proves the machine to the phone) | `tls-key.json` in collied's data dir (P-256 PKCS#8, 0600, made on first start, read only as a regular file, not a symlink, owned by the user with no group or world access); its pin in the pairing QR and the phone's `machines.json` |
| Phone TLS key (proves the phone to collied) | the phone's Secure Enclave: a P-256 key, non-exportable, `.privateKeyUsage`, `AfterFirstUnlockThisDeviceOnly` and no user presence, so lock-screen decisions can connect; collie-core gets a signing callback, never the key; its pin in `peers.json` (`tls_key`), recorded when the pairing is confirmed |
| Pairings (`StableID` list) and the owner user ID | `peers.json` in collied's data dir (0600); optional `owner_user_id` in `collied.toml`; the same positive user pin in the phone's local `machines.json` |

| Live Activity update tokens | collied's `push.json` (0600) next to the device token, bound to the device's `StableID`; collie-core memory. Never logged, audited or written to disk on the phone; redacted in `Debug` |
| Notification keys (32 bytes, one per paired Mac) | iOS Keychain (`dev.rbstp.collie.notify`/`<Mac node ID>`, `AfterFirstUnlockThisDeviceOnly`, shared with ColliePush); a mirror file per Mac in the App Group container (`notify-keys/<node ID>.key`: 0600, `completeUntilFirstUserAuthentication`, excluded from backup), because a Live Activity renders in a process with no Keychain (`errSecNotAvailable`) and needs the key to show the command; collied's `push.json` (0600) next to the device token; collie-core memory. Never logged, audited or written elsewhere; redacted in `Debug`. The mirror is weaker than the `ThisDeviceOnly` Keychain item against a jailbroken or forensically imaged phone (user decision, 2026-10-03) |
| Terminal content, agent and workspace names | herdr, the tailnet session, the phone |
| Agent transcripts (whole conversations, tool output) | Claude Code's `~/.claude/projects/*/<session>.jsonl` (or under `CLAUDE_CONFIG_DIR`) and Codex's `~/.codex/sessions/YYYY/MM/DD/rollout-*-<session>.jsonl` (or under `CODEX_HOME`), 0600, written by the agents; collied reads them and keeps only values derived from them, in memory |
| Plan usage and context window sizes | collied's `usage.json` (0600) in the data dir, written from Claude Code's status line input and the local Codex app-server: Claude's 5-hour and weekly limits, Codex's monthly used and allowed credits and reset date, and up to 64 Claude session ids with their window size; collied memory. Codex handles its OAuth token; collied keeps none of it. |
| Terminal key (signs terminal grants) | the phone's Secure Enclave: a P-256 key apart from the TLS key, non-exportable, `.privateKeyUsage` and `.userPresence`, `WhenPasscodeSetThisDeviceOnly`, so every signature needs Face ID or the passcode and removing the passcode destroys it; its public key in `peers.json` (`terminal_key`), recorded when the pairing is confirmed on the machine, and in the phone's `machines.json` |
| Terminal challenges and grants | collied memory only, per session: one challenge (32 random bytes, 60 s, single use), grants per terminal for 5 min. Never logged or written to disk |
| Attachments (photos and files sent from the phone) | the phone; collied's attachments dir (`~/Library/Caches/dev.rbstp.collied/attachments` on macOS, `$XDG_CACHE_HOME/collied/attachments`, else `~/.cache/collied/attachments`, on Linux; 0700 dirs, 0600 files) for up to 24 h; the tailnet session |

## Trust boundaries

- **Tailnet to collied.** The only network entry point is the tsnet listener on TCP 8457. Every connection passes the whois gate (untagged, not shared in, owned by the positive embedded self user bound before listening, paired `StableID` with its paired user and a pinned TLS key, or an open pairing window), then mutual TLS against the key the gate pinned for that peer (any P-256 key in a pairing-only session), then the same gate again under the peers, pairing and sessions locks, which must reach the same decision (a pairing or revoke during the handshake refuses it), all before the WebSocket upgrade; then a fail-closed method allowlist (`parse_client_frame`: unknown methods rejected before params are decoded, unknown fields denied, herdr privileged methods unreachable). Terminal methods are their own allowlist class, refused with `terminals_disabled` unless `[terminals] enabled = true`, and need a grant signed by the phone's terminal key.
- **collied to herdr.** Same UID. Nothing on the computer running as the user is a boundary. On Linux the systemd unit's sandboxing is defense in depth, not a boundary against the same UID.
- **Tailscale control plane.** Trusted for node identity: whois and the phone's netmap check both come from it.
- **Apple.** APNs sees generic alert text, opaque identifiers, priorities, timing, size and activity lifecycle. All private alert and initial/update/end Live Activity display content is authenticated ciphertext.

User-owned computer nodes inherit their user's tailnet network privileges and normal key expiry. This removes the old tag-confined service identity: a compromised daemon can exercise whatever network access the user's full policy permits. Collie's mTLS and same-user admission protect its sessions, not unrelated tailnet resources. Neither embedded node installs an OS VPN profile or changes the native corporate Tailscale client's account, state or routes. Actual physical-device pairing, reconnect/background recovery and coexistence with an active corporate VPN remain required before App Store submission; static source and local control tests do not establish those outcomes.

## Threats from the spec

### Stolen phone

| | |
|---|---|
| Assets | Paired session (read and control of agents); phone node keys |
| Attack | Thief opens the unlocked app, or unlocks the phone, and drives agents or answers approvals. |
| Mitigations | iOS passcode and data protection on the node state (built). Revocation: `collied peers revoke` plus removing the node in the admin console (built, [tailnet.md](tailnet.md#revocation)). Phone node key expiry (Tailscale default 180 days) bounds a forgotten revocation. Closing a pane or a workspace needs `confirm: true`, else `confirm_required` before herdr is called (built); the phone sets the flag itself, so it guards against an accidental close, not against a thief. Every frame is rate limited per paired `StableID` (20/s, burst 40; `attachment.chunk` frames have their own bucket, 128/s) and every method other than `hello`, `flock.snapshot`, `approval.list`, `attachment.chunk`, `attachment.abort` and an issued `terminal.challenge` is written to the audit log (`server.rs` `finish`; a refused challenge is logged); of a run of frames over the limit only the first is logged, as `rate_limited` (built). Approvals: in-app decisions need LocalAuthentication (`deviceOwnerAuthentication`, fresh context per decision), lock-screen actions need an iOS unlock (`authenticationRequired`), `approval.decide` is limited to 1/s, burst 5, per `StableID`, and every attempt that passes the frame limit is audited (built). Terminals (off by default) need a grant that collied verifies, signed by the Secure Enclave terminal key, which signs only after Face ID or the passcode (built). |
| Residual | Until revoked, an unlocked phone drives agents (prompts, keys, new tasks, closes) without any per-action check, and an agent can run any command: only approval decisions and terminal grants ask for Face ID or the passcode, so the terminal grant does not make the phone as a whole safer against a thief holding it unlocked. A thief who knows the passcode passes both approval gates and the terminal grant. |
| Phase | Revocation built. Approval authentication built. App-level gate for the other drive methods: not planned. |

### Leaked pairing QR

| | |
|---|---|
| Assets | Pairing code, Mac tailnet node name, Mac `StableID`, the pin of its TLS key (public) |
| Attack | Someone photographs the QR, or copies it or the invite URI (printed next to it by `collied pair --show-uri`) from terminal scrollback, a screen share or recording, or a herdr pane that other same-UID code can read. They then pair their own device. The menu bar app's pairing window shows the same QR. |
| Mitigations | The code alone grants nothing: the pairing session is only offered to an untagged, not-shared-in node (owned by the verified embedded self user, including before first pairing) and only while a locally opened window is active. One window at a time, 120 s; the first `pair.complete` from any connection burns it, right or wrong code. With the right code, collied shows the candidate's device label, node name, `StableID`, login name and user ID and asks y/N on the Mac, 60 s timeout. Code compared in constant time; carried in the URI fragment and redacted in `Debug` (built). The same-user gate applies even when a broader policy allows other users to reach port 8457. |
| Residual | An attacker controlling a node logged in as the owner (account compromise) can race the window at any time. Any node admitted to a pairing-only session can burn an open window (denial of pairing only). The QR in the menu bar app's window is on screen for the same 120 s, and screen recordings capture it like the terminal's. The QR drawn in the terminal, and the URI with `--show-uri`, stay in scrollback and screen recordings after the window closes; they are useless once burned or expired, but a capture read live during the 120 s is as good as a scan. Host name and node ID in the QR are not secret. |
| Phase | Built |

### Malicious herdr plugin on the Mac

| | |
|---|---|
| Assets | Everything on the computer (Mac or Linux); the phone's view of agents and approvals |
| Attack | herdr plugins are unsandboxed code running as the user with the full herdr CLI. A plugin can drive every pane directly, read collied's data dir (node keys, `tls-key.json`, `peers.json`, `.p8`; on Linux it also decrypts the APNs credential), drive collied's control socket, and write pane text that collied turns into approval snippets to mislead the phone. |
| Mitigations | None against the computer side: same UID is out of scope for file modes. Snippets are capped at 200 chars with controls, bidi and format characters stripped (built), so a plugin cannot inject escapes into the phone UI through them. Approval decisions only send `up`, `down`, `enter` or `esc`, never text from the pane (built). |
| Residual | Full compromise of the computer. A plugin can draw a fake but well-formed Claude Code menu in a pane and so show the phone a fake approval. It also controls the gate's inputs: it can rewrite `collied.toml` and `peers.json` (owner and paired `StableID`s), answer y/N over the control socket, and run collied's node and TLS keys elsewhere. A same-UID attacker can replace collied or its keys and bypass its application gate. Remaining network restrictions depend on the actual complete tailnet policy; broad grants can also admit other users. User-owned nodes are not confined service identities. |
| Phase | Built as far as it goes (see same-UID malware for the Keychain item's limits). Otherwise not planned (install only trusted plugins). |

### Compromised Tailscale coordination plane

| | |
|---|---|
| Assets | Node identity, which every collie authorization decision rests on |
| Attack | The control server (or a stolen admin account) adds a node with its own key and gives it the phone's `StableID` and the owner's user ID, or changes grants and ownership, or points the phone's netmap at a fake Mac. |
| Mitigations | Admin account protection (IdP, MFA) is the user's. collied binds the owner to its own positive embedded self identity before listening and pins phone `StableID` + user ID + untagged/unshared. The phone pins the same positive user + machine StableID + untagged/unshared, which stops casual misconfiguration but not a control plane that lies. The y/N prompt at pairing catches a new device only during pairing. Mutual TLS inside the tunnel, independent of Tailscale keys (built): the phone pins the machine's TLS key from the pairing QR, which is shown on the machine and so out of band, and collied pins the phone's Secure Enclave key, recorded when the pairing is confirmed. A node the control plane injects with the phone's `StableID`, or a fake machine in the phone's netmap, fails the TLS handshake. |
| Residual | Low: a lying control plane can still cut or delay traffic, and can learn which nodes talk. It cannot get a full session without the phone's Secure Enclave key, or pass as a machine without its TLS key. |
| Phase | Built (Phase 6). |

### Replayed notification

| | |
|---|---|
| Assets | Approval decisions |
| Attack | An old push (or a captured approval decision) is replayed to approve something again or something else. |
| Mitigations | The push payload never carries the nonce, only `approval_id` and `node_id` as lookup keys (built). A lock-screen action fetches the nonce over the tailnet (`approval.list`) from the pinned, paired Mac and decides there; the app validates both keys and trusts nothing else in the payload (built). Nonce: 32 random bytes, constant-time compare, burned by the first attempt past the rate limit, whatever its result, `approval_ttl` 10 minutes; a burned id answers `approval_already_resolved` (built). Every attempt that passes the per-peer frame limit, including replays and expired ones, is audited; a run of frames over that limit logs only its first, as `rate_limited` (built). Decisions are bound to a fingerprint and fail as `superseded` if the prompt changed (built). APNs `apns-expiration` is the approval's expiry, and the opaque terminal-derived collapse id makes a reissued alert replace the dead one (built). The `Nonce` type rejects malformed values and is redacted in `Debug` (built). |
| Residual | A replayed or stale push shows a notification whose `approval_id` no longer resolves: acting on it answers "no longer pending, nothing was sent". A fresh alert for the same terminal can follow each reissue while the agent stays blocked. |
| Phase | Built |

### Leaked APNs key

| | |
|---|---|
| Assets | `.p8` key (team wide), device tokens |
| Attack | With the key and a device token, an attacker sends arbitrary pushes to Collie (or, the key being team wide, to any app of the team) to phish the user. |
| Mitigations | Dedicated, revocable key, never in GitHub ([release.md](release.md)). On macOS it is stored in the login Keychain by `collied apns import`, which deletes the file after confirmation; the item's ACL lets only collied signed with the team's Developer ID (`just collied-install`) read it without a prompt; `collied doctor` warns about a `key_path` config (built). On Linux `collied apns import` stores it as a systemd user credential instead (or a 0600 file where `systemd-creds` cannot encrypt) and offers to delete the original; `collied doctor` warns about a `key_path` config when `systemd-creds` works; limits in [APNs key storage on Linux](#apns-key-storage-on-linux) (built). On both, `collied doctor` warns about a `.p8` left in collied's `apns` dir other than the configured `key_path` (built). Each machine uses its own key with its own key ID, so a key leaked from one machine is revoked in the portal without touching the others. Pushes carry no nonce and cannot create or decide an approval: `approval_id` and `node_id` are validated lookup keys, and a lock-screen action decides only what the pinned, paired Mac returns over the tailnet (built). |
| Residual | A leaked provider key can submit arbitrary original fallback text if the notification extension does not run. Without the notification key it cannot authenticate private display content, and the app rejects unauthenticated decision actions. A forged background push naming a genuine `approval_id` (16 random bytes, seen only by Apple, the paired devices and the Mac) can remove that alert from the phone; the approval stays pending in the app. Copies outside the Keychain or the systemd credential (the downloaded file before import, the password manager backup) are protected only by where they sit. |
| Phase | Built |

### Phone node key extraction

| | |
|---|---|
| Assets | Phone node keys, which pass the whois gate as the paired phone |
| Attack | Keys read from the device (forensic tools, jailbreak, exploit) or from a backup, then used from another machine. |
| Mitigations | App sandbox; state dir 0700 with data protection `completeUntilFirstUserAuthentication`, both set by `StateDirectory.swift`; collie-core refuses a state dir with group or world access or another owner (built). State dir excluded from backups, also set by `StateDirectory.swift` (built). Revocation and key expiry as for a stolen phone. |
| Residual | Node keys are files, readable after first unlock by code inside the app's sandbox. They no longer suffice: collied also requires the phone's TLS key, a Secure Enclave P-256 key that cannot leave the device (`ThisDeviceOnly`, usable after first unlock). Code running on the unlocked phone, inside the app's sandbox, can still use that key there. |
| Phase | Secure Enclave TLS key: built (Phase 6). Backup exclusion for the node state: built. |

## Threats from the design

### Same-UID malware on the Mac

| | |
|---|---|
| Assets | herdr, collied's data dir, the APNs key, the control socket |
| Attack | Any process running as the user controls herdr directly, reads node keys, `tls-key.json` and `peers.json`, uses the 0600 control socket. |
| Mitigations | None by design for herdr and collied's files: same UID already owns every shell. Data dir 0700, files and control socket 0600, control socket peer UID checked: these stop other local users only (built). On macOS the APNs key is the exception: it is a Keychain item whose ACL trusts only collied's designated requirement (Developer ID Application, team `RM3UT3MMSR`, identifier `dev.rbstp.collied`), and the binary is signed with the hardened runtime, so other programs cannot read the key bytes without a Keychain prompt (built). On Linux there is no such exception: any same-UID process decrypts the systemd credential with no prompt ([APNs key storage on Linux](#apns-key-storage-on-linux)). The systemd unit's sandboxing (`NoNewPrivileges`, `ProtectSystem=strict`, a system call filter and more) limits what a compromised collied can reach, but it does not constrain other processes of the same UID, and a user manager skips it where unprivileged user namespaces are unavailable (built). |
| Residual | Full compromise of the computer side. Stolen node keys and `tls-key.json` let the malware impersonate the computer to the phone and show fake state or fake approvals. It can report a tool call through the control socket's hook request that differs from the dialog, so the alert names another call; the decision still binds to the screen's fingerprint, and the in-app approval also shows the screen's snippet. It controls the gate's configuration (`collied.toml`, `peers.json`) and can answer the y/N prompt, so the gate no longer protects anything; other users' devices are kept out only by the tailnet policy, which needs the admin account to change. Keychain ACL limits (macOS): malware can raise a prompt that the user may accept; anyone with the login password can change the ACL or export the item; it can run the signed collied itself (its own `--config` or `HOME`) to make it send pushes with the key, so it can push through collied without holding the key; a `key_path` config or an un-deleted `.p8` gets none of this protection. On Linux the malware reads the key itself and can push from anywhere until the key is revoked. |
| Phase | Built (Keychain item, systemd credential). Otherwise out of scope. |

### Menu bar app

| | |
|---|---|
| Assets | The invite (pairing code) while its QR is shown; the y/N decision on a candidate phone; the state of collied |
| Attack | Another app or a stray click approves a phone in the app's pairing window; the invite leaks from the app; phone-provided strings disguise the candidate; the app becomes a way in from the network. |
| Mitigations | The app is a local client of the 0600, same-UID control socket only, with the CLI's requests plus a read-only `watch`; it opens no network listener. Developer ID with the hardened runtime and no entitlements. The invite is never shown as text, copied, logged or persisted, and window restoration is off. Pair is not the default button and is live only 1 s after the candidate appears; one answer per candidate, never automatic; collied refuses after 60 s. The candidate's strings are escaped like `collied::printable` (controls, format and bidi characters, combining marks, default-ignorable characters and non-ASCII spaces). Closing the window cancels the pairing. First-run Set Up opens only the fixed installed regular executable in the system Terminal, through a private self-cleaning command file with a quoted literal path. The CLI still checks its installed path and signing identity. Interactive login opens only the exact Tailscale HTTPS login authority, once; browser failure leaves the printed fallback (built). |
| Residual | Same-UID code can drive the control socket or the app itself, as under [Same-UID malware on the Mac](#same-uid-malware-on-the-mac): it can already answer the y/N prompt. The QR is on screen for up to 120 s, like the terminal's. |
| Phase | Built |

### Bar widget (Linux)

| | |
|---|---|
| Assets | The invite while its QR is shown; the y/N decision on a candidate phone; the state of collied |
| Attack | A stray click or key approves a phone; the invite leaks into argv, a file or the shell's log; phone strings render as rich text or disguise the candidate; the audit log is edited through the viewer; the widget becomes a way in from the network. |
| Mitigations | A plugin of the Omarchy shell, a local client of the 0600, same-UID control socket only, with CollieBar's three requests; no listener, no network access, no change to collied. The invite reaches `qrencode` on stdin only and is never logged or shown as text; the QR is dropped with the pairing, but qrencode's output, which encodes the one-time invite, stays in the shell's memory until the next pairing. Pair is bound to no key, is live only 1 s after the candidate appears, and sends one answer; collied refuses after 60 s; closing the panel cancels. Phone strings are escaped like `collied::printable` and drawn as plain text. Commands run by argv, never a shell string. The audit log opens in `less` with `LESSSECURE=1` (built). |
| Residual | Same-UID code can drive the control socket, the shell or the plugin files under `~/.config/omarchy/plugins`, as under [Same-UID malware on the Mac](#same-uid-malware-on-the-mac). Any other shell plugin runs in the same Quickshell process. The QR is on screen for up to 120 s. |
| Phase | Built |

### `collied setup`

| | |
|---|---|
| Assets | The y/N decision on a candidate phone; the launchd agent or the systemd user unit; `collied.toml` and the APNs key |
| Attack | Setup runs with piped input (`yes` into it) so a pairing is confirmed without a human; it installs an unsigned agent, or a service running a build output; it leaves the key or config readable; on Linux it logs in a new node over the paired one. |
| Mitigations | Refuses unless stdin is a terminal and the binary is the regular `~/.cargo/bin/collied`, or the regular package-owned `/usr/bin/collied` on Linux, on macOS also Developer ID signed as `dev.rbstp.collied`, before any step: the service then never points at a build output that the next `cargo build` replaces unsigned. Never confirms a pairing: it runs the `collied pair` flow, whose `y` follows a `tcflush`. Reuses `service install` and `apns import` (Keychain, read back, offer to delete the `.p8`); a new `collied.toml` is created 0600, an existing one is rewritten atomically keeping its mode (`[apns]` holds no secret, the key is in the Keychain). It changes no bind, gate or pairing rule, refuses to drop the `--config` the service runs with, and stops on any doctor fail line, `listen` included (built). On both, `~/.cargo/bin/collied` must be a regular file, so a symlink cannot point the service at a build output. On Linux there is no signing: it accepts the regular `~/.cargo/bin/collied` or `/usr/bin/collied` matching the current executable, writes the unit through `service install` (0644, no secret, `UMask=0077`), and imports the key through `apns import` (systemd credential, or the 0600 fallback, read back, offer to delete the `.p8`; the key is never printed). It refuses a unit loaded from another file, with a `collied.service.d` drop-in it cannot check, or pinning another `XDG_DATA_HOME`, so it never logs in a fresh node beside the paired one (built). |
| Residual | As under [Same-UID malware on the Mac](#same-uid-malware-on-the-mac): same-UID code can drive a terminal or the control socket. |
| Phase | Built |

### APNs key storage on Linux

| | |
|---|---|
| Assets | The machine's APNs `.p8` key; the systemd host secret `/var/lib/systemd/credential.secret` |
| Attack | Read the key from `<data dir>/apns/<key ID>.cred` or the fallback file: a process running as the user, another local user, root or a polkit admin, or someone holding an offline copy of the file or of the disk. |
| Mitigations | `collied apns import` applies the same file checks as on macOS (`[apns]` ids, refuses a file named for another key ID, 0600 regular file owned by the user, opened with `O_NOFOLLOW`, ES256 key), encrypts it with `systemd-creds --user` under the name `collied-apns-<key ID>`, writes the credential itself (0600, `O_NOFOLLOW`, atomic), decrypts it back and compares before and after storing, then asks y/N to delete the original (only if it is still the same inode). An existing credential is kept only if it decrypts to the same key. systemd seals it with AES-256-GCM under a key derived from the host secret (root, 0400), the TPM2 when one is usable, the uid, the user name and the machine-id. An offline copy of the `.cred` alone decrypts nothing; with a TPM2 seal, decryption also needs that TPM chip. Other unprivileged users cannot decrypt it: the key is bound to the uid and user name, and systemd asks polkit for admin authentication (`auth_admin_keep`) before decrypting another user's credential. collied passes `--no-ask-password`, so it never raises a polkit prompt itself. The name is bound into the credential and every decrypt passes it, so a credential made under another name does not decrypt as this key. The daemon, `collied apns test` and doctor decrypt through stdin and stdout, never to a file. Doctor reads the seal from the credential header and reports it ("host key only (no usable TPM2)", "host key and TPM2" or "TPM2"); it fails on a credential that does not decrypt or has a null key, warns on an unrecognized seal, and warns when a host-only credential exists but a TPM2 is now usable (re-import to bind it). When `systemd-creds` fails to encrypt (for example no systemd, no `systemd-creds.socket`, systemd older than 256, a container), import falls back to a 0600 copy at `<data dir>/apns/AuthKey_<key ID>.p8` named by `key_path` and says so; doctor reports that file as protected by its mode only while `systemd-creds` stays unusable, and warns to import again once it works (built). |
| Residual | No per-application binding: any process running as the user decrypts the credential with no prompt, so same-UID malware reads the key itself, where on macOS the Keychain ACL leaves it the signed collied or a Keychain prompt. Root, and anyone who authenticates as an admin through polkit, decrypts it too. An unprivileged caller cannot choose the seal: systemd picks host key and TPM2 when a TPM2 is usable, else host key only, and falls back to host key only if TPM sealing fails; doctor shows which one applies. Without a usable TPM2 the seal is host key only (the dev machine: T2 Mac hardware, where `systemd-analyze has-tpm2` reports partial), so whoever reads the unlocked disk (host secret, machine-id and credential) can decrypt it off the machine. The credential stops decrypting after an OS reinstall, a machine-id change, a uid or user name change, or a restore to another machine: import again from the backup. The 0600 fallback file is protected by its mode only, like `key_path` on macOS. |
| Phase | Built |

### Live Activity on the lock screen

| | |

Running subagents (`Agent.subagents`) come from the session's own `subagents/agent-<id>.jsonl`, `subagents/workflows/<workflow>/agent-<id>.jsonl` and their `.meta.json`, reached only through real directories under the session's directory, for ids of letters and digits and workflow names of letters, digits, `_` and `-`, with the same `O_NOFOLLOW`, `O_NONBLOCK` regular-file open. herdr's session id is cross-checked against the pane's own processes: their pids come from herdr's `pane.process_info` (whose `argv` is read only to recognise `claude attach <target>` and keep that target, a job id or session name, and is otherwise dropped with `cmdline`, since they can hold secrets), and each one's `sessions/<pid>.json` is trusted only when its `pid` matches its name, `kill(pid, 0)` succeeds, the process's start time (from the kernel) is no later than the file's `startedAt` plus 2 s, so a file left by a process whose pid was later reused is refused, and its `cwd` is the pane's. Disagreeing files keep herdr's id. Hand-offs are followed only from the session's own transcript, to a session whose transcript is in the same project directory, at most 4 hops, never around a loop; a `/resume` into a background session needs exactly one live, checked `kind: bg` process of that job and directory, and a `claude attach` target exactly one live, checked `kind: bg` process whose job id starts with it or whose name is it and is the pane's title. Finished and interrupted turns disappear, and the kernel releases locks even after an unclean process exit, so stale lock files alone prove nothing. ## Desktop download verification

The macOS installer requires a strict signature, the expected daemon identifier and publisher team, and Apple's explicit notarized requirement before replacing the installed executable or changing its service. The standalone executable check forces an online ticket lookup; failure leaves the existing binary and service untouched. App and disk-image policy checks remain separate. These checks do not replace quarantined-download acceptance on a clean Mac with Gatekeeper enabled.

## Isolated relay foundation

The private Worker in `relay/` accepts only HMAC-authorized, registered destinations and strict generic/encrypted public envelopes. It stores no notification payloads and cannot issue approval decisions. Its validation configuration exposes no public URL or enrollment bypass. App Attest control authorization, retention cleanup and measured production resource limits are launch gates, not completed protections. Stolen grants permit bounded sends until expiry or revocation, and revocation can race an already authorized in-flight attempt. See [relay.md](relay.md) for storage, privacy, abuse and deployment constraints.


## Attested relay control validation

The private relay control path trusts pinned Apple certificate chains and fixed publisher app/environment policy. App Attest establishes app integrity, while the phone's confirmed pairing authorizes machine-specific, exact-destination grants. Assertions require a valid ECDSA signature over the SHA-256 nonce of authenticator data plus client-data hash. Accepting a retained AT flag does not permit credential bytes or bypass App ID, extension, signature or counter checks. It does not establish a person's identity or token ownership. HMAC challenges bind canonical operations and an exact prior durable counter/epoch, preventing replay even with a newly signed higher counter. D1 trigger failures roll back counters, quotas and authorization together. A stolen grant can send bounded pushes only to its route until revocation/expiry; it carries no approval or decryption authority.

The isolated phone client pins the publisher's endpoint and refuses redirects. Its whole control transaction uses an explicit FIFO gate across actor awaits. Offline revocation retains minimal retry credentials and remains pending until success or expiry; local removal cannot guarantee immediate remote denial. Raw destinations and verified attestation metadata remain in bounded D1 records until retention cleanup, with no notification keys, payloads or sensitive request logs. The exact validation and external rollout gates are in [relay.md](relay.md#attested-control-contract).
Measured full attestation exceeded the Free CPU budget, including hostile invalid-nonce cases. The relay cannot claim availability within that budget; do not expose enrollment until the design is revised and remeasured. See [the validation report](reviews/relay-free-tier.md).

## Internal relay crypto prototype

The crypto actor is reachable through an internal binding, with one fixed object name and no HTTP handler. The public Worker applies its existing admission, body and challenge checks before forwarding bounded verification inputs. The actor independently derives publisher/environment/version policy from trusted bindings and uses its own current time; callers cannot supply alternate roots or validation context. No destinations, notification plaintext, decryption keys or authorization decisions enter actor storage. Verification remains separate from D1's atomic replay/epoch/quota guard. Unavailable or exhausted compute returns a closed failure, with no expensive inline fallback. Paid validation adds shared control/enrollment limiter keys before D1 or crypto, alongside source and installation keys, and a provisional 250 ms script CPU ceiling. Shared limiter counters are local to a Cloudflare location and permissive; distributed attempts still consume billed requests and may reach D1/crypto before committed daily quotas reject them. Neither mechanism is an account spending cap. Shared exhaustion can deny legitimate enrollment or revocation. The singleton is an availability bottleneck; native queuing and platform quota exhaustion can deny legitimate requests. One small guarded Free-account cycle completed within the observed CPU limits; full production CPU distributions, actor duration/capacity and fresh Collie enrollment remain unvalidated. See [relay.md](relay.md#internal-crypto-prototype).

## Relay sender outages and stale authorization

The daemon selects a fixed HTTPS publisher endpoint from its own mutually exclusive push mode, never from a phone-supplied URL. It sends only a bounded grant in the sensitive Authorization header and an encrypted/generic public envelope, refuses redirects, and bounds response size and attempt time. No grant, destination or payload is written to logs or doctor output. Only private `push.json` retains route grants with their exact paired device/activity.

Relay retries hold at most 64 encrypted pending destinations in memory, with no durable payload queue. Routine states coalesce and share a 60-second cadence; transient errors and Cloudflare non-JSON limit responses pause attempts with bounded exponential backoff and jitter. Daily quotas remain server-authoritative across all machines. The worker rechecks pairing, exact token/generation, grant expiry, live approval/expiry and activity replacement before every attempt. APNs expired/unregistered invalidations remove only the matching old destination generation; configuration errors retain registrations. A genuine OS token registration can authorize a newer generation for the same token through the existing attested control gate. Polls and foreground snapshots cannot force repeated rotations. Late invalidations cannot revoke that replacement or another installation, app or activity route. Ambiguous successful responses can duplicate display, but cannot grant approval authority. Offline revocation and an already authorized in-flight push retain their documented races. Push outages do not block authenticated tailnet or local desktop operations.

## Local Simulator development trust
