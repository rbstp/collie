# Threat model

Scope: collied on a Mac or Linux machine (a systemd user unit on Linux), Collie.app on the iPhone, the tailnet between them, herdr as collied's local backend, APNs and the publisher relay. The computer and the phone each run their own user-owned embedded Tailscale node, with no OS VPN profile. Tailnet configuration is in [tailnet.md](tailnet.md), design in [architecture.md](architecture.md).

## Trust boundaries

- **Tailnet to collied.** The only network entry point is collied's tsnet listener (TCP 8457 by default). Each connection passes, in order: the whois gate before the WebSocket upgrade (untagged, not shared in, owned by the positive embedded self user bound before listening, and either a paired `StableID` with its paired user and pinned TLS key, or an open pairing window); mutual TLS against the key the gate pinned (any P-256 key in a pairing-only session); the same gate again under the peers, pairing and sessions locks, which must reach the same decision, so a pairing or revoke during the handshake refuses it. Frames then pass a fail-closed method allowlist: unknown methods are rejected before params are decoded, unknown fields are denied, herdr's privileged methods are unreachable. Terminal methods are their own class: refused with `terminals_disabled` unless `[terminals] enabled = true`, and they need a grant signed by the phone's terminal key.
- **collied to herdr.** Same UID: nothing running as the user is a boundary. On Linux, the systemd unit's sandboxing is defense in depth, not a boundary against the same UID.
- **Tailscale control plane.** Trusted for node identity: whois and the phone's netmap check both come from it.
- **Apple and the publisher relay.** They see push metadata, never private display content, which is authenticated ciphertext ([Apple sees push payload metadata](#apple-sees-push-payload-metadata)).

Computer nodes are user-owned, not tag-confined: they get their user's tailnet privileges and normal key expiry, so a compromised daemon can use whatever network access the user's policy permits. Collie's mutual TLS and same-user admission protect its sessions, not other tailnet resources. Neither embedded node installs an OS VPN profile or touches a native (for example corporate) Tailscale client's account, state or routes. Before App Store submission, pairing on a physical device, reconnect and background recovery, and coexistence with an active corporate VPN must still be tested; static source and local control tests do not establish them.

## Threats from the spec

### Stolen phone

| | |
|---|---|
| Assets | Paired session (read and control of agents); phone node keys |
| Attack | A thief opens the unlocked app, or unlocks the phone, and drives agents or answers approvals. |
| Mitigations | iOS passcode and data protection on the node state. Revocation: `collied peers revoke` plus removing the node in the admin console ([tailnet.md](tailnet.md#revocation)); node key expiry (Tailscale default 180 days) bounds a forgotten revocation. Closing a pane or workspace needs `confirm: true` (else `confirm_required` before herdr is called), which guards only against accidents, since the phone sets it. Rate limits per paired `StableID`: frames 20/s, burst 40; `attachment.chunk` and `file.chunk` in their own bucket, 128/s; `approval.decide` 1/s, burst 5. The audit log records every method except `hello`, `flock.snapshot`, `approval.list`, `usage.costs`, `file.chunk`, `file.close`, `attachment.chunk`, `attachment.abort` and an issued `terminal.challenge` (a refused one is logged), and every decide attempt that passes the frame limit; of a run of frames over the limit, only the first is logged, as `rate_limited`. Approval decisions need an iOS unlock (lock screen) or LocalAuthentication (in app) ([Lock-screen and in-app approval](#lock-screen-and-in-app-approval)). Terminals (off by default) need a grant signed by the Secure Enclave terminal key after Face ID or the passcode ([Shell input from the phone](#shell-input-from-the-phone)). |
| Residual | Until revoked, an unlocked phone drives agents (prompts, keys, new tasks, closes) with no per-action check, and an agent can run any command. Only approval decisions and terminal grants ask for Face ID or the passcode, so the terminal grant does not protect the phone as a whole from a thief holding it unlocked. A thief who knows the passcode passes both approval gates and the terminal grant. |
| Phase | Revocation and approval authentication: built. An app-level gate for the other drive methods: not planned. |

### Leaked pairing QR

| | |
|---|---|
| Assets | Pairing code; the machine's tailnet node name, `StableID` and TLS key pin (public) |
| Attack | Someone photographs or copies the QR or the invite URI (`--show-uri`) from the terminal, a desktop pairing window, scrollback, a screen share or recording, or a herdr pane other same-UID code can read, then pairs their own device. |
| Mitigations | The code alone grants nothing: pairing is offered only to an untagged, not-shared-in node owned by the verified embedded self user (also before the first pairing), and only while a locally opened window is active. One window at a time, 120 s, burned by the first `pair.complete`, right or wrong code. With the right code, collied shows the candidate's device label, node name, `StableID`, login name and user ID and asks y/N on the machine (60 s timeout). The code is compared in constant time, carried in the URI fragment and redacted in `Debug`. The same-user gate holds even when a broader policy lets other users reach collied's port. |
| Residual | A node logged in as the owner (account compromise) can race the window at any time. Any node admitted to a pairing-only session can burn an open window (denial of pairing only). Desktop windows show the QR for the same 120 s, and screen recordings capture it. The terminal's QR, and the URI with `--show-uri`, stay in scrollback and recordings: useless once burned or expired, but as good as a scan if read live within the 120 s. The host name and node ID in the QR are not secret. |
| Phase | Built |

### Malicious herdr plugin on the Mac

| | |
|---|---|
| Assets | Everything on the computer (Mac or Linux); the phone's view of agents and approvals |
| Attack | herdr plugins are unsandboxed code running as the user with the full herdr CLI. A plugin can drive every pane, read collied's data dir (node keys, `tls-key.json`, `peers.json`, `.p8`; on Linux, decrypt the APNs credential), drive the control socket, and write pane text that collied turns into approval snippets to mislead the phone. |
| Mitigations | None on the computer: same UID is out of scope for file modes. Snippets are capped at 200 characters with controls, bidi and format characters stripped, so they cannot inject escapes into the phone UI. Claude Code's reason for asking is capped the same way with terminal escape sequences dropped, and is not shown at all if it carries any other control, bidi or format character. Decisions send only `up`, `down`, `enter` and `esc` (plus `tab` and the user's own text for a note), never pane text. |
| Residual | Full compromise of the computer ([Same-UID malware on the Mac](#same-uid-malware-on-the-mac)). A plugin can also draw a fake but well-formed Claude Code menu and so show the phone a fake approval. |
| Phase | Built as far as it goes (Keychain item limits: [Same-UID malware on the Mac](#same-uid-malware-on-the-mac)); otherwise not planned: install only trusted plugins. |

### Compromised Tailscale coordination plane

| | |
|---|---|
| Assets | Node identity, on which every collie authorization decision rests |
| Attack | The control server (or a stolen admin account) adds a node with its own key and gives it the phone's `StableID` and the owner's user ID, changes grants and ownership, or points the phone's netmap at a fake machine. |
| Mitigations | Protecting the admin account (IdP, MFA) is up to the user. collied binds the owner to its own positive embedded self identity before listening and pins the phone's `StableID`, user ID and untagged, unshared state; the phone pins the same user and the machine's `StableID` and untagged, unshared state. These pins stop casual misconfiguration, not a lying control plane, and the y/N prompt catches a new device only during pairing. Mutual TLS is independent of Tailscale keys: the phone pins the machine's TLS key from the QR the machine shows (out of band), and collied pins the phone's Secure Enclave key recorded when the pairing is confirmed. A node injected with the phone's `StableID`, or a fake machine in the phone's netmap, fails the TLS handshake. |
| Residual | Low: a lying control plane can still cut or delay traffic and learn which nodes talk. It cannot get a full session without the phone's Secure Enclave key, or pass as a machine without its TLS key. |
| Phase | Built (Phase 6). |

### Replayed notification

| | |
|---|---|
| Assets | Approval decisions |
| Attack | An old push (or a captured approval decision) is replayed to approve something again or something else. |
| Mitigations | The push carries no nonce, only `approval_id` and `node_id` as lookup keys; the app validates both and trusts nothing else in the payload. A lock-screen action fetches the nonce from the pinned, paired machine over the tailnet (`approval.list`) and decides there. The nonce is 32 random bytes, compared in constant time and burned by the first attempt past the rate limit, whatever its result; a burned id answers `approval_already_resolved`. The `Nonce` type rejects malformed values and is redacted in `Debug`. Approvals expire after 10 minutes, and `apns-expiration` is the approval's expiry. Every attempt that passes the per-peer frame limit, replays and expired ones included, is audited. Decisions are bound to a fingerprint and fail as `superseded` if the prompt changed. The opaque terminal-derived collapse id makes a reissued alert replace the dead one. |
| Residual | A replayed or stale push shows a notification whose `approval_id` no longer resolves; acting on it answers "This approval is no longer pending. Nothing was sent." While the agent stays blocked, each reissue can bring a fresh alert for the same terminal. |
| Phase | Built |

### Leaked APNs key

| | |
|---|---|
| Assets | `.p8` key (team wide), device tokens |
| Attack | With the key and a device token, an attacker sends arbitrary pushes to Collie (or, since the key is team wide, to any app of the team) to phish the user. |
| Mitigations | A dedicated, revocable key, never in GitHub ([release.md](release.md)), one per machine with its own key ID, so a key leaked from one machine is revoked in the portal without touching the others. On macOS, `collied apns import` stores the key in the login Keychain, whose ACL lets only collied signed with the team's Developer ID (`just collied-install`) read it without a prompt, and deletes the file after confirmation. On Linux it stores a systemd user credential (or a 0600 file where `systemd-creds` cannot encrypt) and offers to delete the original ([APNs key storage on Linux](#apns-key-storage-on-linux)). `collied doctor` warns about a `key_path` config (on Linux, when `systemd-creds` works) and about a `.p8` in collied's `apns` dir other than the configured `key_path`. Pushes carry no nonce and cannot create or decide an approval ([Replayed notification](#replayed-notification)). |
| Residual | A leaked provider key can submit its own fallback text if the notification extension does not run. Without the notification key it cannot authenticate private display content, and the app rejects unauthenticated decision actions. A forged background push naming a genuine `approval_id` (16 random bytes, seen only by Apple, the publisher relay when used, the paired devices and the machine) can remove that alert from the phone; the approval stays pending in the app. Copies outside the Keychain or systemd credential (the download before import, the password manager backup) are protected only by where they sit. |
| Phase | Built |

### Phone node key extraction

| | |
|---|---|
| Assets | Phone node keys, which pass the whois gate as the paired phone |
| Attack | Keys read from the device (forensic tools, jailbreak, exploit) or a backup, then used from another machine. |
| Mitigations | App sandbox; the state dir is 0700, `completeUntilFirstUserAuthentication` and excluded from backups; collie-core refuses a state dir with group or world access or another owner. Revocation and key expiry as for a stolen phone. |
| Residual | Node keys are files, readable after first unlock by code inside the app's sandbox. Alone they do not suffice: collied also requires the phone's Secure Enclave TLS key, which cannot leave the device (`ThisDeviceOnly`, usable after first unlock). Code running on the unlocked phone inside the app's sandbox can still use that key there. |
| Phase | Secure Enclave TLS key: built (Phase 6). Backup exclusion for the node state: built. |

## Threats from the design

### Same-UID malware on the Mac

| | |
|---|---|
| Assets | herdr, collied's data dir, the APNs key, the control socket |
| Attack | Any process running as the user controls herdr directly, reads node keys, `tls-key.json` and `peers.json`, and uses the 0600 control socket. |
| Mitigations | None by design for herdr and collied's files: the same UID already owns every shell. The 0700 data dir, the 0600 files and control socket, and the socket's peer UID check stop only other local users. On macOS the APNs key is the exception: a Keychain item whose ACL trusts only collied's designated requirement (Developer ID Application, team `RM3UT3MMSR`, identifier `dev.rbstp.collied`, hardened runtime), so other programs cannot read the key bytes without a Keychain prompt. Linux has no such exception: any same-UID process decrypts the systemd credential without a prompt ([APNs key storage on Linux](#apns-key-storage-on-linux)). The systemd unit's sandboxing (`NoNewPrivileges`, `ProtectSystem=strict`, a system call filter and more) limits a compromised collied, not other same-UID processes, and a user manager skips it where unprivileged user namespaces are unavailable. |
| Residual | Full compromise of the computer side. With the node keys and `tls-key.json`, malware can impersonate the computer to the phone, from this machine or elsewhere, and show fake state or approvals; it can replace collied or its keys and bypass the application gate. Through the control socket's hook request it can report a tool call that differs from the dialog, so the alert names another call; the decision still binds to the screen's fingerprint, and the in-app approval also shows the screen's snippet. It controls the gate's configuration (`collied.toml`, `peers.json`: owner and paired `StableID`s) and can answer the y/N prompt, so the gate protects nothing. Only the tailnet policy, which needs the admin account to change, keeps other users' devices out, and broad grants can admit them: user-owned nodes are not confined service identities. macOS Keychain limits: malware can raise a prompt the user may accept; anyone with the login password can change the ACL or export the item; malware can run the signed collied itself (with its own `--config` or `HOME`) to push with the key without holding it; a `key_path` config or an undeleted `.p8` gets none of this protection. On Linux, malware reads the key itself and can push from anywhere until the key is revoked. |
| Phase | Built (Keychain item, systemd credential). Otherwise out of scope. |

### Menu bar app

| | |
|---|---|
| Assets | The invite (pairing code) while its QR is shown; the y/N decision on a candidate phone; collied's state |
| Attack | Another app or a stray click approves a phone in the pairing window; the invite leaks from the app; phone-provided strings disguise the candidate; the app becomes a way in from the network. |
| Mitigations | Only a local client of the 0600, same-UID control socket, sending `pair` (with its `confirm` answer), `peers_list` and a read-only `watch`; no network listener. Developer ID signed, hardened runtime, no entitlements. The invite is never shown as text, copied, logged or persisted; window restoration is off. Pair is not the default button and is live only 1 s after the candidate appears; one answer per candidate, never automatic; collied refuses after 60 s; closing the window cancels the pairing. Candidate strings are escaped like `collied::printable` (controls, format and bidi characters, combining marks, default-ignorable characters, non-ASCII spaces). First-run Set Up opens only the fixed, installed regular executable in the system Terminal, through a private self-cleaning command file with a quoted literal path; the CLI still checks its installed path and signing identity. Interactive login opens only the exact Tailscale HTTPS login authority, once; if the browser fails, the printed fallback remains. |
| Residual | Same-UID code can drive the control socket or the app itself, and can already answer the y/N prompt ([Same-UID malware on the Mac](#same-uid-malware-on-the-mac)). The QR is on screen for up to 120 s, like the terminal's. |
| Phase | Built |

### Bar widget (Linux)

| | |
|---|---|
| Assets | As for the menu bar app |
| Attack | A stray click or key approves a phone; the invite leaks into argv, a file or the shell's log; phone strings render as rich text or disguise the candidate; the audit log is edited through the viewer; the widget becomes a way in from the network. |
| Mitigations | An Omarchy shell plugin and only a local client of the 0600, same-UID control socket, sending CollieBar's requests; no listener, no network access, no change to collied. The invite reaches `qrencode` only on stdin and is never logged or shown as text; the QR is dropped with the pairing, but qrencode's output, which encodes the one-time invite, stays in the shell's memory until the next pairing. Pair is bound to no key, is live only 1 s after the candidate appears and sends one answer; collied refuses after 60 s; closing the panel cancels. Phone strings are escaped like `collied::printable` and drawn as plain text. Commands run by argv, never through a shell string. The audit log opens in `less` with `LESSSECURE=1`. |
| Residual | Same-UID code can drive the control socket, the shell or the plugin files under `~/.config/omarchy/plugins` ([Same-UID malware on the Mac](#same-uid-malware-on-the-mac)). Any other shell plugin runs in the same Quickshell process. The QR is on screen for up to 120 s. |
| Phase | Built |

### `collied setup`

| | |
|---|---|
| Assets | The y/N decision on a candidate phone; the launchd agent or systemd user unit; `collied.toml` and the APNs key |
| Attack | Piped input (`yes`) confirms a pairing without a human; setup installs an unsigned agent or a service running a build output, leaves the key or config readable, or on Linux logs in a new node over the paired one. |
| Mitigations | Before any step, setup refuses unless stdin is a terminal and the running binary is the regular file `~/.cargo/bin/collied` (on Linux, or the package-owned `/usr/bin/collied`) and, on macOS, Developer ID signed as `dev.rbstp.collied`. So the service never runs a build output that the next `cargo build` replaces unsigned, nor one reached through a symlink. Setup never confirms a pairing: it runs the `collied pair` flow, whose `y` follows a `tcflush`. It reuses `service install` and, with `--direct-apns`, `apns import` (Keychain, systemd credential or the Linux 0600 fallback; read back; offer to delete the `.p8`; key never printed). A new `collied.toml` is created 0600; an existing one is rewritten atomically, keeping its mode; neither `[apns]` nor `[push.relay]` holds a secret. Setup changes no bind, gate or pairing rule, refuses to drop the `--config` the service runs with, and stops on any doctor fail line, `listen` included. On Linux the unit is written through `service install` (0644, no secret, `UMask=0077`); setup refuses a unit loaded from another file, a `collied.service.d` drop-in it cannot check, or a unit pinning another `XDG_DATA_HOME`, so it never logs in a fresh node beside the paired one. |
| Residual | Same-UID code can drive a terminal or the control socket ([Same-UID malware on the Mac](#same-uid-malware-on-the-mac)). |
| Phase | Built |

### APNs key storage on Linux

| | |
|---|---|
| Assets | The machine's APNs `.p8` key; the systemd host secret `/var/lib/systemd/credential.secret` |
| Attack | Read the key from `<data dir>/apns/<key ID>.cred` or the fallback file: a process running as the user, another local user, root or a polkit admin, or someone holding an offline copy of the file or the disk. |
| Mitigations | **Import:** `collied apns import` applies the macOS file checks (`[apns]` ids; refuses a file named for another key ID; a user-owned 0600 regular file opened with `O_NOFOLLOW`; an ES256 key), encrypts the key with `systemd-creds --user` under the name `collied-apns-<key ID>`, writes the credential itself (0600, `O_NOFOLLOW`, atomic), checks that it decrypts to the same key before and after storing, then asks y/N to delete the original, only if it is still the same inode. An existing credential is kept only if it decrypts to the same key. **Seal:** systemd uses AES-256-GCM under a key derived from the host secret (root, 0400), the TPM2 when usable, the uid, the user name and the machine-id. An offline copy of the `.cred` alone decrypts nothing; a TPM2 seal also needs that TPM chip. Other unprivileged users cannot decrypt it: the key is bound to the uid and user name, and systemd asks polkit for admin authentication (`auth_admin_keep`) before decrypting another user's credential; collied passes `--no-ask-password`, so it never raises a polkit prompt itself. Every decrypt passes the name bound into the credential, so a credential made under another name does not decrypt as this key. The daemon, `collied apns test` and doctor decrypt through stdin and stdout, never to a file. **Doctor** reports the seal from the credential header ("host key only (no usable TPM2)", "host key and TPM2" or "TPM2"), fails on a credential that does not decrypt or has a null key, and warns on an unrecognized seal or on a host-only credential once a TPM2 is usable (import again to bind it). **Fallback:** where `systemd-creds` cannot encrypt (for example no systemd, no `systemd-creds.socket`, systemd older than 256, a container), import says so and writes a 0600 copy at `<data dir>/apns/AuthKey_<key ID>.p8` named by `key_path`; doctor reports it as protected by its mode only while `systemd-creds` stays unusable, and warns to import again once it works. |
| Residual | No per-application binding: any same-UID process decrypts the credential without a prompt, so same-UID malware reads the key itself, where on macOS the Keychain ACL leaves it only the signed collied or a Keychain prompt. Root, and anyone who authenticates as an admin through polkit, decrypts it too. An unprivileged caller cannot choose the seal: systemd uses host key and TPM2 when a TPM2 is usable, else host key only, and host key only if TPM sealing fails; doctor shows which. Without a usable TPM2 (the dev machine: T2 Mac hardware, where `systemd-analyze has-tpm2` reports partial), whoever reads the unlocked disk (host secret, machine-id and credential) can decrypt the key off the machine. The credential stops decrypting after an OS reinstall, a machine-id change, a uid or user name change, or a restore to another machine: import again from the backup. The 0600 fallback is protected by its mode only, like `key_path` on macOS. |
| Phase | Built |

### Live Activity on the lock screen

| | |
|---|---|
| Assets | Followed agents' status and labels; the update tokens |
| Attack | Someone looks at the locked phone, or a party holding the APNs key and a token pushes fake content. |
| Mitigations | Nothing shows unless the user follows the agent (off by default). The activity shows status, labels, elapsed time and the approvals count. While an approval routed to it is pending, and only when `enc` opens with the `approvalId` as AAD, it also shows Approve, Deny and the command, which the widget decrypts on the phone with the per-machine notification key and marks `privacySensitive`, so iOS redacts it while the phone is locked or the display dimmed. Unauthenticated state shows neutral `Collie` content and no buttons. The buttons are a `LiveActivityIntent` with `authenticationPolicy = .requiresAuthentication` and take the [lock-screen path](#lock-screen-and-in-app-approval), one decision at a time per approval. Tapping elsewhere only opens the app on that agent; the app validates both ids and decides nothing. Tokens (stored as listed under [Assets](#assets)) are never logged or audited and are bound to the registering device's `StableID`, so another paired device can neither replace nor end them. They are dropped on revoke, on `Unregistered` or `BadDeviceToken`, on end, when the terminal is gone, and 8 h after the activity first registered (ActivityKit's activity lifetime), so a dead activity stops receiving encrypted updates; at most 8 per device, one per terminal. ## Desktop download verification

Before it replaces the installed executable or changes its service, the macOS installer requires a strict signature, the expected daemon identifier and publisher team, and Apple's explicit notarized requirement. The standalone executable check forces an online ticket lookup; a failure leaves the existing binary and service untouched. App and disk-image policy checks are separate. ## Publisher relay

The Worker in `relay/`, deployed at `collie-push.rbstp.dev`, accepts only HMAC-authorized, registered destinations and strict generic or encrypted public envelopes. It stores no notification payloads, cannot issue approval decisions and has no enrollment bypass. An hourly cleanup deletes expired relay records within 14 days of the last grant expiry, even at the exact global control and enrollment caps; D1 Time Travel keeps them restorable for 30 days after deletion. Production resource limits rest on measurements and soft controls, not a spending cap; [relay.md](relay.md) covers them and the storage, privacy, abuse and deployment constraints.

## Attested relay control

The relay control path trusts pinned Apple certificate chains and a fixed publisher app/environment policy. App Attest establishes app integrity, not a person's identity or token ownership; the phone's confirmed pairing authorizes machine-specific, exact-destination grants. An assertion needs a valid ECDSA signature over the SHA-256 nonce of the authenticator data plus the client-data hash. Accepting a retained AT flag permits no credential bytes and bypasses no App ID, extension, signature or counter check. HMAC challenges bind canonical operations and an exact prior durable counter/epoch, so even a newly signed higher counter cannot replay one. A D1 trigger failure rolls back counters, quotas and authorization together. A stolen grant can send bounded pushes only to its route until revocation or expiry, and revocation can race an already authorized in-flight attempt; the grant carries no approval or decryption authority.

The phone client pins the publisher's endpoint, refuses redirects and runs its whole control transaction under an explicit FIFO gate across actor awaits. An offline revocation keeps minimal retry credentials and stays pending until it succeeds or expires; local removal cannot guarantee immediate remote denial. Raw destinations and verified attestation metadata stay in bounded D1 records until retention cleanup, with no notification keys, payloads or sensitive request logs. The exact control contract and retention bound are in [relay.md](relay.md#attested-control-contract). Measured full attestation exceeded the Free plan's CPU budget, including hostile invalid-nonce cases, so the relay runs on Workers Paid with the internal crypto actor below ([validation report](reviews/relay-free-tier.md)).

## Internal relay crypto prototype

The crypto actor is reachable through an internal binding, under one fixed object name, with no HTTP handler. The public Worker applies its admission, body and challenge checks before forwarding bounded verification inputs. The actor derives publisher/environment/version policy from trusted bindings and uses its own current time; callers cannot supply other roots or validation context. No destinations, notification plaintext, decryption keys or authorization decisions enter actor storage. Verification stays separate from D1's atomic replay/epoch/quota guard. Unavailable or exhausted compute fails closed, with no expensive inline fallback. Paid validation adds shared control/enrollment limiter keys before D1 or crypto, alongside source and installation keys, and a provisional 250 ms script CPU ceiling. Shared limiter counters are local to a Cloudflare location and permissive: distributed attempts still consume billed requests and may reach D1/crypto before committed daily quotas reject them. Neither mechanism is an account spending cap, and shared exhaustion can deny legitimate enrollment or revocation. The singleton is an availability bottleneck; native queuing and platform quota exhaustion can deny legitimate requests. One small guarded Free-account cycle completed within the observed CPU limits; full production CPU distributions, actor duration/capacity and fresh Collie enrollment remain unvalidated. See [relay.md](relay.md#internal-crypto-prototype).

## Relay sender outages and stale authorization

collied takes a fixed HTTPS publisher endpoint from its own push mode (relay and direct APNs are mutually exclusive), never from a phone-supplied URL. It sends only a bounded grant in the sensitive Authorization header and an encrypted or generic public envelope, refuses redirects, and bounds response size and attempt time. No grant, destination or payload reaches logs or doctor output; only the private `push.json` keeps route grants, each with its exact paired device or activity.

Relay retries hold at most 64 encrypted pending destinations in memory, with no durable payload queue. Routine states coalesce and share a 60-second cadence; transient errors and Cloudflare non-JSON limit responses pause attempts with bounded exponential backoff and jitter. Daily quotas stay server-authoritative across all machines. Before every attempt, the sender rechecks pairing, exact token/generation, grant expiry, live approval/expiry and activity replacement. APNs expired/unregistered invalidations remove only the matching old destination generation; configuration errors keep registrations. A genuine OS token registration can authorize a newer generation for the same token through the attested control gate; polls and foreground snapshots cannot force repeated rotations. Late invalidations cannot revoke that replacement or another installation, app or activity route. An ambiguous successful response can duplicate a display but grants no approval authority. Offline revocation and an already authorized in-flight push keep their races ([Attested relay control](#attested-relay-control)). Push outages do not block authenticated tailnet or local desktop operations.

## Local Simulator development trust

The local-only Simulator entry pre-provisions a fresh software key into private, isolated D1 storage and refuses enrollment. It fixes sandbox APNs and uses separate send secrets. Its control assertions still pass the production verifier and atomic counter/epoch checks. Production cannot authenticate this key through enrollment or verify the local HMAC grants. Do not copy development database rows or secrets into production. Swift development import exists only in DEBUG Simulator builds; the daemon loopback switch is debug-only and absent from Release artifacts. Real APNs keys stay locally held operator credentials, never provisioning fixtures. [Simulator testing](simulator.md) has the exact boundary and limits.

## Local VM test boundary

The [VM and Simulator harness](vm-simulator.md) is a Debug-only trust island: a disposable macOS guest, a separately recorded host Simulator, fresh software identities, synthetic tailnet authorization and a private mock publisher database. The fixed local control hook requires explicit opt-in plus owned private marker files; unsupported Rust frameworks fail before Swift creates state or identity. Neither physical-device nor Release artifacts expose this hook. Ordinary pairing confirmation, identity pins and mutual TLS still apply.

SSH host keys come through the local VM guest agent and are verified with a private per-run known-hosts file. The harness forwards only fixed loopback endpoints with a task-only key, disables agent forwarding, shares no host directories and refuses occupied test ports. Reset and teardown touch only recorded test resources. VM image tooling and any guest desktop-control permissions belong to the guest; a CI image with SIP or Gatekeeper disabled cannot prove pristine consumer acceptance. Local mock success establishes neither genuine App Attest nor Apple APNs acceptance.
