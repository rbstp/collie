# Threat model

Scope: collied on the Mac or on a Linux machine, Collie.app on the iPhone, the tailnet between them, herdr as collied's local backend, and APNs. On Linux collied runs as a systemd user unit and advertises `tag:collie-linux`. Tailnet configuration is in [tailnet.md](tailnet.md), design in [architecture.md](architecture.md).

## Assets

| Asset | Where |
|---|---|
| Control of every shell and agent on the computer | herdr socket (0600, no auth: same UID means full control); reachable from the phone only through collied's allowlist |
| Mac node keys | `~/Library/Application Support/collie/tsnet` (0700) |
| Linux node keys | `<data dir>/tsnet` (0700), data dir `$XDG_DATA_HOME/collie`, else `~/.local/share/collie`. Separate from a system tailscaled's state (`/var/lib/tailscale`): the embedded node is its own device with its own keys |
| Phone node keys | app container `Application Support/collie/tsnet` (0700, `completeUntilFirstUserAuthentication`, excluded from backup) |
| Machine TLS key (proves the machine to the phone) | `tls-key.json` in collied's data dir (P-256 PKCS#8, 0600, made on first start, read only as a regular file, not a symlink, owned by the user with no group or world access); its pin in the pairing QR and the phone's `machines.json` |
| Phone TLS key (proves the phone to collied) | the phone's Secure Enclave: a P-256 key, non-exportable, `.privateKeyUsage`, `AfterFirstUnlockThisDeviceOnly` and no user presence, so lock-screen decisions can connect; collie-core gets a signing callback, never the key; its pin in `peers.json` (`tls_key`), recorded when the pairing is confirmed |
| Pairings (`StableID` list) and the owner user ID | `peers.json` in collied's data dir (0600); optional `owner_user_id` in `collied.toml` |
| Pairing code | the QR that `collied pair` draws as text in the terminal, and the invite URI it also prints with `--show-uri`; 16 random bytes, one window at a time, 120 s, burned by the first attempt, redacted in `Debug` |
| Approval nonces | collied memory and the phone session (collie-core only, never handed to Swift); 32 random bytes, single use |
| APNs `.p8` key (macOS) | login Keychain item `dev.rbstp.collied.apns`/`<key ID>`, ACL trusting only the Developer ID signed collied (legacy: 0600 file named by `key_path`); a backup in the user's password manager |
| APNs `.p8` key (Linux) | systemd user credential `<data dir>/apns/<key ID>.cred` (0600), encrypted by `systemd-creds` with the host secret (`/var/lib/systemd/credential.secret`, root, 0400) and the TPM2 when one is usable, bound to the user and to the name `collied-apns-<key ID>`; fallback when `systemd-creds` cannot encrypt: 0600 file `<data dir>/apns/AuthKey_<key ID>.p8` named by `key_path`; a backup in the user's password manager. Each machine has its own key and key ID |
| Live Activity update tokens | collied's `push.json` (0600) next to the device token, bound to the device's `StableID`; collie-core memory. Never logged, audited or written to disk on the phone; redacted in `Debug` |
| Notification keys (32 bytes, one per paired Mac) | iOS Keychain (`dev.rbstp.collie.notify`/`<Mac node ID>`, `AfterFirstUnlockThisDeviceOnly`, shared with ColliePush); a mirror file per Mac in the App Group container (`notify-keys/<node ID>.key`: 0600, `completeUntilFirstUserAuthentication`, excluded from backup), because a Live Activity renders in a process with no Keychain (`errSecNotAvailable`) and needs the key to show the command; collied's `push.json` (0600) next to the device token; collie-core memory. Never logged, audited or written elsewhere; redacted in `Debug`. The mirror is weaker than the `ThisDeviceOnly` Keychain item against a jailbroken or forensically imaged phone (user decision, 2026-10-03) |
| Terminal content, agent and workspace names | herdr, the tailnet session, the phone |
| Agent transcripts (whole conversations, tool output) | Claude Code's `~/.claude/projects/*/<session>.jsonl` (or under `CLAUDE_CONFIG_DIR`) and Codex's `~/.codex/sessions/YYYY/MM/DD/rollout-*-<session>.jsonl` (or under `CODEX_HOME`), 0600, written by the agents; collied reads them and keeps only values derived from them, in memory |
| Plan usage and context window sizes | collied's `usage.json` (0600) in the data dir, written by `collied statusline` from Claude Code's status line input: the 5-hour and weekly limits' percentages and reset times, and up to 64 session ids with their window size; collied memory |
| Terminal key (signs terminal grants) | the phone's Secure Enclave: a P-256 key apart from the TLS key, non-exportable, `.privateKeyUsage` and `.userPresence`, `WhenPasscodeSetThisDeviceOnly`, so every signature needs Face ID or the passcode and removing the passcode destroys it; its public key in `peers.json` (`terminal_key`), recorded when the pairing is confirmed on the machine, and in the phone's `machines.json` |
| Terminal challenges and grants | collied memory only, per session: one challenge (32 random bytes, 60 s, single use), grants per terminal for 5 min. Never logged or written to disk |
| Attachments (photos and files sent from the phone) | the phone; collied's attachments dir (`~/Library/Caches/dev.rbstp.collied/attachments` on macOS, `$XDG_CACHE_HOME/collied/attachments`, else `~/.cache/collied/attachments`, on Linux; 0700 dirs, 0600 files) for up to 24 h; the tailnet session |

## Trust boundaries

- **Tailnet to collied.** The only network entry point is the tsnet listener on TCP 8457. Every connection passes the whois gate (untagged, not shared in, owned by the owner once one is known, paired `StableID` with its paired user and a pinned TLS key, or an open pairing window), then mutual TLS against the key the gate pinned for that peer (any P-256 key in a pairing-only session), then the same gate again under the peers, pairing and sessions locks, which must reach the same decision (a pairing or revoke during the handshake refuses it), all before the WebSocket upgrade; then a fail-closed method allowlist (`parse_client_frame`: unknown methods rejected before params are decoded, unknown fields denied, herdr privileged methods unreachable). Terminal methods are their own allowlist class, refused with `terminals_disabled` unless `[terminals] enabled = true`, and need a grant signed by the phone's terminal key.
- **collied to herdr.** Same UID. Nothing on the computer running as the user is a boundary. On Linux the systemd unit's sandboxing is defense in depth, not a boundary against the same UID.
- **Tailscale control plane.** Trusted for node identity: whois and the phone's netmap check both come from it.
- **Apple.** APNs sees what collied pushes: labels and ids in clear, the pending action only as ciphertext, and the Live Activity content of followed agents.

## Threats from the spec

### Stolen phone

| | |
|---|---|
| Assets | Paired session (read and control of agents); phone node keys |
| Attack | Thief opens the unlocked app, or unlocks the phone, and drives agents or answers approvals. |
| Mitigations | iOS passcode and data protection on the node state (built). Revocation: `collied peers revoke` plus removing the node in the admin console (built, [tailnet.md](tailnet.md#revocation)). Phone node key expiry (Tailscale default 180 days) bounds a forgotten revocation. Closing a pane or a workspace needs `confirm: true`, else `confirm_required` before herdr is called (built); the phone sets the flag itself, so it guards against an accidental close, not against a thief. Every frame is rate limited per paired `StableID` (20/s, burst 40; `attachment.chunk` frames have their own bucket, 128/s) and every method other than `hello`, `flock.snapshot`, `approval.list`, `attachment.chunk`, `attachment.abort` and an issued `terminal.challenge` is written to the audit log (`server.rs` `finish`; a refused challenge is logged); of a run of frames over the limit only the first is logged, as `rate_limited` (built). Approvals: in-app decisions need LocalAuthentication (`deviceOwnerAuthentication`, fresh context per decision), lock-screen actions need an iOS unlock (`authenticationRequired`), `approval.decide` is limited to 1/s, burst 5, per `StableID`, and every attempt that passes the frame limit is audited (built). Terminals (off by default) need a grant that collied verifies, signed by the Secure Enclave terminal key, which signs only after Face ID or the passcode (built). |
| Residual | Until revoked, an unlocked phone drives agents (prompts, keys, new tasks, closes) without any per-action check, and an agent can run any command: only approval decisions and terminal grants ask for Face ID or the passcode, so the terminal grant does not make the phone as a whole safer against a thief holding it unlocked. A thief who knows the passcode passes both approval gates and the terminal grant. |
| Phase | Revocation built. Approval authentication built. App-level gate for the other drive methods: not planned. |

### Leaked pairing QR

| | |
|---|---|
| Assets | Pairing code, Mac tailnet node name, Mac `StableID`, the pin of its TLS key (public) |
| Attack | Someone photographs the QR, or copies it or the invite URI (printed next to it by `collied pair --show-uri`) from terminal scrollback, a screen share or recording, or a herdr pane that other same-UID code can read. They then pair their own device. The menu bar app's pairing window shows the same QR. |
| Mitigations | The code alone grants nothing: the pairing session is only offered to an untagged, not-shared-in node (owned by the owner, once one is known) and only while a locally opened window is active. One window at a time, 120 s; the first `pair.complete` from any connection burns it, right or wrong code. With the right code, collied shows the candidate's device label, node name, `StableID`, login name and user ID and asks y/N on the Mac, 60 s timeout. Code compared in constant time; carried in the URI fragment and redacted in `Debug` (built). The policy grants port 8457 to the owner's devices only. |
| Residual | When `owner_user_id` is not configured and nothing is paired yet, the owner is set by the first confirmed pairing (trust on first use), so any tailnet member the policy lets reach the port can race the window with a leaked code; the y/N prompt, which shows the login name, is then the only check. An attacker controlling a node logged in as the owner (account compromise) can race the window at any time. Any node admitted to a pairing-only session can burn an open window (denial of pairing only). The QR in the menu bar app's window is on screen for the same 120 s, and screen recordings capture it like the terminal's. The QR drawn in the terminal, and the URI with `--show-uri`, stay in scrollback and screen recordings after the window closes; they are useless once burned or expired, but a capture read live during the 120 s is as good as a scan. Host name and node ID in the QR are not secret. |
| Phase | Built |

### Malicious herdr plugin on the Mac

| | |
|---|---|
| Assets | Everything on the computer (Mac or Linux); the phone's view of agents and approvals |
| Attack | herdr plugins are unsandboxed code running as the user with the full herdr CLI. A plugin can drive every pane directly, read collied's data dir (node keys, `tls-key.json`, `peers.json`, `.p8`; on Linux it also decrypts the APNs credential), drive collied's control socket, and write pane text that collied turns into approval snippets to mislead the phone. |
| Mitigations | None against the computer side: same UID is out of scope for file modes. Snippets are capped at 200 chars with controls, bidi and format characters stripped (built), so a plugin cannot inject escapes into the phone UI through them. Approval decisions only send `up`, `down`, `enter` or `esc`, never text from the pane (built). |
| Residual | Full compromise of the computer. A plugin can draw a fake but well-formed Claude Code menu in a pane and so show the phone a fake approval. It also controls the gate's inputs: it can rewrite `collied.toml` and `peers.json` (owner and paired `StableID`s), answer y/N over the control socket, and run collied's node and TLS keys elsewhere. Other users' devices are then kept out only by the tailnet policy, whose `src` names the owner alone and which only the admin account can change. |
| Phase | Built as far as it goes (see same-UID malware for the Keychain item's limits). Otherwise not planned (install only trusted plugins). |

### Compromised Tailscale coordination plane

| | |
|---|---|
| Assets | Node identity, which every collie authorization decision rests on |
| Attack | The control server (or a stolen admin account) adds a node with its own key and gives it the phone's `StableID` and the owner's user ID, or changes the tag owners and grants, or points the phone's netmap at a fake Mac. |
| Mitigations | Admin account protection (IdP, MFA) is the user's. collied pins `StableID` + user ID + untagged, and the phone pins the machine's `StableID` + the tag seen at pairing, `tag:collie-mac` or `tag:collie-linux` (built; the owners of either tag are trusted for the tag half of the pin), which stops casual misconfiguration but not a control plane that lies. The y/N prompt at pairing catches a new device only during pairing. Mutual TLS inside the tunnel, independent of Tailscale keys (built): the phone pins the machine's TLS key from the pairing QR, which is shown on the machine and so out of band, and collied pins the phone's Secure Enclave key, recorded when the pairing is confirmed. A node the control plane injects with the phone's `StableID`, or a fake machine in the phone's netmap, fails the TLS handshake. |
| Residual | Low: a lying control plane can still cut or delay traffic, and can learn which nodes talk. It cannot get a full session without the phone's Secure Enclave key, or pass as a machine without its TLS key. |
| Phase | Built (Phase 6). |

### Replayed notification

| | |
|---|---|
| Assets | Approval decisions |
| Attack | An old push (or a captured approval decision) is replayed to approve something again or something else. |
| Mitigations | The push payload never carries the nonce, only `approval_id` and `node_id` as lookup keys (built). A lock-screen action fetches the nonce over the tailnet (`approval.list`) from the pinned, paired Mac and decides there; the app validates both keys and trusts nothing else in the payload (built). Nonce: 32 random bytes, constant-time compare, burned by the first attempt past the rate limit, whatever its result, `approval_ttl` 10 minutes; a burned id answers `approval_already_resolved` (built). Every attempt that passes the per-peer frame limit, including replays and expired ones, is audited; a run of frames over that limit logs only its first, as `rate_limited` (built). Decisions are bound to a fingerprint and fail as `superseded` if the prompt changed (built). APNs `apns-expiration` is the approval's expiry, and the `terminal_id` collapse id makes a reissued alert replace the dead one (built). The `Nonce` type rejects malformed values and is redacted in `Debug` (built). |
| Residual | A replayed or stale push shows a notification whose `approval_id` no longer resolves: acting on it answers "no longer pending, nothing was sent". A fresh alert for the same terminal can follow each reissue while the agent stays blocked. |
| Phase | Built |

### Leaked APNs key

| | |
|---|---|
| Assets | `.p8` key (team wide), device tokens |
| Attack | With the key and a device token, an attacker sends arbitrary pushes to Collie (or, the key being team wide, to any app of the team) to phish the user. |
| Mitigations | Dedicated, revocable key, never in GitHub ([release.md](release.md)). On macOS it is stored in the login Keychain by `collied apns import`, which deletes the file after confirmation; the item's ACL lets only collied signed with the team's Developer ID (`just collied-install`) read it without a prompt; `collied doctor` warns about a `key_path` config (built). On Linux `collied apns import` stores it as a systemd user credential instead (or a 0600 file where `systemd-creds` cannot encrypt) and offers to delete the original; `collied doctor` warns about a `key_path` config when `systemd-creds` works; limits in [APNs key storage on Linux](#apns-key-storage-on-linux) (built). On both, `collied doctor` warns about a `.p8` left in collied's `apns` dir other than the configured `key_path` (built). Each machine uses its own key with its own key ID, so a key leaked from one machine is revoked in the portal without touching the others. Pushes carry no nonce and cannot create or decide an approval: `approval_id` and `node_id` are validated lookup keys, and a lock-screen action decides only what the pinned, paired Mac returns over the tailnet (built). |
| Residual | A leaked key sends fake notifications to Collie (and to every app of the team) until revoked in the portal: a phishing alert with Approve/Deny buttons whose `approval_id` matches nothing ends as "no longer pending, nothing was sent", but its text is the attacker's (as a plaintext body only: without the notification key it cannot produce an `enc` the NSE opens). A forged background push naming a genuine `approval_id` (16 random bytes, seen only by Apple, the paired devices and the Mac) can remove that alert from the phone; the approval stays pending in the app. Copies outside the Keychain or the systemd credential (the downloaded file before import, the password manager backup) are protected only by where they sit. |
| Phase | Built |

### Phone node key extraction

| | |
|---|---|
| Assets | Phone node keys, which pass the whois gate as the paired phone |
| Attack | Keys read from the device (forensic tools, jailbreak, exploit) or from a backup, then used from another machine. |
| Mitigations | App sandbox; state dir 0700 with data protection `completeUntilFirstUserAuthentication`, both set by `StateDirectory.swift`; collie-core refuses a state dir with group or world access or another owner (built). State dir excluded from backups, also set by `StateDirectory.swift` (built). Revocation and key expiry as for a stolen phone. |
| Residual | Node keys are files, readable after first unlock by code inside the app's sandbox. They no longer suffice: collied also requires the phone's TLS key, a Secure Enclave P-256 key that cannot leave the device (`ThisDeviceOnly`, usable after first unlock). Code running on the unlocked phone, inside the app's sandbox, can still use that key there. |
| Phase | Secure Enclave TLS key: built (Phase 6). Backup exclusion for the node state: built. |

## Threats from the design

### Same-UID malware on the Mac

| | |
|---|---|
| Assets | herdr, collied's data dir, the APNs key, the control socket |
| Attack | Any process running as the user controls herdr directly, reads node keys, `tls-key.json` and `peers.json`, uses the 0600 control socket. |
| Mitigations | None by design for herdr and collied's files: same UID already owns every shell. Data dir 0700, files and control socket 0600, control socket peer UID checked: these stop other local users only (built). On macOS the APNs key is the exception: it is a Keychain item whose ACL trusts only collied's designated requirement (Developer ID Application, team `RM3UT3MMSR`, identifier `dev.rbstp.collied`), and the binary is signed with the hardened runtime, so other programs cannot read the key bytes without a Keychain prompt (built). On Linux there is no such exception: any same-UID process decrypts the systemd credential with no prompt ([APNs key storage on Linux](#apns-key-storage-on-linux)). The systemd unit's sandboxing (`NoNewPrivileges`, `ProtectSystem=strict`, a system call filter and more) limits what a compromised collied can reach, but it does not constrain other processes of the same UID, and a user manager skips it where unprivileged user namespaces are unavailable (built). |
| Residual | Full compromise of the computer side. Stolen node keys and `tls-key.json` let the malware impersonate the computer to the phone and show fake state or fake approvals. It can report a tool call through the control socket's hook request that differs from the dialog, so the alert names another call; the decision still binds to the screen's fingerprint, and the in-app approval also shows the screen's snippet. It controls the gate's configuration (`collied.toml`, `peers.json`) and can answer the y/N prompt, so the gate no longer protects anything; other users' devices are kept out only by the tailnet policy, which needs the admin account to change. Keychain ACL limits (macOS): malware can raise a prompt that the user may accept; anyone with the login password can change the ACL or export the item; it can run the signed collied itself (its own `--config` or `HOME`) to make it send pushes with the key, so it can push through collied without holding the key; a `key_path` config or an un-deleted `.p8` gets none of this protection. On Linux the malware reads the key itself and can push from anywhere until the key is revoked. |
| Phase | Built (Keychain item, systemd credential). Otherwise out of scope. |

### Menu bar app

| | |
|---|---|
| Assets | The invite (pairing code) while its QR is shown; the y/N decision on a candidate phone; the state of collied |
| Attack | Another app or a stray click approves a phone in the app's pairing window; the invite leaks from the app; phone-provided strings disguise the candidate; the app becomes a way in from the network. |
| Mitigations | The app is a local client of the 0600, same-UID control socket only, with the CLI's requests plus a read-only `watch`; it opens no network listener. Developer ID with the hardened runtime and no entitlements. The invite is never shown as text, copied, logged or persisted, and window restoration is off. Pair is not the default button and is live only 1 s after the candidate appears; one answer per candidate, never automatic; collied refuses after 60 s. The candidate's strings are escaped like `collied::printable` (controls, format and bidi characters, combining marks, default-ignorable characters and non-ASCII spaces). Closing the window cancels the pairing (built). |
| Residual | Same-UID code can drive the control socket or the app itself, as under [Same-UID malware on the Mac](#same-uid-malware-on-the-mac): it can already answer the y/N prompt. The QR is on screen for up to 120 s, like the terminal's. |
| Phase | Built |

### APNs key storage on Linux

| | |
|---|---|
| Assets | The machine's APNs `.p8` key; the systemd host secret `/var/lib/systemd/credential.secret` |
| Attack | Read the key from `<data dir>/apns/<key ID>.cred` or the fallback file: a process running as the user, another local user, root or a polkit admin, or someone holding an offline copy of the file or of the disk. |
| Mitigations | `collied apns import` applies the same file checks as on macOS (`[apns]` ids, refuses a file named for another key ID, 0600 regular file owned by the user, opened with `O_NOFOLLOW`, ES256 key), encrypts it with `systemd-creds --user` under the name `collied-apns-<key ID>`, writes the credential itself (0600, `O_NOFOLLOW`, atomic), decrypts it back and compares before and after storing, then asks y/N to delete the original (only if it is still the same inode). An existing credential is kept only if it decrypts to the same key. systemd seals it with AES-256-GCM under a key derived from the host secret (root, 0400), the TPM2 when one is usable, the uid, the user name and the machine-id. An offline copy of the `.cred` alone decrypts nothing; with a TPM2 seal, decryption also needs that TPM chip. Other unprivileged users cannot decrypt it: the key is bound to the uid and user name, and systemd asks polkit for admin authentication (`auth_admin_keep`) before decrypting another user's credential. collied passes `--no-ask-password`, so it never raises a polkit prompt itself. The name is bound into the credential and every decrypt passes it, so a credential made under another name does not decrypt as this key. The daemon, `collied apns test` and doctor decrypt through stdin and stdout, never to a file. Doctor reads the seal from the credential header and reports it ("host key only (no usable TPM2)", "host key and TPM2" or "TPM2"); it fails on a credential that does not decrypt or has a null key, warns on an unrecognized seal, and warns when a host-only credential exists but a TPM2 is now usable (re-import to bind it). When `systemd-creds` fails to encrypt (for example no systemd, no `systemd-creds.socket`, systemd older than 256, a container), import falls back to a 0600 copy at `<data dir>/apns/AuthKey_<key ID>.p8` named by `key_path` and says so; doctor reports that file as protected by its mode only while `systemd-creds` stays unusable, and warns to import again once it works (built). |
| Residual | No per-application binding: any process running as the user decrypts the credential with no prompt, so same-UID malware reads the key itself, where on macOS the Keychain ACL leaves it the signed collied or a Keychain prompt. Root, and anyone who authenticates as an admin through polkit, decrypts it too. An unprivileged caller cannot choose the seal: systemd picks host key and TPM2 when a TPM2 is usable, else host key only, and falls back to host key only if TPM sealing fails; doctor shows which one applies. Without a usable TPM2 the seal is host key only (the dev machine: T2 Mac hardware, where `systemd-analyze has-tpm2` reports partial), so whoever reads the unlocked disk (host secret, machine-id and credential) can decrypt it off the machine. The credential stops decrypting after an OS reinstall, a machine-id change, a uid or user name change, or a restore to another machine: import again from the backup. The 0600 fallback file is protected by its mode only, like `key_path` on macOS. |
| Phase | Built |

### Live Activity on the lock screen

| | |
|---|---|
| Assets | Followed agents' status and labels; the update tokens |
| Attack | Someone looks at the locked phone, or a party holding the APNs key and a token pushes fake content. |
| Mitigations | Nothing is shown unless the user follows the agent, which is off by default. The activity shows status, labels, elapsed time and the approvals count. While an approval routed to it is pending it also shows the command, decrypted on the phone by the widget with the per-Mac notification key and marked `privacySensitive`, so iOS redacts it while the phone is locked or the display dimmed, and Approve and Deny, only when `enc` opens with the `approvalId` as AAD (an id pushed without a valid `enc` shows "Approval needed" and no buttons). The buttons are a `LiveActivityIntent` with `authenticationPolicy = .requiresAuthentication`, so iOS asks for Face ID or the passcode before the decision runs, then the same background path as the notification actions, one decision at a time per approval (nonce fetched from the pinned, paired Mac over the tailnet, fingerprint checked, `approval.decide` rate limited and audited). Tapping elsewhere only opens the app on that agent, which validates both ids and decides nothing. Tokens live only in collied's `push.json` (0600) and collie-core memory, are never logged or audited, are bound to the registering device's `StableID` (another paired device can neither replace nor end them) and are dropped on revoke, on `Unregistered`/`BadDeviceToken`, on end, when the terminal is gone and 8 h after the activity first registered (ActivityKit's activity lifetime), so a dead activity stops receiving plaintext; at most 8 per device, one per terminal (built). The alert that expands the Dynamic Island is the approval alert itself, under the same rules (a new prompt alerts, the same prompt reissued within 30 s does not), and replaces the approval notification on that device, so a flapping agent cannot turn it into an alert stream (built in collied). |
| Residual | Anyone who sees the locked phone sees the followed agents' names, workspaces, whether they wait for approval and the Approve and Deny buttons, but not the command. With the APNs key and a token, an attacker can make an activity show any status or text until it ends, including a fake "Approval needed"; buttons need an `enc` sealed under the notification key, and a decision still needs an unlock and the Mac's nonce. `enc` is bound to the approval id but not to the terminal, so such an attacker can replay a real approval's `approvalId` and `enc` onto another followed agent's activity: the real command shows, under the other agent's name. |
| Phase | Built; to be verified on device. |

### Lock-screen and in-app approval

| | |
|---|---|
| Assets | The decision on a blocked agent |
| Attack | Someone holding the phone approves or denies from a notification or from the app, or a fake alert tricks the owner into an action. |
| Mitigations | Lock-screen Approve and Deny are `authenticationRequired` on the notification and `.requiresAuthentication` on the Live Activity's intent: iOS asks for Face ID or the passcode before the app runs; collie adds no check of its own there (built for notifications). "Approve always" is not offered on the lock screen. In the app, each decision first passes LocalAuthentication `deviceOwnerAuthentication` with a fresh `LAContext`, so one unlock never covers a later approval (built). The background decision runs a 20 s capped one-shot session: never a Tailscale login (`NeedsLogin` fails at once as `Unauthorized`), pinned Mac `StableID`, paired `hello`, then the nonce from the Mac; the follow-up notification claims success only on `applied` (built). |
| Residual | The lock-screen gate is iOS's unlock and nothing more: a device unlocked recently enough for iOS to skip the prompt, or a known passcode, passes it. The alert title and body come through Apple and are shown before any check. |
| Phase | Built; timings to be measured on device. |

### Apple Watch approvals

| | |
|---|---|
| Assets | The decision on a blocked agent; the commands, agent lines and plan usage shown on the watch |
| Attack | Someone wearing or holding the owner's watch approves or denies, a watch message claims to be allowed, or a watch request names an approval or an answer the phone never showed. |
| Mitigations | Watch decisions are off by default; turning them on in the iPhone's Settings needs LocalAuthentication `deviceOwnerAuthentication`, and turning them off needs nothing. On every request the phone re-reads the setting from `prefs.json` (missing, unreadable or before first unlock: off) and trusts no flag from the watch. It decides only an unexpired approval, and an answer it offered, that is in the last application context it sent the watch; anything else is refused with nothing sent. A leaked notification key (from `push.json` or a Mac compromise, which already exposes far more; from the phone's Keychain) lets whoever also has the APNs payloads read past and future alert contexts for that Mac until the phone pairs again; it grants no decision, since the nonce never travels in a push. With a leaked APNs key as well, it also lets an attacker forge an alert whose body the NSE shows as genuine context. |
