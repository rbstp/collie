# Threat model

Scope: collied on a Mac or Linux machine (a systemd user unit on Linux), Collie.app on the iPhone, the tailnet between them, herdr as collied's local backend, APNs and the publisher relay. Computer and phone each run their own user-owned embedded Tailscale node, with no OS VPN profile. Tailnet configuration is in [tailnet.md](tailnet.md), design in [architecture.md](architecture.md).

## Trust boundaries

- **Tailnet to collied.** collied's tsnet listener (TCP 8457 by default) is the only network entry point. Before the WebSocket upgrade, each connection passes, in order: the whois gate (untagged, not shared in, owned by the positive embedded self user bound before listening, and either a paired `StableID` with its paired user and pinned TLS key, or an open pairing window); mutual TLS against the pinned key (any P-256 key in a pairing-only session); the same gate again under the peers, pairing and sessions locks, which must agree, so a pairing or revoke mid-handshake refuses it. A fail-closed method allowlist then rejects unknown methods before decoding params, denies unknown fields and keeps herdr's privileged methods unreachable. Terminal methods, a class of their own, need `[terminals] enabled = true` (else `terminals_disabled`) and a grant signed by the phone's terminal key.
- **collied to herdr and herdr-core.** Same UID: nothing running as the user is a boundary. On Linux, the systemd unit's sandboxing is defense in depth, not a boundary against the same UID.
- **Tailscale control plane.** Trusted for node identity: whois and the phone's netmap check both come from it.
- **Apple and the publisher relay.** They see push metadata, never private display content, which is authenticated ciphertext ([Apple sees push payload metadata](#apple-sees-push-payload-metadata)).

Computer nodes are user-owned, not tag-confined: they get their user's tailnet privileges and normal key expiry, so a compromised daemon can use whatever network access the user's policy permits; Collie's mutual TLS and same-user admission protect only its own sessions. Neither embedded node installs an OS VPN profile or touches a native (for example corporate) Tailscale client's account, state or routes. Still to test before App Store submission, since static source and local control tests do not establish them: pairing on a physical device, reconnect and background recovery, and coexistence with an active corporate VPN.

## Threats from the spec

### Stolen phone

| | |
|---|---|
| Assets | Paired session (read and control of agents); phone node keys |
| Attack | A thief opens the unlocked app, or unlocks the phone, and drives agents or answers approvals. |
| Mitigations | iOS passcode and data protection on the node state. Revocation: `collied peers revoke` plus removing the node in the admin console ([tailnet.md](tailnet.md#revocation)); node key expiry (Tailscale default 180 days) bounds a forgotten one. Closing a pane or workspace needs `confirm: true` (else `confirm_required`), which the phone sets, so it guards only against accidents. Rate limits per paired `StableID`: frames 20/s, burst 40; `attachment.chunk` and `file.chunk` 128/s in their own bucket; `approval.decide` 1/s, burst 5. The audit log records every method except `hello`, `flock.snapshot`, `approval.list`, `usage.costs`, `file.chunk`, `file.close`, `attachment.chunk`, `attachment.abort` and an issued `terminal.challenge`, and of a run of frames over the limit only the first (as `rate_limited`). Approval decisions need an iOS unlock on the lock screen, LocalAuthentication in the app ([approvals](#lock-screen-and-in-app-approval)); terminals, off by default, need a grant signed after Face ID or the passcode ([terminals](#shell-input-from-the-phone)). |
| Residual | Until revoked, an unlocked phone drives agents (prompts, keys, new tasks, closes) with no per-action check, and an agent can run any command. Only approvals and terminal grants ask for Face ID or the passcode, so the terminal grant does not make an unlocked phone safer as a whole, and a thief who knows the passcode passes both. |
| Phase | Revocation and approval authentication: built. An app-level gate for the other drive methods: not planned. |

### Leaked pairing QR

| | |
|---|---|
| Assets | Pairing code; the machine's node name, `StableID` and TLS key pin (public) |
| Attack | Someone captures the QR or invite URI (`--show-uri`) from the terminal, a desktop window, scrollback, a screen share or recording, or a herdr pane other same-UID code can read, and pairs their own device. |
| Mitigations | The code alone grants nothing: pairing is offered only to an untagged, not-shared-in node owned by the verified embedded self user (even before the first pairing), while a locally opened window is active. One window at a time, 120 s, burned by the first `pair.complete`, right or wrong. With the right code, collied shows the candidate's device label, node name, `StableID`, login name and user ID and asks y/N on the machine (60 s timeout). The code is compared in constant time, carried in the URI fragment and redacted in `Debug`. The same-user gate holds even when a broader policy lets other users reach collied's port. |
| Residual | A node logged in as the owner (account compromise) can race the window at any time. Any node admitted to a pairing-only session can burn an open window (denial of pairing only). The terminal's QR and the `--show-uri` URI stay in scrollback and recordings; a capture is as good as a scan if used live within the 120 s, and useless once burned or expired. The host name and node ID in the QR are not secret. |
| Phase | Built |

### Malicious herdr plugin on the Mac

| | |
|---|---|
| Assets | Everything on the computer (Mac or Linux); the phone's view of agents and approvals |
| Attack | herdr plugins are unsandboxed code running as the user with the full herdr CLI: a plugin can drive every pane and the control socket, read collied's data dir (node keys, `tls-key.json`, `peers.json`, `.p8`; on Linux, decrypt the APNs credential), and write pane text that collied turns into approval snippets to mislead the phone. |
| Mitigations | None on the computer: same UID is out of scope for file modes. Snippets are capped at 200 characters with controls, bidi and format characters stripped, so they cannot inject escapes into the phone UI. Claude Code's reason for asking gets the same cap with terminal escapes dropped, and stays in the snippet if it carries any other control, bidi or format character. Decisions send only `up`, `down`, `enter` and `esc` (plus `tab` and the user's note), never pane text. |
| Residual | Full compromise of the computer ([same-UID malware](#same-uid-malware-on-the-mac)), including a fake but well-formed Claude Code menu that shows the phone a fake approval. |
| Phase | Built as far as it goes (Keychain limits: [same-UID malware](#same-uid-malware-on-the-mac)); otherwise not planned: install only trusted plugins. |

### Compromised Tailscale coordination plane

| | |
|---|---|
| Assets | Node identity, on which every collie authorization decision rests |
| Attack | The control server (or a stolen admin account) adds a node with its own key, the phone's `StableID` and the owner's user ID; changes grants and ownership; or points the phone's netmap at a fake machine. |
| Mitigations | Protecting the admin account (IdP, MFA) is up to the user. collied binds the owner to its positive embedded self identity before listening; each side pins the other's `StableID`, the owner's user ID and untagged, unshared state. These pins stop casual misconfiguration, not a lying control plane; the y/N prompt catches a new device only during pairing. Mutual TLS does not depend on Tailscale keys: the phone pins the machine's TLS key from the QR (out of band), and collied pins the phone's Secure Enclave key from the confirmed pairing, so an injected node with the phone's `StableID`, or a fake machine in the netmap, fails the handshake. |
| Residual | Low: a lying control plane can still cut or delay traffic and learn which nodes talk, but cannot get a full session without the phone's Secure Enclave key, or pass as a machine without its TLS key. |
| Phase | Built (Phase 6). |

### Replayed notification

| | |
|---|---|
| Assets | Approval decisions |
| Attack | An old push (or a captured approval decision) is replayed to approve something again or something else. |
| Mitigations | The push carries no nonce, only `approval_id` and `node_id` as lookup keys; the app validates both and trusts nothing else in it. A lock-screen action fetches the nonce from the pinned, paired machine over the tailnet (`approval.list`) and decides there. The nonce (32 random bytes; malformed values rejected; redacted in `Debug`) is compared in constant time and burned by the first attempt past the rate limit, whatever its result; a burned id answers `approval_already_resolved`. Approvals expire after 10 minutes, and `apns-expiration` matches. Every attempt within the per-peer frame limit is audited, replays and expired ones included. Decisions bind to a fingerprint and fail as `superseded` if the prompt changed ([Approval TOCTOU](#approval-toctou)). An opaque terminal-derived collapse id makes a reissued alert replace the dead one. |
| Residual | A replayed or stale push shows a notification whose `approval_id` no longer resolves; acting on it reports that the approval is no longer pending and nothing was sent. While the agent stays blocked, each reissue can bring a fresh alert for the same terminal. |
| Phase | Built |

### Leaked APNs key

| | |
|---|---|
| Assets | `.p8` key (team wide), device tokens |
| Attack | With the key and a device token, an attacker sends arbitrary pushes to Collie (or, since the key is team wide, to any app of the team) to phish the user. |
| Mitigations | A dedicated, revocable key per machine, with its own key ID and never in GitHub ([release.md](release.md)): a leaked one is revoked in the portal without touching the others. `collied apns import` moves it into the macOS login Keychain, readable without a prompt only by collied signed with the team's Developer ID (`just collied-install`), or on Linux into a systemd credential or 0600 fallback file ([APNs key storage on Linux](#apns-key-storage-on-linux)), then offers to delete the original. `collied doctor` warns about a `key_path` config (on Linux, when `systemd-creds` works) and about a `.p8` in collied's `apns` dir other than the configured `key_path`. Pushes carry no nonce and cannot create or decide an approval ([Replayed notification](#replayed-notification)). |
| Residual | A leaked key can submit its own fallback text if the notification extension does not run; without the notification key it cannot authenticate private display content, and the app rejects unauthenticated decision actions. A forged background push naming a genuine `approval_id` (16 random bytes, seen only by Apple, the publisher relay when used, the paired devices and the machine) can remove that alert from the phone; the approval stays pending in the app. Copies outside the Keychain or credential (the download before import, the password manager backup) are protected only by where they sit. |
| Phase | Built |

### Phone node key extraction

| | |
|---|---|
| Assets | Phone node keys, which pass the whois gate as the paired phone |
| Attack | Keys read from the device (forensic tools, jailbreak, exploit) or a backup, then used from another machine. |
| Mitigations | App sandbox; the state dir is 0700, `completeUntilFirstUserAuthentication` and excluded from backups; collie-core refuses one with group or world access or another owner. Revocation and key expiry as for a [stolen phone](#stolen-phone). |
| Residual | Code in the app's sandbox can read the node key files after first unlock, but they do not suffice: collied also requires the phone's Secure Enclave TLS key, which cannot leave the device (`ThisDeviceOnly`, usable after first unlock), though such code on the unlocked phone can use it there. |
| Phase | Secure Enclave TLS key: built (Phase 6). Backup exclusion for the node state: built. |

## Threats from the design

### Same-UID malware on the Mac

| | |
|---|---|
| Assets | herdr, collied's data dir, the APNs key, the control socket |
| Attack | Any process running as the user controls herdr, reads node keys, `tls-key.json` and `peers.json`, and uses the 0600 control socket. |
| Mitigations | None by design for herdr and collied's files: the same UID already owns every shell. The 0700 data dir, the 0600 files and control socket, and the socket's peer UID check stop only other local users. The macOS APNs key is the exception: its Keychain item's ACL trusts only collied's designated requirement (Developer ID Application, team `RM3UT3MMSR`, identifier `dev.rbstp.collied`; the binary is signed with the hardened runtime), so other programs need a Keychain prompt to read it; Linux has no such exception ([APNs key storage on Linux](#apns-key-storage-on-linux)). The systemd unit's sandboxing (`NoNewPrivileges`, `ProtectSystem=strict`, a system call filter and more) limits a compromised collied, not other same-UID processes, and a user manager skips it where unprivileged user namespaces are unavailable. |
| Residual | Full compromise of the computer side. Malware can replace collied or its keys, edit `collied.toml` and `peers.json` (owner, paired `StableID`s) and answer the y/N prompt, so the gate protects nothing. Only the tailnet policy, which needs the admin account to change, keeps other users' devices out, and broad grants can admit them: user-owned nodes are not confined service identities. With the node keys and `tls-key.json` it can impersonate the computer to the phone from anywhere, with fake state or approvals. Through the control socket's hook request it can report a tool call other than the dialog's, so the alert names another call; the decision still binds to the screen's fingerprint, and the in-app approval also shows the screen's snippet. macOS Keychain limits: malware can raise a prompt the user may accept, or run the signed collied itself (with its own `--config` or `HOME`) to push with the key without holding it; anyone with the login password can change the ACL or export the item; a `key_path` config or an undeleted `.p8` gets none of this protection. On Linux, malware reads the key and can push from anywhere until the key is revoked. |
| Phase | Built (Keychain item, systemd credential). Otherwise out of scope. |

### herdr-core (Herdr 2)

| | |
|---|---|
| Assets | Every terminal a herdr-core core runs, and what its API reaches beyond them: programs and files on this and every machine the core added (`machine.exec`, `file.*`), documents other apps read (`doc.*`), the core itself (`server.stop`) |
| Attack | A phone, or collied acting for it, reaches the core's wider API or another machine through it; a socket some other process placed where collied looks speaks for the core; a terminal program's status, title or name misleads the phone; the starter's environment reaches every terminal; a session bound to the wrong terminal shows another conversation in Chat or names another call in an approval. |
| Mitigations | collied never starts a core and finds its socket as `hc` does, from its own environment; it refuses a socket served by another user (the peer's uid, read with `peer_cred`, must be its own), which `collied doctor` reports as a failure. It calls only `hello`, `events.subscribe`, `terminal.get`, `terminal.read`, `terminal.send`, `terminal.keys`, `terminal.attach`, `terminal.run`, `terminal.kill` and `terminal.rm` (`server.status` from `collied doctor`), never `machine.*`, `file.*`, `doc.*`, `server.stop`, `server.restart`, `terminal.put` or a template; the client refuses any other method before it writes. The phone reaches the core through `pane.close`, which ends and removes only a terminal collied lists as an agent: its address is checked against the followed core's terminals, and `workspace.close` on the core's group is refused, so no phone call ends every terminal in it. Screen reads (`agent.read`, `pane.read`, `agent.watch`, `agent.draft`) attach only to a terminal collied lists as an agent, always watch-only (`observe`), so the core takes no input from the attach and never sizes the terminal to it; collied sends nothing on the stream but credit and close. Input reaches a terminal collied lists as an agent only through the phone calls and checks a herdr agent's input takes ([Prompt injection into the terminal](#prompt-injection-into-the-terminal)): `terminal.send` for prompts and typed answers, `terminal.keys` for the closed `Key` list, Ctrl+End and a notice digit, and, for the slash token and an approval note only, a typing attach at the terminal's current size that writes that text in one frame and closes. An agent with no OSC 7501 status takes no input from the phone, since nothing would tell collied it shows a dialog (Copilot CLI never reports; Claude Code reports nothing at its folder trust prompt, whose highlighted option a prompt's Enter would pick). Its emulator answers no query and keeps titles, clipboard writes and links to itself; only SGR reaches the phone, as for herdr. A frame is at most 16 MiB, a read's paint ends within a second of its first bytes, an emulated screen is at most 1000 columns by 500 rows whatever size the core reports, and a watch keeps at most 1000 rows of history. Terminals on other machines (`box/t7`) are skipped, so no phone call names another machine. Focus on a herdr-core agent is refused before any herdr or herdr-core call. `task.new` reaches `terminal.run` only while herdr does not answer, behind the gates and checks of a herdr task ([Task folders from the phone](#task-folders-from-the-phone)): the program is the `claude` or `codex` CLI collied finds by absolute path on the machine (never a bare name, which the core would take for a template, and never one the phone names), its arguments are collied's own (a checked session id, the ultracode setting, Codex's `--no-daemon`), its folder resolves under the roots, and it runs on this machine only, as `/usr/bin/env` with `-u` for herdr's six `HERDR_*` and Claude Code's ten session variables, so the starter's herdr pane identity and Claude Code messaging socket and token never reach it. A worktree task's `git worktree add` and an archive's `git worktree remove --force` run in the clone's environment (no prompt, no inherited `GIT_*`) on a checkout path collied built or checked under the roots; an archive ends only task-labelled herdr-core terminals whose start or foreground folder lies in the checkout it recorded for that task. Of the foreground process collied keeps only the basename of `argv[0]` when it is `claude`, `codex` or `copilot`, never the rest of `argv`. Status, title and name are the program's own words, shown as text like herdr's titles. A blocked report's `kind` (`permission`, `question`) only decides whether collied parses a menu from the screen, as herdr's rule id does; its `msg` is never read, and options, snippet and fingerprint come from the screen. `collied doctor` checks that the socket's folder is 0700 and the user's, and warns when the core's holder process holds `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` or `CLAUDE_CODE_CHILD_SESSION`, reading variable names only. Sessions: a Claude Code session comes only from `sessions/<pid>.json` for the terminal's own foreground pid, opened without following symlinks, size-capped, and trusted only while that pid is alive and started no later than the file says. A Codex session comes from the control socket's `session` request (same-UID, peer uid checked), kept only for an address the core lists, a plain-UUID session id, and a reporter whose process ancestry reaches that terminal's foreground process through exactly one `codex`, so a shared Codex app-server reporting with the environment of the terminal that started it is refused; it holds only while that process leads the terminal. Session ids become file names only after the plain-UUID check. |
| Residual | A program's output is parsed in collied's process by `alacritty_terminal`, as a desktop terminal would parse it. No authentication, as for herdr: any same-UID process can drive the core and every machine it added, or place a socket where collied looks before a core starts and feed it agents to list (another user cannot: the peer uid check refuses it) ([Same-UID malware on the Mac](#same-uid-malware-on-the-mac)). The starter's environment reaches every terminal: a core started inside a herdr pane running Claude Code gives its terminals that pane's `HERDR_*` identity and the Claude Code session's messaging socket and token, a channel into that session and into herdr speaking for that pane; collied cannot change the core's environment: it strips those variables from the agents it starts, and only `doctor` reports a core that holds them for the terminals others start. Screens saved by the core outlive their agents on disk. A program can report any status, title or name, so a card can claim `blocked` or `idle` falsely: a program reporting `idle` while it shows a dialog takes a prompt's Enter into it, as a herdr agent whose dialog herdr does not detect, and one reporting `blocked` with a menu on screen raises an approval, as a screen herdr matches would. Any same-UID process can write a session file for a live Claude Code pid, and any process a terminal's own Codex runs (tool commands, MCP servers, other hooks, a prompt-injected command) sits under its single `codex` and can report any session id for that terminal, so Chat would show another of the user's conversations; a process outside that tree cannot get under it by naming itself `codex`. This crosses no boundary. The `collie.kind` and `collie.worktree` labels that mark a task and its checkout can be set by any same-UID client of the core, a prompt-injected agent included (through `HC_TERMINAL_SOCKET` and `hc run --label`), and archive trusts them: such a terminal can make a checkout under the roots removable, or keep its own folder from being refused, also without crossing a boundary. |
| Phase | Built: listing, status, sessions, close, screen reads, input and approvals, and task start, resume and archive while herdr does not answer. |

### Menu bar app

| | |
|---|---|
| Assets | The invite (pairing code) while its QR is shown; the y/N decision on a candidate phone; collied's state |
| Attack | Another app or a stray click approves a phone; the invite leaks from the app; phone-provided strings disguise the candidate; the app becomes a way in from the network. |
| Mitigations | Only a local client of the 0600, same-UID control socket (`pair` with its `confirm` answer, `peers_list`, a read-only `watch`); no network listener. Developer ID signed, hardened runtime, no entitlements. The invite is never shown as text, copied, logged or persisted; window restoration is off. Pair is not the default button and is live only 1 s after the candidate appears; one answer per candidate, never automatic; collied refuses after 60 s; closing the window cancels. Candidate strings are escaped like `collied::printable` (controls, format and bidi characters, combining marks, default-ignorable characters, non-ASCII spaces). First-run Set Up runs only the fixed installed executable in Terminal (a private, self-cleaning command file with a quoted literal path), and the CLI still checks its path and signing identity. Interactive login opens only the exact Tailscale HTTPS login authority, once; the printed URL remains the fallback. |
| Residual | Same-UID code can drive the control socket or the app, and can already answer the y/N prompt ([same-UID malware](#same-uid-malware-on-the-mac)). The QR is on screen for up to 120 s ([leaks](#leaked-pairing-qr)). |

### `collied setup`

| | |
|---|---|
| Assets | The y/N decision on a candidate phone; the launchd agent or systemd user unit; `collied.toml` and the APNs key |
| Attack | Piped input (`yes`) confirms a pairing without a human; setup installs an unsigned agent or a service running a build output, leaves the key or config readable, or on Linux logs in a new node over the paired one. |
| Mitigations | Setup refuses to start unless stdin is a terminal and the running binary is the regular file `~/.cargo/bin/collied` (on Linux, or the package-owned `/usr/bin/collied`), on macOS Developer ID signed as `dev.rbstp.collied`, so the service never runs a build output that the next `cargo build` replaces unsigned, nor one reached through a symlink. ### APNs key storage on Linux

| | |
|---|---|
| Assets | The machine's APNs `.p8` key; the systemd host secret `/var/lib/systemd/credential.secret` |
| Attack | A same-UID process, another local user, root, a polkit admin, or someone with an offline copy of the file or disk reads the key from `<data dir>/apns/<key ID>.cred` or the fallback file. |
| Mitigations | **Import** ([architecture.md](architecture.md#apns-key-on-linux)): `collied apns import` applies the macOS file checks (`[apns]` ids, no file named for another key ID, a user-owned 0600 regular file opened with `O_NOFOLLOW`, an ES256 key), encrypts with `systemd-creds --user` under the name `collied-apns-<key ID>`, writes the credential itself (0600, `O_NOFOLLOW`, atomic), verifies it decrypts to the same key before and after storing, then offers to delete the original if it is still the same inode. **Seal:** AES-256-GCM under a key derived from the host secret (root, 0400), the TPM2 when usable, the uid, user name and machine-id, so a copy of the `.cred` alone decrypts nothing, and a TPM2 seal also needs that chip. | Residual | No per-application binding: any same-UID process decrypts the credential without a prompt, unlike the macOS Keychain item ([same-UID malware](#same-uid-malware-on-the-mac)). Root, and anyone who passes polkit admin authentication, decrypts it too. An unprivileged caller cannot choose the seal: systemd uses host key and TPM2 when a TPM2 is usable and sealing to it succeeds, else host key only; doctor shows which. Without a usable TPM2 (the dev machine: T2 Mac hardware, where `systemd-analyze has-tpm2` reports partial), whoever reads the unlocked disk (host secret, machine-id, credential) can decrypt the key elsewhere. The credential stops decrypting after an OS reinstall, a machine-id, uid or user name change, or a restore to another machine: import again from the backup. The 0600 fallback is protected by its mode only, like `key_path` on macOS. |

### Prompt injection into the terminal

| | |
|---|---|
| Assets | The shells behind herdr panes and herdr-core terminals |
| Attack | A prompt or key sequence sent from the phone, or a compromised phone session, escapes the agent and runs commands in the shell. |
| Mitigations | `PromptText` rejects ESC and every C0/C1 control except newline and tab, so a prompt cannot embed a paste terminator. `Key` is a closed list of nineteen keys (no ctrl+d, ctrl+z, ctrl+r, ctrl+j, ctrl+m, ctrl+o or ctrl+t). herdr's privileged methods are unreachable. `agent.type_text` sends bracketed-paste text and Enter in one ordered write after validating the live agent identity and authorization, and by design accepts approval answers without parsing their prompt ([Keys and text on a blocked prompt](#keys-and-text-on-a-blocked-prompt)). Shell input needs enabled terminals and a live grant ([Shell input from the phone](#shell-input-from-the-phone)). Approval notes are one line, typed only into a verified amend field. Narrow writes, which share a lock and recheck authorization: `agent.scroll_bottom` sends only fixed Ctrl+End bytes to a scrolled-up Claude Code screen; `agent.answer_notice` sends one listed digit, no Enter, only above an empty input box under the displayed label; `agent.slash_draft` pastes a bounded slash token, no Enter, only into an unblocked, unscrolled Claude Code input box, then verifies it; draft replacement clears only the exact expected text in a readable, ordinary input box and rechecks that it is empty before prompting. Enter and Ctrl+Enter are refused for mirrored slash commands while Claude Code is not blocked. Agent startup and new folders stay within configured task roots and agent kinds; occupied panes are refused; authorization is checked before every write. |
| Residual | If the agent exits between herdr's foreground-agent check and the queued text and delayed Enter, the shell receives the prompt; closing that gap needs conditional input in herdr upstream. herdr-core has it: a prompt or typed answer to a herdr-core agent the check saw `idle` or `working` carries `if` with that status, so the core types only while the program still reports it, which narrows the gap to the core's own check. `if` takes no other status, so to a `done` or `error` agent the prompt goes without it and only the core's refusal of a `blocked` program applies. Keys and the typing attach carry no condition, and the core holds a send or keys call until nobody has typed for about 3 s, counting collied's own typing attach (measured 2.8 to 3.3 s on 0.1.16); a held call is delivered whenever the typing pauses, with no bound and even after collied gave up on it: collied waits up to 15 s for a prompt, a typed answer or keys from the key strip, and up to the decide budget (6 s, 9.5 s with a note) for an approval's keys. So a key collied sends right after its own typing attach lands about 3 s after collied's last read: an approval note's Enter therefore waits the hold out and reads the dialog again first ([Approval TOCTOU](#approval-toctou)), while the slash mirror's next clear keys (Ctrl+E, Ctrl+U, Backspace, Ctrl+K) are not held back, as none of them answers a dialog. A key held because the user types on the machine lands once the user stops, after collied's checks; the user at the machine is the owner, and the same keys then reach whatever they left on screen. A program that reported a status and exited, or was suspended, leaves it in herdr-core 0.1.16; collied lists no terminal a shell leads, so a shell is never prompted as the agent that left it once the core has seen the shell lead; the core's foreground check lags a few hundred ms (0.38 to 0.49 s after Ctrl+Z, measured), and a write checked within that window still goes to the shell. A `state_change_seq` condition on `terminal.keys`, or a way to cancel a held call, would close the key gaps upstream. Text an agent reads from a repository can still steer the agent; that is outside collie. A dialog Claude Code draws between `agent.slash_draft`'s last read and its write receives the token as a paste: the `agent.answer_notice` gap, narrower because the token starts with `/`, is never a bare digit and carries no Enter. The iOS keyboard's dictation and paste reach the prompt field like typing, so a dictated or pasted `/word` can show in the machine's input box; it is never submitted without a send. |
| Phase | Built; herdr conditional input: upstream proposal. |

## Desktop download verification

Before replacing the installed executable or changing its service, the macOS installer requires a strict signature, the expected daemon identifier and publisher team, and Apple's explicit notarized requirement. The standalone executable check forces an online ticket lookup; on failure the existing binary and service stay untouched. App and disk-image policy checks are separate. None of these replaces accepting a quarantined download on a clean Mac with Gatekeeper enabled.

## Publisher relay

The Worker in `relay/`, deployed at `collie-push.rbstp.dev`, accepts only HMAC-authorized, registered destinations and strict generic or encrypted public envelopes. It stores no notification payloads, cannot issue approval decisions and has no enrollment bypass. An hourly cleanup deletes expired relay records within 14 days of the last grant expiry, even at the exact global control and enrollment caps; D1 Time Travel keeps them restorable for 30 days after deletion. Production resource limits rest on measurements and soft controls, not a spending cap; [relay.md](relay.md) covers them and the storage, privacy, abuse and deployment constraints.

## Attested relay control

The relay control path trusts pinned Apple certificate chains and a fixed publisher app/environment policy. App Attest proves app integrity, not a person's identity or token ownership; the phone's confirmed pairing authorizes machine-specific, exact-destination grants. An assertion needs a valid ECDSA signature over the SHA-256 nonce of the authenticator data plus the client-data hash. Accepting a retained AT flag admits no credential bytes and skips no App ID, extension, signature or counter check. HMAC challenges bind canonical operations and the exact prior durable counter/epoch, so even a newly signed higher counter cannot replay one. A D1 trigger failure rolls back counters, quotas and authorization together. A stolen grant can send bounded pushes only to its route until revocation or expiry, and carries no approval or decryption authority; revocation can race an already authorized in-flight attempt.

The phone client pins the publisher's endpoint, refuses redirects and runs its whole control transaction under an explicit FIFO gate across actor awaits. An offline revocation keeps minimal retry credentials and stays pending until it succeeds or expires; local removal cannot guarantee immediate remote denial. Raw destinations and verified attestation metadata stay in bounded D1 records until retention cleanup, with no notification keys, payloads or sensitive request logs; [relay.md](relay.md#attested-control-contract) has the exact control contract and retention bound. Measured full attestation exceeded the Free plan's CPU budget, hostile invalid-nonce cases included, so the relay runs on Workers Paid with the internal crypto actor below ([validation report](reviews/relay-free-tier.md)).

## Internal relay crypto prototype

The crypto actor has no HTTP handler; the public Worker reaches it through an internal binding under one fixed object name, forwarding bounded verification inputs only after its admission, body and challenge checks. The actor takes publisher/environment/version policy from trusted bindings and uses its own clock; callers cannot supply other roots or validation context. No destinations, notification plaintext, decryption keys or authorization decisions enter actor storage. Verification stays separate from D1's atomic replay/epoch/quota guard. Unavailable or exhausted compute fails closed, with no expensive inline fallback. Paid validation adds shared control/enrollment limiter keys before D1 or crypto, beside source and installation keys, and a provisional 250 ms script CPU ceiling. Shared limiter counters are local to a Cloudflare location and permissive: distributed attempts still consume billed requests and may reach D1/crypto before committed daily quotas reject them. Neither mechanism is an account spending cap, and shared exhaustion can deny legitimate enrollment or revocation. The singleton is an availability bottleneck; native queuing and platform quota exhaustion can deny legitimate requests. One small guarded Free-account cycle completed within the observed CPU limits; full production CPU distributions, actor duration/capacity and fresh Collie enrollment remain unvalidated ([relay.md](relay.md#internal-crypto-prototype)).

## Relay sender outages and stale authorization

collied takes a fixed HTTPS publisher endpoint from its own push mode (relay and direct APNs are mutually exclusive), never from a phone-supplied URL. It sends only a bounded grant in the sensitive Authorization header and an encrypted or generic public envelope, refuses redirects, and bounds response size and attempt time. No grant, destination or payload reaches logs or doctor output; only the private `push.json` keeps route grants, each with its exact paired device or activity.

Retries hold at most 64 encrypted pending destinations in memory, with no durable payload queue. Routine updates coalesce to at most one per 60 s for each agent and phone; transient errors and Cloudflare non-JSON limit responses pause attempts with bounded exponential backoff and jitter. Daily quotas stay server-authoritative across all machines. Before every attempt, the sender rechecks pairing, exact token/generation, grant expiry, live approval/expiry and activity replacement. APNs expired/unregistered invalidations remove only the matching old destination generation; configuration errors keep registrations. A genuine OS token registration can authorize a newer generation for the same token through the attested control gate; polls and foreground snapshots cannot force repeated rotations, and late invalidations cannot revoke that replacement or another installation, app or activity route. An ambiguous successful response can duplicate a display but grants no approval authority. Offline revocation and an already authorized in-flight push keep their races ([Attested relay control](#attested-relay-control)). Push outages do not block authenticated tailnet or local desktop operations.

## Local Simulator development trust

The local-only Simulator entry pre-provisions a fresh software key into private, isolated D1 storage, refuses enrollment, fixes sandbox APNs and uses separate send secrets. Its control assertions still pass the production verifier and atomic counter/epoch checks. Production cannot authenticate this key through enrollment or verify the local HMAC grants; never copy development database rows or secrets into production. Swift development import exists only in DEBUG Simulator builds; the daemon loopback switch is debug-only and absent from Release artifacts. Real APNs keys stay locally held operator credentials, never provisioning fixtures. [Simulator testing](simulator.md) has the exact boundary and limits.

## Local VM test boundary

The [VM and Simulator harness](vm-simulator.md) is a Debug-only trust island: a disposable macOS guest, a separately recorded host Simulator, fresh software identities, synthetic tailnet authorization and a private mock publisher database. Its fixed local control hook needs explicit opt-in plus owned private marker files; unsupported Rust frameworks fail before Swift creates state or identity. No physical-device or Release artifact exposes the hook. Ordinary pairing confirmation, identity pins and mutual TLS still apply.

SSH host keys come through the local VM guest agent and are verified against a private per-run known-hosts file. The harness forwards only fixed loopback endpoints with a task-only key, disables agent forwarding, shares no host directories and refuses occupied test ports. Reset and teardown touch only recorded test resources. VM image tooling and any guest desktop-control permissions belong to the guest; a CI image with SIP or Gatekeeper disabled cannot prove pristine consumer acceptance. Local mock success proves neither genuine App Attest nor Apple APNs acceptance.
