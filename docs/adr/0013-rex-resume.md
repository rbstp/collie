# ADR-0013: A Claude Code in Rex resumes once, beside its restored shell, which closes only once it runs

- Status: accepted
- Date: 2026-11-23 (#927; revised after two reviews and two field tests on 2026-11-23 and 2026-11-24)

## Context

When the Rex server restarts, or the Mac reboots, Rex restores its sessions, windows and blocks under the ids they had, each block as a new shell. The agent conversation that ran in a block is gone until someone runs its resume command. collied already knows each Rex agent's kind, conversation and folder.

The first design typed the resume command into the restored shell. Review showed screen checks cannot make that safe: in a vi keymap text after the cursor survives Ctrl+E and Ctrl+U and runs with the line, a shell waiting in a builtin `read` looks like an idle prompt and the typed Enter answers it, and a program started between the checks and the write (ssh, a REPL) or a `cd` receives the line.

Checked on a scratch server (Rex.app 0.1.0 build 2104, API revision 19, restore on, its own state folder): after a restart the session and block ids were the same, `server.status` named a new `instance_id` and a new `started_at`, a shell block came back as a shell in the folder its shell was last in, and a block started with a command came back as a shell in that block's folder. Stopping the server with SIGTERM while a program ran in a shell sent no `process_changed` or `child_exited` before the connection closed. Rex has no call that replaces a block's program, but `session.new_split` anchored on a block, followed by `block.close` of that block, leaves the new block in the old one's place: the same split id, ratio and rect, and the focus.

Field tests on the owner's Rex.app:
- The version that closed the shell as soon as the new block started (99f247be) lost the pane of every Claude Code that exited. Claude Code 2.1.331's `--resume ID` fails only with `No conversation found with session ID` when no transcript is found, and Claude Code writes the transcript only with the first prompt while naming the conversation in its pid file from the start; reproduced on a scratch server. Whether every agent in that test had no transcript is not known.
- A prompted Claude Code was not resumed and nothing showed in its pane. That version required an empty prompt with the cursor after a blank and nothing after it, and a real zsh with a two-line prompt and a right prompt never passed (`live_rex_resume`, run against that version, timed out). Which guard refused in the field is not known, since that version logged no wait.

## Decision

- Claude Code only. A resumed Codex reports its conversation only once its first turn starts, and an Antigravity CLI's is not checked live, so neither can be confirmed by its conversation before the shell would close; they are left to a follow-up issue and never recorded. Copilot CLI has no conversation collied binds in Rex.
- Nothing is typed. The agent starts as an argument vector in a new block, `session.new_split` anchored on the restored block (`side: before`) with a shell-flavor block whose `options.command` is what a phone's resume task runs (`/usr/bin/env -u` with each stripped name, Claude Code by absolute path, then `--resume ID`, as `runtime::herdr::agent_args` gives them) and whose `cwd` is the recorded folder. No shell parses it. The new block is given up and the restored shell stays beside it.
- The shell is never closed on the chance that the agent starts. On each tick, an exit is decided before anything else: an exit event or `last_exit`, or a block collied saw that the server no longer lists, closes the new block and keeps the shell. A block missing from the model because its reads failed (`Model::holds`), or while collied is not in sync with the server, is not an exit. The shell closes only once collied has listed the new block for 3 s in a row as a Claude Code running that conversation (its session binding) in the recorded folder (its `foreground_cwd`). Right before `block.close`, collied reads the shell's process and screen once more (the only awaits before the close), then checks from the model, with no await, that the agent still runs that conversation in that folder and has not exited, that the option is on and that the window is open. Otherwise the shell stays; if the agent does not show its conversation in its folder within 30 s, both stay. A collied task's record moves to the new block before the close.
- A restart is a new `instance_id`. collied keeps the instance with its agents in `rex-resume.json` (0600, data folder, flushed on each change) and plans only when it follows another instance than the recorded one, whose `started_at` is less than 90 s before now and not in the future. The plan lasts until 90 s after that start, measured from the planning moment on collied's monotonic clock. A reconnect to the same instance keeps the plan and the grace timers. Planning takes the agents off the record and plans only once that is saved, so a crash or a restart of collied never starts one twice.
- The record holds a listed Claude Code with a bound conversation and an absolute foreground folder, by block id, once the conversation's transcript exists in the folder's project under Claude Code's folder; the transcript is checked again before the start. A Claude Code's foreground folder is its own process's, the folder its pid file names; a `! cd` moved neither (checked). A conversation a live Claude Code process holds (its pid file, alive) waits until that process is gone, since `claude --resume` does not refuse a conversation another process runs. collied reads at most 256 KiB of the record, the limit applying to the read on the descriptor it checked; it keeps at most 256 entries with a valid block id, a lowercase hyphenated UUID and a folder of at most 4,096 bytes, and drops entries before writing until the record fits 256 KiB. A record that cannot be read or parsed is logged with the error's category only. An agent that leaves its block stays recorded for 15 s while collied follows the same instance, since a shutdown ends the agents before the server stops.
- The shell's guard reads no prompt shape: once nothing is typed and the shell closes only after the agent runs, what protects the user is a shell running nothing and a screen nobody changed. A fresh `process` read must show the shell running nothing (the block's own program, or the only process under Rex.app's `login`). collied takes its first read of the screen on the first tick it finds that shell running nothing, not before: while a startup command runs, the screen is still being drawn, and the line editor that shows typed text runs only once the shell is at its prompt. Changes in the 2 s after that first read are taken as the prompt settling (an asynchronous prompt redraws); after them any change refuses the block for good, and the screen must have been unchanged for 2 s before the start.
- Each decision and outcome is logged at warn level with the block id and the kind, never the conversation id or folder: each planned block, a restart that plans nothing and why, each refusal and the guard that refused, each start, each outcome, and each block still waiting when the window ends with its last wait reason.
- The option is on by default. `rex-resume-off` in the data folder turns it off, and turning it off deletes the record. The control socket's `rex_resume` request reads it and sets it, audited, and CollieBar shows it as a menu item; CollieTray has none, since collie follows Rex on the Mac only.

## Consequences

- These are closed with the shell: text typed or a command left at the restored shell's prompt before collied's first read (the first reconcile tick, each second, on which collied follows the new server and finds the shell running nothing) or in the 2 s after it; a program started or text typed between collied's last screen read and `block.close`, one round trip on the local socket; and a startup file waiting in the builtin `read`, which looks like a shell running nothing, so its question goes unanswered.
- A conversation quit less than 15 s before the server stopped gets the agent back.
- The resumed agent is its block's program: when it exits, the block closes, as a task's does, instead of returning to a shell. It gets a new block id, so what the phone keys by terminal id (a star, for example) does not follow it.
- `session.new_split` is in collied's method allowlist, so a Rex server without it is not followed at all. A lost `session.new_split` answer leaves the agent's block beside the shell, never retried; `session.new_split` ends any zoom in that window.
- A prompt that redraws itself after its first 2 s (a clock) refuses its shell.
- `live_rex_resume` runs a real restart of a scratch server with restore on, inside `sandbox-exec` denying every folder under `/Users`, since a restored block runs the account's default shell. Rex.app's own restored login shells were not checked against the owner's server.
