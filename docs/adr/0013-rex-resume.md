# ADR-0013: An agent in Rex resumes once, through the login shell, beside its restored shell, which closes only once the agent runs

- Status: accepted
- Date: 2026-11-23 (#927; revised after two reviews and three field tests on 2026-11-23 and 2026-11-24, and for Codex, Copilot CLI and Antigravity CLI in #934)

## Context

When the Rex server restarts, or the Mac reboots, Rex restores its sessions, windows and blocks under the ids they had, each block as a new shell. The agent conversation that ran in a block is gone until someone runs its resume command. collied already knows each Rex agent's kind, conversation and folder.

The first design typed the resume command into the restored shell. Review showed screen checks cannot make that safe: in a vi keymap text after the cursor survives Ctrl+E and Ctrl+U and runs with the line, a shell waiting in a builtin `read` looks like an idle prompt and the typed Enter answers it, and a program started between the checks and the write (ssh, a REPL) or a `cd` receives the line.

Checked on a scratch server (Rex.app 0.1.0 build 2104, API revision 19, restore on, its own state folder): after a restart the session and block ids were the same, `server.status` named a new `instance_id` and a new `started_at`, a shell block came back as a shell in the folder its shell was last in, and a block started with a command came back as a shell in that block's folder. Stopping the server with SIGTERM while a program ran in a shell sent no `process_changed` or `child_exited` before the connection closed. Rex has no call that replaces a block's program, but `session.new_split` anchored on a block, followed by `block.close` of that block, leaves the new block in the old one's place: the same split id, ratio and rect, and the focus.

Field tests on the owner's Rex.app:
- The version that closed the shell as soon as the new block started (99f247be) lost the pane of every Claude Code that exited. Claude Code 2.1.331's `--resume ID` fails only with `No conversation found with session ID` when no transcript is found, and Claude Code writes the transcript only with the first prompt while naming the conversation in its pid file from the start; reproduced on a scratch server. Whether every agent in that test had no transcript is not known.
- A prompted Claude Code was not resumed and nothing showed in its pane. That version required an empty prompt with the cursor after a blank and nothing after it, and a real zsh with a two-line prompt and a right prompt never passed (`live_rex_resume`, run against that version, timed out). Which guard refused in the field is not known, since that version logged no wait.
- The version that started Claude Code by absolute path through `/usr/bin/env`, from the Rex server's environment (2026-11-24), resumed no Claude Code: each new block printed "This session was started in Code Mode (experimental), which is off, so it can't be resumed" and exited. The owner's interactive shell sets `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE`; the shell flavor's login shell is not interactive, so its startup files never ran. The new block closed as its program exited, so the owner saw the error for a moment and took it for collied closing the shell.

Checked on scratch servers (sandboxed, scratch `HOME`, restore off) and on each CLI with a scratch home:
- `zsh -l -i -c` and `bash -l -i -c` with a single command `exec` it, so the agent is the block's program. With a `claude` function in `.zshrc` the shell stays as the program and the agent is the foreground process, owning its own OSC 7501 record; a zsh or bash alias is `exec`d. The rc's variables and `REX_BLOCK` reached the agent each time. A block with `options: {shell: "none", login: false}` ran `.zprofile` and `.zshrc` once each; the default shell flavor's login shell around the same argv ran `.zprofile` a second time.
- A conversation id no transcript has: Codex 0.171.0 prints "No saved session found" and exits, Copilot CLI (package 1.0.112) prints "No session, task, or name matched" and exits, and the Antigravity CLI prints a warning and goes on (to its sign-in screen on a scratch home).
- A new block whose program exits about a second after it starts closes, whether collied's connection still owns it or gave it up, with no `block.close` from collied; one whose program exits within milliseconds stayed with `last_exit` and its screen. So collied cannot keep a failed agent's output on screen by keeping its block.
- Before any turn, a resumed Codex 0.171.0 with `--no-daemon` holds its rollout open and an `flock` on `thread-writer-locks/<id>.lock` in its own process; without it, the shared app-server holds both and the terminal's `codex` holds neither. A resumed Copilot CLI holds an `flock` on `session-state/<id>/inuse.<pid>.hold` with `inuse.<pid>.lock` naming its pid. The Antigravity CLI cannot sign in on a scratch home, so what it holds and when its `SessionStart` hook reports on a resume were not checked.

## Decision

- Claude Code, Codex, Copilot CLI and Antigravity CLI (`agy`). Each kind is recorded, started and confirmed by what proves its conversation:

  | Kind | Recorded from | Transcript | A live holder | Resumed with | Confirmed by |
  |---|---|---|---|---|---|
  | Claude Code | its pid file's `sessionId` | `projects/<folder>/<id>.jsonl` | a live pid file naming it | `claude --resume ID` | its pid file |
  | Codex | collied's hook, from under the block's `codex` (`--no-daemon` only) | a rollout whose `session_meta` names the id and the folder | an `flock` on its writer lock | `codex resume ID --no-daemon` | the block's process holds the writer lock, locked, and the rollout open |
  | Copilot CLI | the one session with `events.jsonl` and the folder as its `cwd` whose marker the block's process holds | `events.jsonl` | any held `inuse.*.hold` | `copilot --resume=ID` | the block's process holds `inuse.<pid>.hold`, its `.lock` names it, and it started before the marker |
  | Antigravity CLI | collied's hook, from under the block's `agy` | `brain/<id>/.system_generated/logs/transcript.jsonl` | none known | `agy --conversation ID` | collied's hook naming it from the block's `agy` |

  An Antigravity CLI whose hook reports only with its first turn is never confirmed, so its shell and its block both stay.
- Nothing is typed. The agent starts as an argument vector in a new block, `session.new_split` anchored on the restored block (`side: before`) with `options: {command, cwd, shell: "none", login: false}`: `command` is `/usr/bin/env`, `-u` with each stripped name, the account's login shell from the user database (absolute), `-l`, `-i`, `-c` and one string, the CLI's bare name and its resume arguments, so the user's startup files, environment, aliases and functions apply as in their own terminal. Only zsh and bash are used, the shells checked; for any other login shell nothing is started and the refusal is logged. The string holds only words of lowercase letters, digits, `-` and `=`, and the id is a lowercase hyphenated UUID; an id that is not is never recorded. `cwd` is the recorded folder.
- collied gives the new block up at once, so Rex.app sizes it. The shell is never closed on the chance that the agent starts. On each tick, an exit is decided before anything else: an exit event or `last_exit`, or a block collied saw that the server no longer lists, ends the attempt, and collied closes neither block; Rex closes the new one as its program exits. A block missing from the model because its reads failed (`Model::holds`), or while collied is not in sync with the server, is not an exit. The shell closes only once collied has listed the new block for 3 s in a row as that kind in the recorded folder (its `foreground_cwd`) with the kind's proof above. collied then reads the shell's process and screen once more (the only awaits before the close), then checks from the model, with no await, that the agent still runs that conversation in that folder and has not exited, that the option is on and that the window is open. Otherwise the shell stays; if the agent is not confirmed within 30 s, both stay. A collied task's record moves to the new block before the close.
- A restart is a new `instance_id`. collied keeps the instance with its agents in `rex-resume.json` (0600, data folder, flushed on each change) and plans only when it follows another instance than the recorded one, whose `started_at` is less than 90 s before now and not in the future. The plan lasts until 90 s after that start, measured from the planning moment on collied's monotonic clock. A reconnect to the same instance keeps the plan and the grace timers. Planning takes the agents off the record and plans only once that is saved, so a crash or a restart of collied never starts one twice.
- The record holds a listed agent of these kinds with its conversation and an absolute foreground folder, by block id, once the transcript exists; the transcript is checked again before the start. A Claude Code's foreground folder is its own process's, the folder its pid file names; a `! cd` moved neither (checked). A conversation a live process holds, as the table says, waits until it lets go, since `claude --resume` does not refuse a conversation another process runs. collied reads at most 256 KiB of the record, the limit applying to the read on the descriptor it checked; it keeps at most 256 entries with a valid block id, a lowercase hyphenated UUID and a folder of at most 4,096 bytes, and drops entries before writing until the record fits 256 KiB. A record that cannot be read or parsed is logged with the error's category only. An agent that leaves its block stays recorded for 15 s while collied follows the same instance, since a shutdown ends the agents before the server stops.
- The shell's guard reads no prompt shape: once nothing is typed and the shell closes only after the agent runs, what protects the user is a shell running nothing and a screen nobody changed. A fresh `process` read must show the shell running nothing (the block's own program, or the only process under Rex.app's `login`). collied takes its first read of the screen on the first tick it finds that shell running nothing, not before: while a startup command runs, the screen is still being drawn, and the line editor that shows typed text runs only once the shell is at its prompt. Changes in the 2 s after that first read are taken as the prompt settling (an asynchronous prompt redraws); after them any change refuses the block for good, and the screen must have been unchanged for 2 s before the start.
- Each decision and outcome is logged at warn level with the block id and the kind, never the conversation id or folder: each planned block, a restart that plans nothing and why, each refusal and the guard that refused, each start, each outcome, and each block still waiting when the window ends with its last wait reason.
- The option is on by default. `rex-resume-off` in the data folder turns it off, and turning it off deletes the record. The control socket's `rex_resume` request reads it and sets it, audited, and CollieBar shows it as a menu item; CollieTray has none, since collie follows Rex on the Mac only.

## Consequences

- collied runs the account's login and interactive startup files (`.zprofile`, `.zshrc`, `.bash_profile` and what they source) for each resumed agent, as opening a terminal does: whatever they print shows in the new block, and a startup file that waits for input waits there, so the agent is not confirmed and both blocks stay.
- These are closed with the shell: text typed or a command left at the restored shell's prompt before collied's first read (the first reconcile tick, each second, on which collied follows the new server and finds the shell running nothing) or in the 2 s after it; a program started or text typed between collied's last screen read and `block.close`, one round trip on the local socket; and a startup file waiting in the builtin `read`, which looks like a shell running nothing, so its question goes unanswered.
- An agent that exits before it is confirmed loses its block as it exits, so its error shows only for a moment; its restored shell stays, and collied's log says the agent exited.
- A conversation quit less than 15 s before the server stopped gets the agent back.
- Once confirmed, the resumed agent is its block's program (or, under a shell function, the shell's foreground): when it exits, the block closes, as a task's does, instead of returning to a shell. It gets a new block id, so what the phone keys by terminal id (a star, for example) does not follow it.
- A Codex started without `--no-daemon` is never recorded: its hook runs under the shared app-server and is refused, and its terminal process holds no file of the conversation. A resumed Codex is recorded again once its hook reports, with its first prompt, so a second restart before that loses it.
- `session.new_split` is in collied's method allowlist, so a Rex server without it is not followed at all. A lost `session.new_split` answer leaves the agent's block beside the shell, never retried; `session.new_split` ends any zoom in that window.
- A prompt that redraws itself after its first 2 s (a clock) refuses its shell.
- `live_rex_resume` runs a real restart of a scratch server with restore on, inside `sandbox-exec` denying every folder under `/Users`, since a restored block runs the account's default shell, and starts a stand-in Claude Code through the account's login shell, wrapped in a `.zshrc` function. Rex.app's own restored login shells and a `login: false` block in Rex.app were not checked against the owner's server.
