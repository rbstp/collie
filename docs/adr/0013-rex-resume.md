# ADR-0013: A Rex agent resumes once, in place of its own untouched restored shell, never typed

- Status: accepted
- Date: 2026-11-23 (#927; revised after review the same day)

## Context

When the Rex server restarts, or the Mac reboots, Rex restores its sessions, windows and blocks under the ids they had, each block as a new shell. The Claude Code, Codex or Antigravity CLI conversation that ran in a block is gone until someone runs its resume command. collied already knows each Rex agent's kind, conversation and folder.

The first design typed the resume command into the restored shell. Review showed screen checks cannot make that safe: in a vi keymap text after the cursor survives Ctrl+E and Ctrl+U and runs with the line, a shell waiting in a builtin `read` looks like an idle prompt and the typed Enter answers it, and a program started between the checks and the write (ssh, a REPL) or a `cd` receives the line.

Checked on a scratch server (Rex.app 0.1.0 build 2104, API revision 19, restore on, its own state folder): after a restart the session and block ids were the same, `server.status` named a new `instance_id` and a new `started_at`, a shell block came back as a shell in the folder its shell was last in, and a block started with a command came back as a shell in that block's folder. Stopping the server with SIGTERM while a program ran in a shell sent no `process_changed` or `child_exited` before the connection closed. Rex has no call that replaces a block's program, but `session.new_split` anchored on a block, followed by `block.close` of that block, leaves the new block in the old one's place: the same split id, ratio and rect, and the focus. A second field test showed a prompted Claude Code that was not resumed and nothing visible in its pane. The version tested then required an empty prompt with the cursor after a blank and nothing after it, and a real zsh with a two-line prompt and a right prompt never passed that check (`live_rex_resume`, run against that version, timed out waiting). Which guard refused in the field is not known, since that version logged no wait.

## Decision

- Nothing is typed, and the restored shell is never closed on the chance that the agent starts. The agent starts as an argument vector in a new block, `session.new_split` anchored on the restored block (`side: before`) with a shell-flavor block whose `options.command` is what a phone's resume task runs (`/usr/bin/env -u` with each stripped name, the CLI by absolute path, then `--resume ID`, `resume ID --no-daemon` or `--conversation ID`, as `runtime::herdr::agent_args` gives them) and whose `cwd` is the recorded folder. No shell parses it. The new block is given up and the restored shell stays beside it until collied has listed the new block for 3 s in a row as a Claude Code running that conversation, or as a Codex or Antigravity CLI of the recorded kind (a resumed Codex reports its conversation only once its first turn starts, so its binding cannot confirm it); only then, after the second reads below, is the restored block closed, so the agent takes its place. If the new block's program exits first, collied closes the new block and the shell stays (a block not yet in collied's model, or a lost connection, is not taken for an exit); if the agent does not show its conversation within 30 s, both stay. The owner's first field test (2026-11-23, PR #932 at 99f247be) closed the shell at once, and a Claude Code that exited left no pane.
- A restart is a new `instance_id`. collied keeps the instance with its agents in `rex-resume.json` (0600, data folder, flushed on each change) and plans only when it follows another instance than the recorded one, whose `started_at` is less than 90 s before now and not in the future. The plan lasts until 90 s after that start, measured from the planning moment on collied's monotonic clock, so a clock change does not extend it. A reconnect to the same instance keeps the plan and the grace timers.
- The record holds what collied lists: a Claude Code, Codex or Antigravity CLI agent with a bound conversation and an absolute foreground folder, by block id, and a Claude Code conversation only once its transcript exists in the folder's project under Claude Code's folder. Claude Code names a conversation in its pid file from the start but writes its transcript only with the first prompt, and `claude --resume` of a conversation without one prints `No conversation found with session ID` and exits (Claude Code 2.1.331, read in its code and reproduced on a scratch server): this matches the field test's failure. Whether every Claude Code in that test was in that state (never prompted, or cleared with no prompt since) is not known. A Claude Code agent's foreground folder is its own process's, the folder its pid file names; a `! cd` moved neither (checked). The transcript is checked again before the start, and a conversation a live Claude Code process holds (its pid file, alive) waits until that process is gone: `claude --resume` does not refuse a conversation another process runs, so two would run it. It is never read past 256 KiB, and what is read keeps at most 256 agents with a valid block id, a known kind, a lowercase hyphenated UUID and a folder of at most 4,096 bytes. An agent that leaves its block stays recorded for 15 s while collied follows the same instance, since a shutdown ends the agents before the server stops, then goes. Copilot CLI has no conversation collied binds in Rex, so it is never recorded.
- Planning takes the agents off the record and plans only once that is saved, so a crash or a restart of collied never starts one twice.
- A planned block is replaced only when, read just before acting: it is on the new instance with a shell in front, and a fresh `process` read shows the shell running nothing (it is the block's own program, or the only process under Rex.app's `login`); the shell's screen, read as text, has not changed for 2 s since collied first read it (no prompt shape is read: once nothing is typed and the shell closes only after the agent runs, what protects the user is a shell running nothing and a screen nobody changed in the last seconds); the recorded folder is a directory; no agent in the live model runs the conversation; and a claim under the lock the option's toggle takes finds the block planned, the option on, the window open and the conversation not started on this instance. After the new block starts, a second `process` and screen read must show the same idle shell with exactly the screen it had at the start, and the option and window must still hold, before the old block is closed; otherwise the new block is closed and the user's stays. A collied task's record moves to the new block before the close, so its name, worktree and own session stay with it.
- The option is on by default. `rex-resume-off` in the data folder turns it off, and turning it off deletes the record. The control socket's `rex_resume` request reads it and sets it, audited, and CollieBar shows it as a menu item; CollieTray has none, since collie follows Rex on the Mac only.

## Consequences

- A Codex conversation is recorded only when collied bound it, which needs `codex --no-daemon` (a Codex on the shared daemon reports from the daemon, so collied refuses it) and happens once its first prompt starts. An Antigravity CLI conversation is recorded once its hook reports from under the block's `agy`.
- Each decision and outcome is logged at warn level with the block id and the kind, never the conversation id or folder.

- The resumed agent is its block's program: when it exits, the block closes, as a task's does, instead of returning to a shell.
- The resumed agent gets a new block id, so what the phone keys by terminal id (a star, for example) does not follow it.
- A start that fails after the close (no transcript yet, an expired sign-in) leaves the failed program's terminal where the shell was, or none once it closes.
- `session.new_split` is in collied's method allowlist, so a Rex server without it is not followed at all.
- A lost `session.new_split` answer leaves the agent's block beside the shell, never retried; `session.new_split` ends any zoom in that window.
- A shell the user starts using in the round trip between the second reads and the close is closed with what was typed in it. A startup file waiting in `read` looks idle, and its shell is closed with the question unanswered. Text typed at a restored shell's prompt and left unchanged for 2 s before the start is closed with the shell.
- A restored shell used and left within the window, and a conversation quit less than 15 s before the server stopped, get the agent back.
- A prompt that redraws itself on its own (a clock) keeps its shell from settling, and it is not resumed.
- A restart that plans nothing is logged with why, and each block still waiting when the window ends with its last wait reason.
- Rex.app's restored login shells were not checked against the owner's server.
