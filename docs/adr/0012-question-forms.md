# ADR-0012: A question form is answered only when its call or the screen proves it whole

- Status: accepted
- Date: 2026-11-21 (recorded from the comments of #879)

## Context

Claude Code's AskUserQuestion draws a form of numbered options that the phone can answer. The agent writes the question, its labels and its descriptions, so a form can be worded as a permission prompt, an amend field or the plan prompt, and its text can draw what looks like the dialog's own rules, header and menu. The screen alone cannot say a question form is whole: its text starts at the top rule's column, so a row of `─` in it passes for that rule with the rows above it unseen, and a form taller than the terminal scrolls its options. An answer to a cut or forged form picks an option the owner did not see.

## Decision

### Which dialog it is

- Which dialog blocks the agent is the report's to say, never the wording on screen. A form is reported by herdr's rule for one, or by the kind a herdr-core or Rex agent's own report gives (Claude Code reports `question` for AskUserQuestion's form, `permission` for its permission and plan prompts). Under a report of a form, a menu drawn without a `▔` border is a question, answered only by choosing an option, except the folder trust prompt, which herdr reports as a form. Under any other report a menu that reads as a question is refused, and a report of a permission prompt never takes a menu drawn as a question for one.
- How a menu is drawn comes before any wording (`Menu::is_question`). Claude Code draws AskUserQuestion's form and its review page with the cursor row at column 0 (2.1.289 to 2.1.329), and adds its own entries under a question's options (`Type something.` then `Chat about this`; for a multi-select question a `[ ]` or `[✔]` box before each label, `[ ] Type something` over `Submit`, then `Chat about this`). It indents its permission prompts, the plan prompt and the workflow prompt, and no row of an option's text starts at column 0. Either mark makes a menu a question, whatever its labels read. Only a menu with neither is another dialog by its wording: a permission prompt holds an option that reads as an approval (`classify`) or, left in its amend state after Tab, as an amend field; the plan prompt is told by its own wording (its question over option 1 and `Yes` leading that option, 2.1.289 to 2.1.329), so plans are still chosen from with no session tied. A menu with none of these is no dialog collied knows, whatever call the transcript names, so a form drawn without those marks does not fail open. The review page needs no mark: `Submit answers` and `Cancel` read as no other dialog.
- The unnumbered folder trust prompt has its cursor at column 1, where no row the agent writes starts (an option's text starts at its label's column, 5 or deeper, and a question's at column 0 or behind the gutter).
- `Yes, run it` is the dynamic workflow prompt's approval (2.1.300) only as that whole label; `View raw script` is listed and is no decision.
- A numbered row inside an option's own text is no option (`option_rows`): one under an option row, indented deeper than that row's number, with every row between as deep. Claude Code draws an option's number left of all its text and its numbers in one column; 2.1.329 wraps a description as one paragraph at the label's column with a line break as U+FFFD, so a description of the right width can draw `1. ` or `❯ 2. ` rows, a rule, a header and a menu with the cursor where the agent put it. A blank row ends nothing, since the text may draw one. The cursor is the `❯` row set in least. A form that scrolls marks its last row on screen `↓` in the cursor column, and `↑` above; that row is no option, so no index or decision answers a list not seen whole.

### When a question is answered

- While the session's one pending AskUserQuestion call is known, a form is answered only when it draws that call whole (`Menu::asks`), as the transcript records it, and no other menu gets an answer. Every option of the question is on screen in order, label and description each read whole, followed only by Claude Code's own entries, with no row under the last; the rows between the dialog's first row (header or tabs) and option 1 read the question's whole text, all behind the `│` gutter Claude Code draws a long or multi-line question behind, or none of them. The review page (2.1.329: under the tabs, `Review your answers`, every question whole behind `●` with its answer behind `→`, over `Submit answers` and `Cancel`) must list every question. When the options read as those of more than one question of the call the form is refused, since a cut first question can draw the second's tabs and text; the match is label and description together. Only whitespace is set aside, as wrapping moves it: a text Claude Code rewrites on screen (format characters, a cut at 2000 columns) offers nothing. `Chat about this` keeps its number under options a form hides, so a menu numbered through to it holds every option.
- In Code Mode the model's one tool is a script runner (`REPL`) and a question is a function its script calls; the transcript holds only the script's text. A form is then matched against the script's whole string literals (`Menu::scripted`): the question's text and every option's label and description must each be the whole content of a literal, whitespace aside, and the text on screen must not be the end of a longer literal, which is what a cut form leaves. Claude Code draws no question's options under another's text, so text and options that are each whole are one question's. A script written to hold a decoy literal is not defended against: it could as well ask the short question outright. A script is pending through every call it makes, so beside one a permission prompt is decided as the screen says. The literals are kept as a set, looked up once for each way an option's rows split, since a script of a megabyte can hold a literal hundreds of thousands of times.
- With no such call or script known, only a menu the screen alone shows to be another dialog is answered, so approvals work without the transcript. The one exception is a question asked outside Code Mode: Claude Code 2.1.329 writes a message holding an AskUserQuestion call only once the call has its result, so while the form is up the transcript ends at the prompt. Then the screen alone may stand for the call (`Menu::stands_whole`), only for the versions known to draw so (2.1.329 and later, compared by number), only under a report that a form blocks the agent, and only when the turn is open. 2.1.329 draws a question that holds a line break or is wider than 80 columns behind the gutter, where no row is a rule; any other question is one row of at most 80 columns in a terminal wider than that, and wraps at column 0 in a narrower one (2.1.330, captured). So the form is whole when Claude Code's header or tabs sit directly under its top rule and the text under them is one row of at most 80 columns under a rule of more than 80, or rows all behind the gutter under a rule of more than 75: a question of at most 80 characters without the gutter cannot hold such a rule, a header and a `│` row. A form taller than the terminal hides its header and top rule, and no row the agent writes above it starts at the screen's edge. The menu must end in Claude Code's own entries with no row under the last. Not shown whole this way: the review page of several questions, a form in a terminal of 75 columns or fewer, or one of 80 or fewer whose question fits one row. A rule of the terminal's width with a copy of the header under it reads as a whole form, as Claude Code drew multi-line questions before its gutter: the version check is what tells them apart.
- A menu shaped as a question with no top on screen is refused before any match, and logged as such.
- A matched question is answered by choosing its option, whatever its labels read: no decision, and no Esc for an option labelled `(esc)`. A form with an option that starts with `Yes` still takes no keys typed by hand (`open_to_keys`).
- An approval binds the call's session and id, so a later call asking the same question, the same script run again, or a copy of the session under another process, is another approval. The decision reads the transcript again and sends nothing once the call has its result, as when the question was answered on the Mac.
- The approval keeps the menu on screen whether or not the question rule lets the phone answer it, so a decision under way compares it with the menu it claimed (`Menu::only_changed`); the note Tab types turns `Yes` into text that reads as no approval, on the same prompt.
- A refused form is logged once per blocked episode and reason, whatever its cursor or its approval's expiry reissue, and the log names only the reason and the terminal: never the question's text, its labels or a path.

### Reading the transcript

- The session is the terminal's by process only (`Transcripts::holder`): the pane's own processes for a herdr pane, never herdr's id or an attach target, and for a herdr-core or Rex terminal the session the runtime read from its foreground process. It is refused unless exactly one live process claims that session, since two would write one transcript, and a process list cut at `MAX_PIDS` ties nothing, since a second Claude Code past the cut is not seen. Two sessions in one folder never answer for each other. The sessions folder is listed up to its cap and not judged past it.
- "Not known" is kept apart from "nothing" (`Waits`): only a transcript read whole to the last message says no question is pending. The file is read without the lock on `Transcripts`.
- Pending calls are those of the last assistant message without a result. That message starts at an assistant line of another message or, when lines carry no message id, at a `user` line that is not only tool results. Claude Code writes one line per content block, so parallel calls are several lines of one message and other lines can come between them. A `user` line that is no result under the last call ends the turn, and so does the line Claude Code writes when a call is interrupted; records it writes as the user's that are no prompt do not open a turn. A result above its own call means the file is not what Claude Code wrote. A result is read as its own call's, since any tool's output can hold the text of a receipt or of an event.
- Scripts: where Claude Code asks before running a tool, a `REPL` call has no result until its script ends. In auto mode it answers at once with a receipt, `(dispatched #N)` and nothing else (as a string or one text block), lets the script run, and writes a `poll_events` attachment naming script N in a `repl-eval` event when it ends. A call with a receipt and no such event under it is still running; the numbers restart in a new context, so an event counts for the nearest receipt above it. When the model waits on its scripts itself (`Poll`), the events come as that call's result, and an event counts only where it opens with a nonce the result's first line names, since a script's output can hold a line that opens an event. Only the event's opening tag is read. A script whose line is older than the process died with the process that ran it. When a dispatched script's question is answered, Claude Code writes the question as an AskUserQuestion call of its own and then its result: a read between the two sees a question nobody is asked any more, and a form still drawn once its script ended is asked no more.
- One script that names AskUserQuestion, running or without a result, is what a form is matched against, whatever else waits beside it (Claude Code's own `Poll`, or another call, whose permission prompt is no question form); one AskUserQuestion call with no result and nothing else pending is the question outside Code Mode. With more than one of either, the screen does not say which form is drawn.
- The mode: Claude Code 2.1.329 writes `permission-mode` records through a session, each followed in Code Mode by a `repl-mode` one; a read that starts inside the file and holds neither says nothing of a script above it.
- Nothing is concluded from a read that is not whole: a last line without its newline is still being written and a line that does not parse may be cut, and either can be the result of the call above it or a second call. A read that starts inside the file says nothing of calls above its first line, nor of a result whose call is above it. The pending call must be the session's and no older than its process, so a call a killed session left in a transcript another process resumed is not this terminal's.
- String literals are the text between matching quotes (`'`, `"` or a backtick), with `\n`, escaped quotes and backslashes and `\u` escapes undone. Outside a literal `//` and `/*` open a comment, except after a backslash as in a regular expression; a comment holds no literal and hides none. The script is not otherwise parsed, so a quote in a regular expression throws the read out of step: any sign that a literal may be lost (one a line break or the script's end leaves open, a template holding `${`, an escape not undone) makes the read answer nothing.

### Fixtures

The screens are captures of Claude Code 2.1.329 (100 columns, 2026-11-20) and 2.1.330 (2026-11-21), reduced, with ids, nonces and the plan file's folder renamed. The `live-` and `capture!` transcripts were read while the form was up; the `cut!` ones are finished transcripts cut at the call, which stand for a Claude Code that writes the call first, as the Bash capture shows it does for other tools. The older question captures have no transcript: their calls are written by hand from their screens. Spoofs (a rule and a copy of the header in the question's text, descriptions that draw a menu, an option worded as an approval, amend field or plan prompt, a form set in by a column) are hand-built from captures and say so.

## Consequences

- A Claude Code that draws its question form another way, or writes its transcript another way, gets no answers until its captures are checked and the version gate moves.
- Each rule has a test in `prompt.rs`, `transcript/asked.rs`, `transcript/live.rs` and `tests/approvals.rs`, run against those captures.
